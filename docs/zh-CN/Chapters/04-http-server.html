7  项目 2：从零构建一个 HTTP 服务器

在这一章里，我想和你一起实现一个新的小项目。这一次，我们要从零实现一个基础的 HTTP 服务器。

Zig 标准库里其实已经实现了一个 HTTP 服务器，就在 std.http.Server。但还是那句话，我们这一章的目标是从零实现它，所以不能用 Zig 标准库提供的这个服务器对象。

7.1 什么是 HTTP 服务器？

首先，什么是 HTTP 服务器？和其他任何类型的服务器一样，HTTP 服务器本质上是一个无限期运行的程序：它在一个无限循环里等待客户端发来的连接。服务器收到一个连接后，会接受（accept）这个连接，然后通过这个连接和客户端来回发送消息。

不过，在这个连接里传输的消息有特定的格式。它们是 HTTP 消息（也就是遵循 HTTP 协议规范的消息）。HTTP 协议是现代 Web 的支柱。没有 HTTP 协议，就不会有我们今天所知的万维网。

所以，Web 服务器（其实就是 HTTP 服务器的另一个好听点的叫法）就是和客户端交换 HTTP 消息的服务器。这些 HTTP 服务器和 HTTP 协议规范，对如今万维网的运转至关重要。

整个过程的全貌就是这样。再说一遍，这里涉及两方：一方是服务器（一个无限期运行、等待接收连接的程序），另一方是客户端（想要连接到服务器、和它交换 HTTP 消息的一方）。

Mozilla MDN 文档中关于 HTTP 协议的资料1也是一份很好的参考资源，值得一看。它很好地概述了 HTTP 是怎么工作的，以及服务器在其中扮演什么角色。

7.2 HTTP 服务器是怎么工作的？

把 HTTP 服务器想象成一家大酒店的前台接待员。酒店里有个前台，前台有一位接待员在等客人到来。HTTP 服务器本质上就是一位无限期等待新客人（在 HTTP 的语境里，就是新的客户端）来到酒店的接待员。

客人来到酒店后，会和接待员交谈，告诉接待员他想住几天。然后接待员去查有没有空房。如果当时有空房，客人付了房费，拿到房间钥匙，然后去房间休息。

处理完这位客人的整个流程（查空房、收款、交钥匙）之后，接待员回去做他之前在做的事，也就是等待，等待新的客人到来。

简单来说，这就是 HTTP 服务器做的事。它等待客户端连接到服务器。当客户端尝试连接服务器时，服务器接受这个连接，然后开始通过这个连接和客户端交换消息。这个连接里的第一条消息，总是客户端发给服务器的。这条消息叫作 HTTP 请求（HTTP Request）。

HTTP 请求是一条 HTTP 消息，里面写着客户端想从服务器那里得到什么。它名副其实就是一个请求：连接到服务器的客户端在请求服务器为它做某件事。

客户端可以向 HTTP 服务器发送不同”类型的请求”。但最基础的一种请求，是客户端请 HTTP 服务器把某个特定的网页（也就是一个 HTML 文件）提供（也就是发送）给它。当你在浏览器里输入 google.com 时，本质上就是在向 Google 的 HTTP 服务器发送一个 HTTP 请求，请这些服务器把 Google 的网页发给你。

总之，服务器收到这第一条消息，也就是 HTTP 请求 之后，会分析这个请求，弄清楚：客户端是谁？它想让服务器做什么？它有没有提供执行所请求的操作所需的全部信息？等等。

服务器弄明白客户端想要什么之后，就去执行所请求的操作。最后，为了结束整个过程，服务器会向客户端回发一条 HTTP 消息，告诉它所执行的操作成功与否，然后服务器结束（或者说关闭）和客户端的连接。

服务器发给客户端的这最后一条 HTTP 消息，叫作 HTTP 响应（HTTP Response），因为服务器是在对客户端请求的操作做出响应。这条响应消息的主要目的，是在服务器关闭连接之前，让客户端知道所请求的操作成功了没有。

7.3 HTTP 服务器通常是怎么实现的？

我们拿 C 语言举例。有很多资料教你怎么用 C 代码写一个简单的 HTTP 服务器，比如 Yu (2023)、Weerasiri (2023) 或 Meehan (2021)。考虑到这一点，我在这里就不展示 C 代码示例了，因为你在网上就能找到。不过，我会讲一讲用 C 创建这样一个 HTTP 服务器所需步骤背后的原理。

本质上，在 C 里我们通常用 TCP 套接字（socket）来实现 HTTP 服务器，步骤如下：

  1. 创建一个 TCP 套接字对象。
  2. 给这个套接字对象绑定一个名字（更确切地说，是一个地址）。
  3. 让这个套接字对象开始监听，等待传入的连接。
  4. 连接到来时，接受这个连接，然后交换 HTTP 消息（HTTP 请求和 HTTP 响应）。
  5. 然后直接关闭这个连接。

套接字对象本质上是一个通信通道。你创建的是一个别人可以通过它发送消息的通道。刚创建的套接字对象没有绑定到任何特定的地址。这意味着，这个对象让你手里有了一个通信通道的表示，但这个通道目前还不可用，或者说还没法访问，因为它没有一个已知的地址让别人找到它。

这就是”绑定”（bind）操作要做的事。它给这个套接字对象（也就是这个通信通道）绑定一个名字（更确切地说，是一个地址），让它可以通过这个地址被使用、被访问。而”监听”（listen）操作则让套接字对象在这个地址上监听传入的连接。换句话说，“监听”操作让套接字等待传入的连接。

当客户端真的尝试通过我们指定的套接字地址连接服务器时，为了和客户端建立这个连接，套接字对象需要接受（accept）这个传入的连接。于是，接受了传入的连接之后，客户端和服务器就彼此连接起来，可以开始在这个已建立的连接里读写消息了。

收到客户端的 HTTP 请求、分析它、再把 HTTP 响应发给客户端之后，我们就可以关闭连接，结束这次通信。

7.4 实现服务器：第 1 部分

7.4.1 创建服务器对象

我们先来编写负责监听和接受服务器传入连接的代码。为了让篇幅短一些，我会把这部分代码写在一个单独的 Zig 模块里，命名为 server.zig。

现在，我们基本上需要在代码里创建一个 TCP 套接字对象。在本书之前的版本里，我们选择用 Zig 标准库的 std.posix.socket() 函数来创建这样的 TCP 套接字。但随着 Zig 0.16 引入新的 IO 接口，这个函数和新的 std.Io.net.Stream API 放在一起显得很别扭。

因此，这次我换一条路。简单来说，我们要通过 std.Io.net.IpAddress 的 listen() 方法2来创建 TCP 套接字。然后，对于这个用 std.Io.net.Server 类型表示的 TCP 套接字，我们用 accept() 方法在服务器和客户端之间建立连接。通过 accept() 得到的这个”连接对象”，我们可以访问一个流，服务器和客户端就借助这个流交换消息。

正如我在前面 Section 7.3 中提到的，我们创建的每个套接字对象都代表一个通信通道，需要把这个通道绑定到一个特定的地址上。这里的”地址”指的是一个 IP 地址，更具体地说，是一个 IPv4 地址3。每个 IPv4 地址都由两部分组成。第一部分是主机（host），它是由点号（.）分隔的 4 个数字，用来标识所使用的机器。第二部分是端口号（port），用来标识主机上要使用的那扇特定的”门”，也就是特定的端口。（译注：严格来说，IPv4 地址本身只包含那 4 个数字，“IP 地址 + 端口号”的组合一般称为套接字地址。下面代码里的 std.Io.net.IpAddress 类型同时保存了这两部分。）

这 4 个数字组成的序列（也就是主机）标识的是套接字所在的那台机器（也就是电脑本身）。每台电脑通常都有多扇可用的”门”，因为这样电脑才能同时接收、处理多个连接。它只需给每个连接用一扇门。所以端口号本质上是一个数字，用来标识电脑上套接字用来接收传入连接的那扇”门”。

为了简单起见，这个例子里我会用一个标识当前这台机器的 IP 地址。也就是说，我们的套接字对象会位于我们正在用来编写这些 Zig 源码的这台电脑上（这也叫作”本机”，localhost）。按照惯例，标识”本机”（也就是我们正在用的这台机器）的 IP 地址是 127.0.0.1。所以我们的服务器就用这个 IP 地址。

接下来，需要决定用哪个端口号。按照惯例，有一些端口号是保留的，也就是说我们不能把它们挪作自己的用途，比如 22 号端口（通常用于 SSH 连接）。对于 TCP 连接（也就是我们这里的情况），端口号是一个 16 位无符号整数（在 Zig 里就是 u16 类型），所以取值范围是 0 到 65535 (Wikipedia 2024)。因此，我们可以从 0 到 65535 中选一个数作为端口号。在本书的例子里，我会用 3490 号端口（只是随便挑的一个数）。

上面描述的整个过程和这些步骤，都集中在下面这个我们自定义的结构体 Server 里。注意，我们在这个结构体里创建了一个新的 std.Io.net.IpAddress 对象，还通过这个 IP 地址对象的 listen() 方法创建了 std.Io.net.Server 对象。

const std = @import("std");
const Socket = std.Io.net.Socket;
const Protocol = std.Io.net.Protocol;

pub const Server = struct {
    host: []const u8,
    port: u16,
    addr: std.Io.net.IpAddress,
    io: std.Io,

    pub fn init(io: std.Io) !Server {
        const host: []const u8 = "127.0.0.1";
        const port: u16 = 3490;
        const addr = try std.Io.net.IpAddress.parseIp4(
            host, port
        );

        return .{.host=host, .port=port, .addr=addr, .io=io};
    }

    pub fn listen(self: Server) !std.Io.net.Server {
        std.debug.print("Server Addr: {s}:{any}\n", .{self.host, self.port});
        return try self.addr.listen(
            self.io,
            .{.mode=Socket.Mode.stream, .protocol=Protocol.tcp}
        );
    }
};

7.4.2 监听和接收连接

别忘了，我们在 Section 7.4.1 中写好的 Server 结构体声明位于一个名为 server.zig 的 Zig 模块里。所以在下面的例子里，我把这个模块导入了主模块（main.zig），以便访问 Server 结构体。

现在，存放在 Server 对象里的套接字需要开始监听并接受新的连接。我们可以调用它的 listen() 方法，再对返回的结果调用 accept() 方法来做到这一点。如果运行下面这个主模块，你会发现程序一直不结束，就卡在那里。

之所以这样，是因为程序在等待某件事发生。它在等待有人尝试连接到服务器运行并监听传入连接的那个地址（127.0.0.1:3490）。这就是 listen() 方法做的事：它让套接字处于活动状态，等待有人来连接。

另一方面，accept() 方法是在有人尝试连接套接字时建立连接的那个函数。也就是说，accept() 方法会返回一个新的连接对象作为结果。你可以用这个连接对象从客户端读取消息，或者向客户端写入消息。目前我们还没有对这个连接对象做任何事，下一节就会用到它。

const std = @import("std");
const Server = @import("server.zig").Server;

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    const server = try Server.init(io);
    var listening = try server.listen();
    const connection = try listening.accept(io);
    defer connection.close(io);
}

这个代码示例只允许一个连接。换句话说，服务器会等待一个传入的连接，一旦服务器处理完它建立的第一个连接，程序就结束，服务器也随之停止。

在现实世界里，这可不是常规做法。大多数这样写 HTTP 服务器的人，通常会把 accept() 方法放进一个（无限的）while 循环里：每当 accept() 建立了一个连接，就创建一个新的执行线程来处理这个新连接和对应的客户端。也就是说，现实中的 HTTP 服务器通常依赖并行计算来工作。

在这种设计下，服务器只负责接受连接，而处理客户端、接收 HTTP 请求、发送 HTTP 响应的整个过程，都在后台的一个单独的执行线程里完成。

所以，服务器一接受连接、创建好单独的线程，就会回去做它之前在做的事，也就是无限期地等待下一个要接受的新连接。考虑到这一点，上面给出的代码示例是一个只服务一个客户端的服务器，因为连接一被接受，程序就终止了。

7.4.3 读取客户端发来的消息

现在连接已经建立好了，也就是我们通过 accept() 函数创建的那个连接对象。现在我们可以用这个连接对象读取客户端发给服务器的任何消息，也可以用它向客户端回发消息。

基本思路是：如果我们往这个连接对象里写入数据，就是在向客户端发送数据；如果我们读取这个连接对象里的数据，就是在读取客户端通过这个连接对象发给我们的数据。所以只要记住这个逻辑：“读”是读取客户端发来的消息，“写”是向客户端发送消息。

回想一下 Section 7.2，我们要做的第一件事，是读取客户端发给服务器的 HTTP 请求。因为它是已建立的连接里出现的第一条消息，所以也是我们首先需要处理的东西。

因此，我要在这个小项目里新建一个 Zig 模块，命名为 request.zig，把所有和 HTTP 请求相关的函数放在一起。然后，我会新建一个名为 read_request() 的函数，用我们的连接对象读取客户端发来的消息，也就是 HTTP 请求。

从下面可以看到，read_request() 函数接收三个输入。io 参数接收我们想在 IO 操作中使用的 IO 后端。conn 参数接收我们通过 accept() 方法生成的连接对象。buffer 参数则接收一个缓冲区对象，我们要把客户端发给服务器的请求存进这个缓冲区。

const std = @import("std");
const Stream = std.Io.net.Stream;

pub fn read_request(io: std.Io, conn: Stream, buffer: []u8) !void {
    var recv_buffer: [1024]u8 = undefined;
    var reader = conn.reader(io, &recv_buffer);
    const reader_interface = &reader.interface;
    var start_index: usize = 0;
    for (0..5) |_| {
        const len = try read_next_line(reader_interface, buffer, start_index);
        start_index += len;
    }
}

fn read_next_line(reader: *std.Io.Reader, buffer: []u8, start_index: usize) !usize {
    const next_line = try reader.takeDelimiterInclusive('\n');
    @memcpy(
        buffer[start_index..(start_index + next_line.len)],
        next_line[0..],
    );
    return next_line.len;
}

所以，read_request() 函数本质上是接收一个连接对象（它由一个 IO 流对象表示）作为输入，然后通过”从 IO 流里读取数据”来读取客户端发来的 HTTP 请求，并把这条消息存进我们作为输入提供的那个缓冲区对象。

为此，我先从这个 IO 流对象创建一个 reader 对象。然后调用这个 reader 对象的 takeDelimiterInclusive() 方法，再配合 @memcpy()，真正从流里读取下一行数据。read_request() 里的 for 循环把这个过程重复 6 次，所以我们实际读取的是 HTTP 请求的前 6 行，并把这些数据存进我们之前创建的缓冲区对象。（译注：代码里的循环是 for (0..5)，只会执行 5 次，所以实际读取的是前 5 行。）

7.5 看看程序目前的状态

我觉得现在正是看看程序目前运行情况的好时机，对吧？所以我要做的第一件事，是更新这个小 Zig 项目里的 main.zig 模块，让 main() 函数调用我们刚创建的这个 read_request() 函数。我还会在 main() 函数的末尾加一条打印语句，好让你看看我们刚载入缓冲区对象的 HTTP 请求长什么样。

另外，我在 main() 函数里创建了缓冲区对象（request_buffer），由它负责存储客户端发来的消息，并且用 @memset() 把整个缓冲区对象初始化为零。这一点很重要，能确保这个对象里没有未初始化的内存，因为未初始化的内存可能会在程序里引发未定义行为。

const std = @import("std");
const Request = @import("request.zig");
const Server = @import("server.zig").Server;

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    const server = try Server.init(io);
    var listening = try server.listen();
    const connection = try listening.accept(io);
    defer connection.close(io);

    var request_buffer: [1000]u8 = undefined;
    @memset(request_buffer[0..], 0);
    try Request.read_request(
        io,
        connection,
        request_buffer[0..]
    );

    std.debug.print("{s}\n", .{request_buffer});
}

现在，我要用 zig 编译器的 run 命令执行这个程序。但别忘了，正如前面说过的，程序一执行就会无限期地挂起，因为它在等待客户端尝试连接服务器。

更具体地说，程序会停在调用 accept() 的那一行。一旦有客户端尝试连接服务器，程序就会”恢复”执行，accept() 函数终于执行完毕，创建出我们需要的连接对象，然后程序的其余部分才会运行。

Figure 7.1 展示了这一点。控制台打印出了消息 Server Addr: 127.0.0.1:3490，程序正在等待传入的连接。

终于可以尝试连接这个服务器了，方法有好几种。比如，可以用下面这个 Python 脚本：

import requests
requests.get("http://127.0.0.1:3490")

也可以打开你喜欢的任意一款浏览器，输入网址 localhost:3490。注意：localhost 和 IP 127.0.0.1 是一回事。按下回车，浏览器访问这个地址后，一开始很可能会显示一条消息，说”该网页无法正常运作”（this page isn’t working），随后很可能又变成”无法访问此网站”（the site can’t be reached）。

浏览器之所以显示这些”错误信息”，是因为它没有收到服务器的任何响应。换句话说，浏览器连接到我们的服务器时，确实通过已建立的连接发送了 HTTP 请求。然后浏览器等着收到一个 HTTP 响应，但服务器什么也没返回（我们还没有实现 HTTP 响应的逻辑）。

不过这没关系。我们已经得到了现阶段想要的结果：连接到服务器，并看到浏览器（或者 Python 脚本）发给服务器的 HTTP 请求。

回到你执行程序时开着的那个控制台，会看到程序已经执行结束，控制台上还打印出了一条新消息，这正是浏览器发给服务器的那条 HTTP 请求消息。

由于代码里只读取 HTTP 请求的前 6 行（译注：如前所述，实际是前 5 行），这个程序打印出来的可能不是完整的 HTTP 请求消息，这取决于 HTTP 请求消息有多大。打印出来的 HTTP 请求见 Figure 7.2。

7.6 认识 Zig 中的枚举

Zig 通过 enum 关键字提供枚举结构。枚举（enum，“enumeration”的缩写）是一种特殊的结构，表示一组常量值。所以，如果你有一个变量，它只能取一个范围很小、事先已知的值集合中的值，就可以把这个变量和一个枚举结构关联起来，确保它只会取这个集合里的值。

枚举的一个经典例子是原色。如果出于某种原因，你的程序需要表示某一种原色，就可以创建一个表示这些颜色之一的枚举。在下面的例子里，我们创建了枚举 PrimaryColorRGB，它表示 RGB 色彩体系里的一种原色。用了这个枚举，就能保证像 acolor 这样的对象只会包含 RED、GREEN 或 BLUE 这三个值之一。

const PrimaryColorRGB = enum {
    RED, GREEN, BLUE
};
const acolor = PrimaryColorRGB.RED;
_ = acolor;

如果出于某种原因，我的代码试图往 acolor 里存一个不在这个集合里的值，就会得到一条错误信息，警告我 PrimaryColorRGB 枚举里不存在”MAGENTA”这样的值。这样我就能轻松改正错误。

const acolor = PrimaryColorRGB.MAGENTA;
e1.zig:5:36: error: enum 'PrimaryColorRGB' has
        no member named 'MAGENTA':
    const acolor = PrimaryColorRGB.MAGENTA;
                                   ^~~~~~~

在底层，Zig 的枚举和 C 的枚举工作方式相同。每个枚举值本质上都用一个整数表示：集合里的第一个值用零表示，第二个值是一，依此类推。

下一节我们会了解到，枚举里可以有方法。等等……什么？这太棒了！没错，Zig 的枚举和结构体很像，里面可以有私有方法和公有方法。

7.7 实现服务器：第 2 部分

在这一节，我想集中精力解析从客户端收到的 HTTP 请求。不过，要想有效地解析一条 HTTP 请求消息，首先得了解它的结构。简单来说，HTTP 请求是一条文本消息，分为 3 个不同的部分：

  • 顶层头部（top-level header），指明 HTTP 请求的方法、URI，以及消息所用的 HTTP 版本。
  • HTTP 头部（HTTP header）列表。
  • HTTP 请求的正文（body）。

7.7.1 顶层头部

HTTP 请求的第一行文本总是包含关于这个请求最基本的三项信息。HTTP 请求的这三个关键属性，在请求的第一行里用一个空格分隔。第一项信息是请求所用的 HTTP 方法，第二项是这个 HTTP 请求发往的 URI，第三项是这个 HTTP 请求所用的 HTTP 协议版本。

下面这段内容是 HTTP 请求第一行的一个例子。首先是这个请求的 HTTP 方法（GET）。很多程序员把 URI 部分（/users/list）称为 HTTP 请求发往的”API 端点”（API endpoint）。就这个具体的请求而言，由于它是一个 GET 请求，你也可以说 URI 部分是我们想访问的资源的路径，或者说是我们想从服务器获取的文档（或文件）的路径。

GET /users/list HTTP/1.1

另外，注意这个 HTTP 请求用的是 HTTP 协议的 1.1 版，这是 Web 上最流行的协议版本。

7.7.2 HTTP 头部列表

大多数 HTTP 请求还包含一段 HTTP 头部，它就是与这个请求相关联的一组属性，或者说键值对。这一部分总是紧跟在请求的”顶层头部”之后。

就本章的目的（构建一个简单的 HTTP 服务器）而言，为了简单起见，我们会忽略 HTTP 请求的这一部分。但现实中存在的大多数 HTTP 服务器都会解析并利用这些 HTTP 头部，来改变服务器响应客户端请求的方式。

例如，我们在现实中遇到的很多请求都带有一个叫 Accept 的 HTTP 头部。这个头部里是一个 MIME 类型4列表。这个列表指明了客户端能够读取、解析或解释的文件格式。换句话说，你也可以把这个头部理解为客户端在对服务器说：“嘿！听着，我只能读 HTML 文档，所以请给我回一个 HTML 格式的文档。”

如果 HTTP 服务器能读取并利用这个 Accept 头部，服务器就能判断出要发给客户端的文档用哪种文件格式最合适。也许 HTTP 服务器上同一份文档有多种格式，比如 JSON、XML、HTML 和 PDF，但客户端只能理解 HTML 格式的文档。这就是 Accept 头部的用途。

7.7.3 正文

正文位于 HTTP 头部列表之后，是 HTTP 请求的一个可选部分，也就是说，不是所有 HTTP 请求都带有正文。例如，使用 GET 方法的 HTTP 请求通常都不带正文。

因为 GET 请求是用来请求数据的，而不是向服务器发送数据。所以正文部分更多地和 POST 方法有关，POST 方法会把数据发送给服务器，由服务器处理和存储。

由于这个项目只打算支持 GET 方法，我们也就不需要关心请求的正文了。

7.7.4 创建表示 HTTP 方法的枚举

每个 HTTP 请求都有一个明确的方法。HTTP 请求所用的方法由下面这些词之一来标识：

  • GET；
  • POST；
  • OPTIONS；
  • PATCH；
  • DELETE；
  • 以及其他一些方法。

每种 HTTP 方法都用于一类特定的任务。例如，POST 方法通常用来把一些数据提交（post）到目标那里。换句话说，它用来把一些数据发送给 HTTP 服务器，让服务器处理和存储。

再举个例子，GET 方法通常用来从服务器获取（get）内容。换句话说，每当我们想让服务器给我们发回一些内容时，就用这个方法。内容可以是任何类型：一个网页、一个文档文件，或者一些 JSON 格式的数据。

客户端发送 POST HTTP 请求时，服务器发回的 HTTP 响应通常只有一个目的，就是让客户端知道服务器有没有成功处理并存储数据。相反，服务器收到 GET HTTP 请求时，会在 HTTP 响应本身里发送客户端请求的内容。这说明，HTTP 请求所关联的方法，会在很大程度上改变整个过程的运作方式，以及各方在其中扮演的角色。

由于 HTTP 请求的方法是由这样一组数量很少、内容固定的词来标识的，创建一个枚举结构来表示 HTTP 方法会很合适。这样一来，我们就能轻松检查从客户端收到的 HTTP 请求所用的方法，是不是我们这个小 HTTP 服务器项目目前支持的方法。

下面的 Method 结构就表示这个枚举。注意，目前这个枚举里只包含 GET 这一种 HTTP 方法。因为就本章的目的而言，我只想实现 GET 这一种 HTTP 方法，所以没有把其他 HTTP 方法放进这个枚举。

pub const Method = enum { GET };

现在，我觉得应该给这个枚举结构加上两个方法。一个是 is_supported()，它是一个返回布尔值的函数，表示输入的 HTTP 方法是否受我们的 HTTP 服务器支持。另一个是 init()，它是一个构造函数，接收一个字符串作为输入，并尝试把它转换成一个 Method 值。

不过，为了构建这两个函数，我要用到 Zig 标准库里的一个功能，叫 StaticStringMap()。这个函数可以创建一个从字符串到枚举值的简单映射。换句话说，我们可以用这个映射结构把一个字符串映射到对应的枚举值。在某种程度上，标准库里的这个结构几乎就像一个”哈希表”结构，而且它针对小规模的词集合（或者说小规模的键集合）做了优化，正好是我们这里的情况。我们会在 Section 11.2 中进一步讨论 Zig 中的哈希表。

要使用这个”静态字符串映射”结构，需要从 Zig 标准库的 std.static_string_map 模块导入它。为了让代码更短、更好输入，我会用一个不同的、更短的名字（Map）来导入这个函数。

导入 Map() 之后，只需把这个函数应用到结果映射要用的那个枚举结构上。在我们这里，就是上一个代码示例中声明的 Method 枚举结构。然后，我调用 initComptime() 方法并传入映射内容，也就是我们要用的键值对列表。

在下面的例子里可以看到，我用多个匿名结构体字面量写出了这个映射。在第一个（或者说”顶层的”）结构体字面量里，有一个由结构体字面量组成的列表（或者说序列）。这个列表里的每个结构体字面量代表一个独立的键值对。每个键值对的第一个元素（也就是键）必须是字符串值，第二个元素则必须是你传给 Map() 函数的那个枚举结构里的值。

const std = @import("std");
pub const Method = enum { GET };
const Map = std.static_string_map.StaticStringMap;
const MethodMap = Map(Method).initComptime(.{
    .{ "GET", Method.GET },
});

因此，MethodMap 对象基本上就相当于 C++ 里的 std::map 对象，或者 Python 里的 dict 对象。用映射对象的 get() 方法，可以取得（或者说获取）与某个键对应的枚举值。这个方法返回一个可选值，所以 get() 方法的结果可能是 null。

我们可以利用这一点，检测某个 HTTP 方法是否受我们的 HTTP 服务器支持。因为如果 get() 方法返回 null，就说明它在 MethodMap 对象里没有找到我们提供的方法，也就是说我们的 HTTP 服务器不支持这个方法。

下面的 init() 方法接收一个字符串值作为输入，然后直接把这个字符串值传给 MethodMap 对象的 get() 方法。这样一来，我们就能得到与这个输入字符串对应的枚举值。

注意，在下面的例子里，init() 方法的返回结果要么是一个错误（如果 ? 方法返回 unreachable，就可能出现这种情况，详见 Section 6.4.3），要么是一个 Method 对象。由于 GET 目前是 Method 枚举结构里唯一的值，init() 方法多半会返回 Method.GET。（译注：严格来说，.? 解包到 null 时不会产生错误值，而是触发 unreachable：在 Debug 和 ReleaseSafe 模式下程序会 panic，在 ReleaseFast 和 ReleaseSmall 模式下则是未定义行为。因此这里的 init() 实际上不会返回错误。如果希望遇到不支持的方法时返回错误，可以改写为 return MethodMap.get(text) orelse error.UnsupportedMethod;。）

还要注意，在 is_supported() 方法里，我们用到了 MethodMap 对象的 get() 方法返回的可选值。if 语句会解包这个方法返回的可选值，如果这个可选值不是 null，就返回 true；否则直接返回 false。

const std = @import("std");
pub const Method = enum {
    GET,
    pub fn init(text: []const u8) !Method {
        return MethodMap.get(text).?;
    }
    pub fn is_supported(m: []const u8) bool {
        const method = MethodMap.get(m);
        if (method) |_| {
            return true;
        }
        return false;
    }
};
const Map = std.static_string_map.StaticStringMap;
const MethodMap = Map(Method).initComptime(.{
    .{ "GET", Method.GET },
});

7.7.5 编写解析请求的函数

现在我们已经创建了表示 HTTP 方法的枚举，应该开始编写真正负责解析 HTTP 请求的函数了。

首先可以写一个结构体来表示 HTTP 请求。以下面的 Request 结构体为例，它包含 HTTP 请求”顶层”头部（也就是第一行）里的三项基本信息。

const Request = struct {
    method: Method,
    version: []const u8,
    uri: []const u8,
    pub fn init(method: Method,
                uri: []const u8,
                version: []const u8) Request {
        return Request{
            .method = method,
            .uri = uri,
            .version = version,
        };
    }
};

parse_request() 函数应该接收一个字符串作为输入。这个输入字符串包含 HTTP 请求消息，解析函数需要读取并理解这条消息的各个组成部分。

别忘了，就本章的目的而言，我们只关心这条消息的第一行。这一行包含”顶层头部”，也就是 HTTP 请求的三个基本属性：所用的 HTTP 方法、URI 和 HTTP 版本。

注意，我在 parse_request() 里用了 indexOfScalar() 函数。Zig 标准库里的这个函数会返回我们提供的标量值在字符串中第一次出现的索引。这里我要找的是换行符（\n）第一次出现的位置，因为再说一遍，我们只关心 HTTP 请求消息的第一行。我们想解析的三项信息（HTTP 版本、HTTP 方法和 URI）就在这一行。

因此，我们用这个 indexOfScalar() 函数把解析过程限制在消息的第一行。还值得一提的是，indexOfScalar() 函数返回的是一个可选值，所以我用 orelse 关键字提供了一个备用值，以防这个函数返回的是 null。

由于这三个属性之间都用一个空格分隔，我们可以用 Zig 标准库里的 splitScalar() 函数，找出每个出现空格的位置，把输入字符串切分成几段。换句话说，这个 splitScalar() 函数相当于 Python 里的 split() 方法、C++ 里的 std::getline() 函数，或者 C 里的 strtok() 函数。

用 splitScalar() 函数时，得到的结果是一个迭代器。这个迭代器有一个 next() 方法，可以用来把迭代器推进到下一个位置，也就是切分后字符串的下一段。注意，用 next() 时，这个方法不仅会推进迭代器，还会把指向切分后字符串当前这一段的切片作为结果返回。

如果你想取得指向切分后字符串当前这一段的切片，但又不想把迭代器推进到下一个位置，可以用 peek() 方法。next() 和 peek() 方法都返回可选值，所以我用 ? 方法来解包这些可选值。

pub fn parse_request(text: []u8) Request {
    const line_index = std.mem.indexOfScalar(
        u8, text, '\n'
    ) orelse text.len;
    var iterator = std.mem.splitScalar(
        u8, text[0..line_index], ' '
    );
    const method = try Method.init(iterator.next().?);
    const uri = iterator.next().?;
    const version = iterator.next().?;
    const request = Request.init(method, uri, version);
    return request;
}

（译注：parse_request() 的返回类型不是错误联合类型，函数体内却用了 try。这段代码之所以能通过编译，是因为 Method.init() 推断出的错误集为空，try 实际上不会返回任何错误。如果按前面译注的方式让 init() 返回 error.UnsupportedMethod，就需要把 parse_request() 的返回类型同步改为 !Request，并在调用处加上 try。）

正如我在 Section 1.8 中说过的，在 Zig 语言里，字符串就是字节数组。所以在 Zig 标准库的这个 mem 模块里，你会找到很多可以直接处理字符串的好用的工具函数。其中一些有用的工具函数，我们已经在 Section 1.8.5 中介绍过了。

7.7.6 使用解析请求的函数

既然已经写好了负责解析 HTTP 请求的函数，就可以在程序的 main() 函数里加上对 parse_request() 的调用了。

之后，最好再测试一下程序目前的状态。我再次用 zig 编译器的 run 命令执行这个程序，然后用浏览器通过网址 localhost:3490 再次连接服务器，最后，Request 对象的最终结果被打印到了控制台上。

顺带说明一下：由于我在打印语句里用了 any 格式说明符，Request 结构体的数据成员 version 和 uri 被打印成了原始的整数值。在 Zig 里，字符串数据被打印成整数值是很常见的。别忘了，这些整数值只是组成相应字符串的那些字节的十进制表示。

在下面的结果里，十进制数值序列 72, 84, 84, 80, 47, 49, 46, 49 和 13 是组成文本”HTTP/1.1”的字节。而整数 47 是字符 / 的十进制值，它表示这个请求里的 URI。（译注：最后那个 13 是回车符 \r。HTTP 请求的每一行都以 \r\n 结尾，而 parse_request() 只在 \n 处截断，所以 \r 被留在了 version 的末尾。）

const std = @import("std");
const Request = @import("request.zig");
const Server = @import("server.zig").Server;

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    const server = try Server.init(io);
    var listening = try server.listen();
    const connection = try listening.accept(io);
    defer connection.close(io);

    var request_buffer: [1000]u8 = undefined;
    @memset(request_buffer[0..], 0);
    try Request.read_request(
        io,
        connection,
        request_buffer[0..]
    );
    const request = Request.parse_request(request_buffer[0..]);
    std.debug.print("{any}\n", .{request});
}
request.Request{
    .method = request.Method.GET,
    .version = {72, 84, 84, 80, 47, 49, 46, 49, 13},
    .uri = {47}
}

7.7.7 把 HTTP 响应发给客户端

在这最后一部分，我们要编写负责把 HTTP 响应从服务器发给客户端的逻辑。为了简单起见，这个项目里的服务器只发送一个包含文本”Hello world”的简单网页。

首先，我在项目里新建一个 Zig 模块，命名为 response.zig。在这个模块里，我只声明两个函数，每个函数对应 HTTP 响应里的一个特定状态码。send_200() 函数会向客户端发送一个状态码为 200（表示”成功”）的 HTTP 响应，而 send_404() 函数发送的是状态码为 404（表示”未找到”）的响应。

这显然不是处理 HTTP 响应最顺手、最恰当的方式，但对我们这里的情况来说够用了。毕竟我们在这本书里做的只是一些练手的玩具项目，所以写出来的源码不需要完美，能用就行！

const std = @import("std");
const Stream = std.Io.net.Stream;

pub fn send_200(conn: Stream, io: std.Io) !void {
    const message = (
        "HTTP/1.1 200 OK\nContent-Length: 48"
        ++ "\nContent-Type: text/html\n"
        ++ "Connection: Closed\n\n<html><body>"
        ++ "<h1>Hello, World!</h1></body></html>"
    );
    var stream_writer = conn.writer(io, &.{});
    _ = try stream_writer.interface.write(message);
}

pub fn send_404(conn: Stream, io: std.Io) !void {
    const message = (
        "HTTP/1.1 404 Not Found\nContent-Length: 50"
        ++ "\nContent-Type: text/html\n"
        ++ "Connection: Closed\n\n<html><body>"
        ++ "<h1>File not found!</h1></body></html>"
    );
    var stream_writer = conn.writer(io, &.{});
    _ = try stream_writer.interface.write(message);
}

注意，这两个函数都接收连接对象作为输入，从这个连接对象创建一个写入器（writer）对象，然后用 write() 方法把 HTTP 响应消息直接写进这个通信通道。这样，连接另一端的那一方（也就是客户端）就会收到这条消息。（译注：在 Zig 0.17 里，std.Io.Writer.write() 最多调用一次底层的 drain，返回实际写出的字节数，这个数可能小于消息长度，而代码里用 _ = 丢弃了它。这里的消息很短，实践中通常一次就能写完；要保证整条消息都写出去，应该改用 writeAll()。）

现实中的大多数 HTTP 服务器，都会用一个函数（或一个结构体）来专门处理响应。它接收已经解析好的 HTTP 请求作为输入，然后一点一点地构建 HTTP 响应，最后再通过连接把它发出去。

我们还会有一个专门的结构体来表示 HTTP 响应，以及很多用来构建响应对象各个部分或组件的方法。

7.8 最终结果

现在，我们可以再次更新 main() 函数，把 response.zig 模块里的新函数整合进来。首先，我需要把这个模块导入 main.zig 模块，然后加上对 send_200() 和 send_404() 的调用。

注意，我用 if 语句来决定调用哪个”响应函数”，主要依据是 HTTP 请求里的 URI。如果用户请求的内容（或文档）在我们的服务器上不存在，就应该用 404 状态码响应。不过，由于我们只有一个简单的 HTTP 服务器，没有真正的文档可以发送，所以只需检查 URI 是不是根路径（/），就能决定调用哪个函数。

另外，注意我用了 Zig 标准库里的 std.mem.eql() 函数，来检查 uri 里的字符串是否等于字符串 "/"。我们已经在 Section 1.8.5 中介绍过这个函数，如果你对它还不熟悉，可以回到那一节看看。

const std = @import("std");
const Method = @import("request.zig").Method;
const Request = @import("request.zig");
const Response = @import("response.zig");
const Server = @import("server.zig").Server;

pub fn main(init: std.process.Init) !void {
    const io = init.io;
    const server = try Server.init(io);
    var listening = try server.listen();
    const connection = try listening.accept(io);
    defer connection.close(io);

    var request_buffer: [1000]u8 = undefined;
    @memset(request_buffer[0..], 0);
    try Request.read_request(
        io,
        connection,
        request_buffer[0..]
    );
    const request = Request.parse_request(request_buffer[0..]);
    if (request.method == Method.GET) {
        if (std.mem.eql(u8, request.uri, "/")) {
            try Response.send_200(connection, io);
        } else {
            try Response.send_404(connection, io);
        }
    }
}

调整好 main() 函数之后，就可以执行程序，看看这最后几处改动的效果了。首先，我再次用 zig 编译器的 run 命令执行程序。程序会挂起，等待客户端连接。

然后，我打开浏览器，再次用网址 localhost:3490 尝试连接服务器。这一次，浏览器不会再显示某种错误信息，而是会显示消息”Hello World”。因为这一次，服务器成功把 HTTP 响应发给了浏览器，如 Figure 7.3 所示。
