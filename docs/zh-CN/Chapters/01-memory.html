3  内存与分配器（Allocators）

在本章中，我们将深入探讨内存（Memory）。Zig 是如何管理内存的？日常开发中使用哪些常用工具？有哪些关键特性让 Zig 的内存管理与众不同？你都将在本章中找到答案。

计算机的一切运算都建立在内存基础之上。内存就像一张临时工作台，用来安放计算过程中产生的所有临时数据。没有内存，编程语言里的“变量”与“对象”就成了无源之水。

3.1 内存空间（Memory spaces）

你在 Zig 源码中创建的每一个对象，都需要存放在计算机内存中的某个地方。根据你在哪里、以何种方式定义对象，Zig 会使用不同的”内存空间”（即不同类型的内存）来存放这个对象。 根据定义位置和方式的不同，Zig 会把对象分配到不同的“内存区域”中。

在 Zig 里，我们最关心的内存区域主要有 3 个：

  1. 全局数据段（Global Data Section）；
  2. 栈（Stack）；
  3. 堆（Heap）。

3.1.1 编译期已知 vs 运行时已知

Zig 在决定把一个对象塞到哪个内存空间时，核心评判标准之一就是：这个值到底是在“编译期”就已知，还是必须等“运行时”才能算出来？

在用 Zig 编写程序时，程序中某些对象的值是编译期已知（compile-time known）的。也就是说，在编译 Zig 源码的过程中，zig 编译器能够推算出源码中某个对象的确切值。

对 zig 编译器来说，它其实最在乎的是对象的长度/占用空间大小（Size），其次才是具体的数值。当然，如果值已知，那大小自然水落石出。

因此，编译器的首要任务是摸清每个对象到底占多少字节： - 如果值在编译期已知，那大小自动敲定； - 如果值要在运行时才能算出，那么只有当该对象的类型具备固定的物理尺寸时，其大小才算编译期已知。

什么叫“具有固定的物理尺寸”？比如 u32 占 4 字节、[10]u8 占 10 字节。 反过来，如果类型里包含一个长度不定的切片 []const u8，那它在编译期就属于“尺寸不固定”。因为在运行时这个切片可能装 2 个元素，也可能装 1000 个元素，编译器根本没法未卜先知。

例如，正如在 Section 1.8 中所述，Zig 中的字符串对象在底层是任意字节组成的数组；而正如在 Section 1.8.1 中所讨论的，这个字节数组通常以字节切片（[]const u8）的形式被访问。如果某个函数接收一个字符串作为输入（比如要在数据库中创建的用户名，或者要搜索的商品名称），我们在编写函数时是无法提前预知输入字符串的确切长度的——它可能只有 10 个字符，也可能有 100 个字符。

因此，任何包含“无显式固定大小数据成员”的类型或结构体声明，都会使该类型或结构体在编译期不具备已知固定大小。相反，如果你声明的结构体包含的是固定长度的数组成员（例如 [60]u8，即包含 60 个 u8 元素的数组），那么该结构体类型在编译期就具有已知的固定大小；此时编译器无需在编译期知道该类型对象的具体数值，仅凭类型本身就能算出存储该对象所需的空间。

看下面这个例子：

fn input_length(input: []const u8) usize {
    const n = input.len;
    return n;
}

pub fn main() !void {
    const name = "Pedro";
    const array = [_]u8{1, 2, 3, 4};
    _ = name; _ = array;
}

在 main() 函数里，常量 name 和 array 的内容直接硬编码在源码中，编译器一眼就能把它们算出来，这就是典型的编译期已知。

而在 input_length() 函数里，形参 input 是一个 []const u8 切片。在编译时不可能知道这个参数的值，也不可能知道它的长度，因为它是一个在参数类型注解中没有显式指定固定长度的切片。所以 input 的值和长度都只有在运行时才知道，表达式 input.len 的值也是如此。这是所有函数共有的特性：请记住，函数参数的值通常不是”编译期已知”的。

不过请注意：虽然 input.len 的具体数值是运行时才能拿到的，但承接结果的变量 n 的类型是 usize，而 usize 本身的内存占用在当前平台上是完全固定的（64 位系统上就是 8 字节）。所以 n 所需的内存空间在编译期依然是确定的。

3.1.2 全局数据段（Global Data Register / Section）

全局数据段是最终编译出来的二进制可执行文件中的一个静态区域，专门存放所有在编译期就彻底确定下来的数据。

你在源码里写的所有字面量（比如字符串字面量 "this is a string"、整数 10、布尔值 true），以及所有在编译期已知且不可变的常量，统统被烘焙到了二进制文件的全局数据段里。

说实话，你不需要太关心这块内存空间。因为你无法控制它，也不能有意地访问它或把它用于自己的目的。另外，这块内存空间也不会影响程序的逻辑，它只是存在于你的程序中而已。

3.1.3 栈内存 vs 堆内存

在系统级开发圈子里，“栈（Stack）还是堆（Heap）”永远是绕不开的经典话题。 初学者经常容易被“Stack vs Heap”这种字眼误导，以为它俩是非此即彼的对立关系。其实不然！在真实项目中，栈和堆是紧密互补的搭档，几乎每一个像样的 Zig 程序都在同时结合使用两者。

本质上，栈内存通常用于存放长度固定且在编译期已知的值；相比之下，堆内存是一种动态的内存空间，用于存放在程序执行（运行时）期间长度可能增长的值 (Chen and Guo 2022)。

运行时会增长的长度，本质上与”运行时已知”的值相关联。换句话说，如果一个对象的长度可能在运行时增长，那么这个对象的长度在编译期就是未知的；长度在编译期未知，这个对象的值在编译期也就未知。这类对象应当存放在堆内存空间中，堆是一块动态的内存空间，可以增长或收缩以适应对象的大小。

3.1.4 深入剖析栈内存（Stack）

栈内存之所以叫“栈”，是因为它在底层的管理方式采用了栈数据结构（Stack Data Structure）的后进先出（LIFO - Last In, First Out）机制。相信你对这种数据结构并不陌生；如果想温习其原理，可以参考 Wikipedia 页面1或 Geeks For Geeks 教程2。

在 Zig 中，每次进行函数调用时，都会在栈上为这次函数调用预留一块空间，即栈帧（stack frame） (Chen and Guo 2022; Zig Software Foundation 2024)。这次调用中传给函数的每个参数的值，都存放在这块栈空间中；你在函数作用域内声明的每个局部对象，通常也存放在这块栈空间中。 函数的所有形参、以及在函数体大括号内声明的局部变量，通通存放在这个专属栈帧里。

看下面这个例子：

fn add(x: u8, y: u8) u8 {
    const result = x + y;
    return result;
}

pub fn main() !void {
    const r = add(5, 27);
    _ = r;
}

在上面的代码里，result 是 add() 内部的局部变量，存放在 add 的栈帧里；而 main() 里的 r 则存放在 main 的栈帧里。

栈内存最大的杀手级特性是：全自动释放！ 只要函数执行完毕 return 返回，它对应的整个栈帧会被瞬间弹出并销毁，里面的所有局部变量灰飞烟灭。开发者完全不需要写一行代码去释放栈上的局部变量。

Important

核心认知：分配在栈上的局部对象，在离开其所属的花括号作用域时，会被系统全自动销毁，不需要也不应该手动清理。

不仅是函数，for 循环、if 分支等任何用花括号 {} 圈出来的作用域也是同样的道理。出了大括号，里面的局部变量就彻底失效了：

// 这段代码根本编译不过！
const a = [_]u8{0, 1, 2, 3, 4};
for (0..a.len) |i| {
    const index = i;
    _ = index;
}
// 试图在循环体外面访问 index，直接报错，因为栈变量早随着作用域销毁了
std.debug.print("{d}\n", .{index});

这一机制带来了一个极其重要的推论：一旦函数返回，你就再也不能访问该函数在栈上预留空间内的任何内存地址，因为这片栈空间已经被销毁了。这意味着：如果局部对象存储在栈上，你绝对不能编写一个返回指向该局部对象指针的函数。

不妨想一想：既然栈上的所有局部对象在函数作用域结束时都会被销毁，返回指向它们的指针又有什么意义呢？这个指针指向的地址已经不存在了。如果函数直接返回局部对象本身（即按值返回），那是完全合法的；但绝不能返回指向栈上局部对象的指针。

再以 add() 函数为例，如果你将其改写为返回指向局部对象 result 的指针，zig 编译器实际上会通过编译，不会报任何警告或错误。表面上看代码似乎没问题，但一旦你尝试读取返回值 r 中的内容，或在后续表达式中使用它，就会触发未定义行为（Undefined Behavior）并引发严重的程序 Bug (Zig Software Foundation 2024, 参见 “Lifetime and Ownership”3 与 “Undefined Behaviour”4 章节)。

fn add(x: u8, y: u8) *const u8 {
    const result = x + y;
    return &result;
}

pub fn main() !void {
    // 这段代码能编译通过，但存在未定义行为（UB）！
    // 切勿这样写！对象 `r` 的值是未定义的！
    const r = add(5, 27); _ = r;
}

这种“指向栈变量的无效指针（悬垂指针）”问题在许多编程语言社区中都广为人知（在 C 或 C++ 中返回局部栈变量的地址同样会导致未定义行为）。

Important

如果函数内的局部对象存储在栈上，切勿从函数中返回指向该局部对象的指针。因为函数栈空间会在作用域结束时被销毁，该指针在函数返回后必然处于未定义状态。

那么，如果确实需要在函数返回后继续通过指针使用该对象，应该怎么做呢？答案与 C/C++ 一样：将对象存储在堆（Heap）上，并返回指向堆内存的地址。堆内存具有灵活得多的生命周期，允许你在函数返回后依然持有指向该对象的有效指针。

3.1.5 深入剖析堆内存（Heap）

栈虽然快如闪电，但有两个致命硬伤： 1. 尺寸必须在编译期定死； 2. 离开作用域立即自毁。

这时候就需要堆内存来挑大梁了！ 堆是极其开阔且灵活的动态内存空间，专为“运行时动态扩容”和“持久跨作用域生命周期”而生。

典型的例子是网络服务器（HTTP 服务、RPC 网关等）：服务器在启动前根本无法预估今天会涌进来 1 个请求还是 10 万个请求，每个请求上传的报文到底有多大。这种动态伸缩的业务场景，只能由堆内存来承载。

但世界上没有免费的午餐：堆内存带来了极致的自由度，代价是所有权与生命周期的管控责任完全落在了程序员的肩上！

与栈内存不同，堆内存由程序员显式分配，并且在被显式释放之前不会被回收 (Chen and Guo 2022)。

在 Zig 中，若要将对象存储在堆上，程序员必须显式使用分配器（Allocator）在堆上开辟空间。在 Section 3.3 中，我将详细介绍如何使用分配器在 Zig 中分配内存。

Important

底层铁律：在堆上申请的每一片内存，都必须在用完后由你亲手释放！绝不能有头无尾。

Zig 中的大多数分配器确实是在堆上分配内存，但也有例外，比如 ArenaAllocator() 和 FixedBufferAllocator()：ArenaAllocator() 是一种配合底层子分配器协同工作的特殊分配器；而 FixedBufferAllocator() 则基于预先创建的固定缓冲区对象工作（如果该缓冲区创建在栈上，那么它实际上只在栈上分配空间）。

3.1.6 内存空间决策速查表

总结一下 zig 编译器分配存储位置的内在逻辑：

  1. 字面量（如 "abc"、123）：存放于全局只读数据段；
  2. 编译期已知常量的 const 对象：存放于全局数据段；
  3. 长度在编译期固定的局部变量/常量：存放于当前栈帧；
  4. 通过分配器的 alloc() 或 create() 申请的对象：存放于该分配器管辖的内存池中（除固定栈缓冲区等特殊类型外，通常为堆内存）；
  5. 堆只能通过分配器访问。如果你的对象不是通过分配器对象的 alloc() 或 create() 方法创建的，那么几乎可以肯定它不是存放在堆上的对象。

3.2 栈溢出（Stack Overflow）

在栈上分配内存通常比在堆上更快，但这种性能优势伴随着诸多限制。除了我们在 Section 3.1.4 中讨论过的生命周期和固定大小限制外，栈本身的容量上限也是一个重要限制。

栈的容量是有限的（具体大小因硬件架构和操作系统而异，但通常都不大），因此栈一般只用来存放体积较小的临时对象。如果你试图在栈上进行超过栈容量上限的大规模分配，就会发生栈溢出（Stack Overflow），并直接导致程序崩溃（抛出 Segmentation fault 段错误）：

var very_big_alloc: [1000 * 1000 * 24]u64 = undefined;
@memset(very_big_alloc[0..], 0);
Segmentation fault (core dumped)

所以，大号数据和超长缓冲区千万别硬塞在栈上，老老实实用堆！

3.3 分配器（Allocators）：Zig 的灵魂基石

在 Zig 的设计哲学里，有一条震撼整个系统开发圈的原则：“在 Zig 里，标准库绝不存在任何暗中瞒着你的隐藏内存分配！” (Sobeston 2024)。

这是一个众所周知的问题，尤其是在 C++ 中。因为在 C++ 里，有些运算符会在背后分配内存，而在真正去读这些运算符的源码、找到其中的内存分配调用之前，你根本无从得知。许多程序员觉得这种行为很烦人，而且难以追踪。

而在 Zig 里，规则透明到了极致：如果标准库中的某个函数、运算符或其他任何东西在执行过程中需要分配内存，它就必须接收一个由用户提供的分配器作为输入，才能真正分配所需的内存。

这就形成了一条一目了然的判别法则： 只要看一下函数的参数就能区分：如果一个函数或运算符的输入（参数）中有一个分配器对象，你就可以确定这个函数（运算符）在执行过程中会分配内存。

以标准库的 std.fmt.allocPrint() 为例（它类似 C 的 sprintf，用于动态拼装格式化字符串）：因为需要根据格式化结果动态申请内存，它的第一个形参就是 allocator：

var gpa = std.heap.DebugAllocator(.{}){};
const allocator = gpa.allocator();
const name = "Pedro";
const output = try std.fmt.allocPrint(
    allocator,
    "Hello {s}!!!",
    .{name}
);
try stdout.print("{s}\n", .{output});
try stdout.flush();
Hello Pedro!!!

由调用者来掌控“用哪种分配器、分配到哪里”，这才是真正的“内存全权掌控”。

3.3.1 什么是 Allocator？

在 Zig 中，Allocator（分配器）是供你在程序运行期间动态申请内存的对象，作用类似于 C 语言中的 malloc() 和 calloc()。它们通常位于标准库的 std.heap 模块下，只需 @import("std") 即可使用。

更重要的是，Zig 中的每一个分配器对象都建立在统一的 Allocator 接口之上。这意味着无论你使用哪种分配器，它都必定提供 alloc()、create()、free() 和 destroy() 方法——你可以随时更换底层分配器的类型，而无需改动业务代码中调用内存分配与释放的函数签名。

3.3.2 为什么我们需要分配器？

正如在 Section 3.1.4 中所述，每次在 Zig 中调用函数时，系统都会在栈上预留一段固定空间。但栈有着一条致命的物理局限：存放在栈上的任何对象，在编译期都必须具有固定已知的尺寸。

然而在真实的工程开发中，有两个最常见的场景直接击碎了这一局限： 1. 函数内部创建的对象，其体积在执行过程中可能会不断动态膨胀； 2. 很多时候我们根本无法提前预知会接收到多少外部输入、或者输入数据究竟有多大。

此外还有一个极为核心的动机：从函数中向外部调用方返回一个指向新创建对象的指针。 正如我们在 Section 3.1.4 强调的，如果这个对象存放在栈上，函数一退出栈帧即被销毁，返回该指针就会导致严重悬垂指针 Bug。但如果该对象存放在堆上，它的生命周期就完全由程序员本人掌控，你可以随心所欲决定何时销毁释放它。

正是为了应对这些栈无法胜任的场景，我们必须借助堆内存与分配器（Allocator）对象来实现动态内存管理。

3.3.3 不同类型的分配器（The different types of allocators）

目前 Zig 标准库最常用的几种分配器包括：

  • DebugAllocator()
  • page_allocator()
  • FixedBufferAllocator() 与 ThreadSafeFixedBufferAllocator()
  • ArenaAllocator()
  • c_allocator()（需要链接 libc）

每种分配器都有各自的优势与适用边界。除 FixedBufferAllocator() 和 ArenaAllocator() 外，其余分配器都直接在堆上分配内存。

3.3.4 通用分配器（General-purpose allocators）

DebugAllocator() 是一款通用型分配器，适用于各类常规开发场景。在下面的示例中，我们使用它为对象 some_number 分配足以存储单个整数的空间：

const std = @import("std");

pub fn main() !void {
    var gpa = std.heap.DebugAllocator(.{}){};
    const allocator = gpa.allocator();
    const some_number = try allocator.create(u32);
    defer allocator.destroy(some_number);

    some_number.* = @as(u32, 45);
}

此外，你也可以使用 c_allocator()，它是对 C 标准库分配器 malloc() 的封装。如果你选择使用 c_allocator()，在使用 zig 编译器编译源码时必须加上 -lc 标志以链接 Libc，否则 Zig 将无法在系统中找到 malloc() 的实现。

3.3.5 页分配器（Page allocator）

page_allocator() 每次都会在堆上按完整的内存页（Page）进行分配，而不是只切分一小块内存。

内存页的大小取决于具体操作系统，大多数系统的堆内存页大小为 4KB，因此每次调用 page_allocator() 通常都会直接申请 4KB 内存。这使得 page_allocator() 分配速度很快，但也比较“浪费”空间——如果你只需要存几个字节，整页分配会造成明显的空间闲置。

3.3.6 缓冲区分配器（Buffer allocators）

FixedBufferAllocator() 和 ThreadSafeFixedBufferAllocator() 以一个固定大小的缓冲区（Buffer）对象作为底层内存池。当你请求分配内存时，它们实际上是在你预先提供的这块固定缓冲区内划分空间。

这意味着：使用这类分配器前，你必须先在代码中创建一个缓冲区对象并将其传入；同时也意味着它们既可以在栈上分配内存，也可以在堆上分配内存——完全取决于你提供的底层缓冲区位于栈上还是堆上。

在下面的示例中，我们在栈上创建了一个长度为 10 的 buffer 数组，并将其传给 FixedBufferAllocator.init()。由于 buffer 只有 10 个元素的空间，我们最多只能从中分配 10 个元素；一旦超额申请，alloc() 方法就会返回 OutOfMemory 错误：

var buffer: [10]u8 = undefined;
for (0..buffer.len) |i| {
    buffer[i] = 0; // Initialize to zero
}

var fba = std.heap.FixedBufferAllocator.init(&buffer);
const allocator = fba.allocator();
const input = try allocator.alloc(u8, 5);
defer allocator.free(input);

那么，如果底层缓冲区位于堆上呢？正如我们在 Section 3.2 中所述，使用堆而非栈的主要原因之一就是开辟超大容量来存放巨型对象。假如你想拿一块非常大的缓冲区（例如 100 MB）作为 FixedBufferAllocator 的底层空间，就应当先在堆上分配这块大缓冲区，如下例所示：

const heap = std.heap.page_allocator;
const memory_buffer = try heap.alloc(
    u8, 100 * 1024 * 1024 // 100 MB memory
);
defer heap.free(memory_buffer);
var fba = std.heap.FixedBufferAllocator.init(
    memory_buffer
);
const allocator = fba.allocator();

const input = try allocator.alloc(u8, 1000);
defer allocator.free(input);

3.3.7 竞技场分配器（Arena allocator）

ArenaAllocator() 接收一个子分配器（Child Allocator）作为输入。它的设计理念类似于 Go 语言中的“Arena（区域内存管理）”概念5：允许你按需调用任意多次内存分配，但最后只需调用一次 deinit() 即可将所有已分配的内存一次性全部释放。

例如在下面的代码中，我们将 DebugAllocator() 实例传给 ArenaAllocator.init()，后续每次调用 alloc() 实际上都是由底层的 DebugAllocator() 完成分配。我们连续调用了 3 次 alloc()，如果不用 ArenaAllocator，就需要分别调用 3 次 free()；而借助 ArenaAllocator，只需在作用域结束时调用一次 aa.deinit() 即可统一回收：

var gpa = std.heap.DebugAllocator(.{}){};
var aa = std.heap.ArenaAllocator.init(gpa.allocator());
defer aa.deinit();
const allocator = aa.allocator();

const in1 = try allocator.alloc(u8, 5);
const in2 = try allocator.alloc(u8, 10);
const in3 = try allocator.alloc(u8, 15);
_ = in1; _ = in2; _ = in3;

3.3.8 alloc() 与 free() 方法

在下面的代码示例中，我们访问标准输入通道 stdin 并通过 takeDelimiterExclusive() 方法读取用户输入的一行文本。为了在程序中保存这段输入，我们使用分配器的 alloc() 方法在堆上开辟了一个足以存放 50 个 u8 元素的数组。

注意 alloc() 方法接收两个参数：第一个参数是元素的数据类型（此处为 u8），第二个参数是数组的元素个数（此处为 50）。正如我们在 Section 1.8 中所述，Zig 中的字符串本质上是字节数组，每个 ASCII 字符由一个 u8 值表示6，因此 input 数组可以存储 50 个字节的字符串。换言之，var input: [50]u8 = undefined 会在当前栈帧上创建 50 字节的数组，而 var input = try allocator.alloc(u8, 50) 则会在堆上分配同样的数组：

const std = @import("std");

pub fn main(init: std.process.Init) !void {
    var stdin_buffer: [1024]u8 = undefined;
    var stdin_reader = std.Io.File.stdin().reader(init.io, &stdin_buffer);
    const stdin = &stdin_reader.interface;

    var gpa = std.heap.DebugAllocator(.{}){};
    const allocator = gpa.allocator();

    var input = try allocator.alloc(u8, 50);
    defer allocator.free(input);
    @memset(input[0..], 0);

    // Read user input until a line break is found.
    const stream = try stdin.takeDelimiterExclusive('\n');
    // Store the input into our heap memory.
    @memcpy(input[0..stream.len], stream[0..]);
    // Print our heap memory, so that we can see what
    // was stored in it.
    std.debug.print("{s}\n", .{input});
}

同时注意，我们在示例中使用了 defer 关键字（详见 Section 2.1.3），以便在当前作用域结束时自动执行 allocator.free(input) 释放为 input 分配的堆内存。正如在 Section 3.1.5 中强调的，任何通过分配器申请的内存都必须使用同一个分配器的 free() 方法显式释放。

3.3.9 create() 与 destroy() 方法

借助 alloc() 和 free()，我们可以一次性分配用于存储多个元素的数组切片。但如果你只需要存储单个独立元素（例如单个结构体实例），应该用 alloc() 分配一个长度为 1 的数组吗？答案是否定的！

针对单个对象的分配与释放，每个分配器对象都专门提供了 create() 和 destroy() 方法。简而言之：需要分配元素数组时使用 alloc() 和 free()；需要存储单个独立对象时，则使用 create() 和 destroy()。

在下面的示例中，我们定义了一个表示用户的 User 结构体，通过 allocator.create(User) 在堆上为单个 User 对象分配空间，并在作用域结束时通过 allocator.destroy(user) 将其释放：

const std = @import("std");
const User = struct {
    id: usize,
    name: []const u8,

    pub fn init(id: usize, name: []const u8) User {
        return .{ .id = id, .name = name };
    }
};

pub fn main() !void {
    var gpa = std.heap.DebugAllocator(.{}){};
    const allocator = gpa.allocator();
    const user = try allocator.create(User);
    defer allocator.destroy(user);

    user.* = User.init(0, "Pedro");
}

记住这组搭档关系： - 数组切片批量存：alloc 对应 free； - 单个实体单独存：create 对应 destroy。
