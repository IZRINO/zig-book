15  项目 4：开发一个图像滤镜

在这一章里，我们要做一个新项目。这个项目的目标是写一个程序，对一张图片施加滤镜。更具体地说，是一个”灰度滤镜”，它能把任意一张彩色图片变成灰度图片。

这个项目要用的是 Figure 15.1 中展示的这张图片。换句话说，我们要用自己用 Zig 写的”图像滤镜程序”，把这张彩色图片变成灰度图片。

写这样一个”图像滤镜程序”并不需要很多代码。但我们得先弄懂数字图像是怎么工作的。所以这一章先讲数字图像背后的原理，以及现代计算机是怎么表示颜色的。我们还会简单介绍 PNG（Portable Network Graphics，便携式网络图形）文件格式，示例图片用的就是这种格式。

到本章结束时，我们会得到一个完整的示例程序：它读入 Figure 15.1 这张 PNG 图片，然后在当前工作目录里写出一张新图片，也就是输入图片的灰度版本。Figure 15.1 的灰度版本如 Figure 15.2 所示。这个小项目的完整源码在本书官方仓库1的 ZigExamples/image_filter 文件夹里。

15.1 我们是怎么看见东西的？

这一节我想简单讲讲我们人类是怎么用眼睛看见东西的，也就是眼睛是怎么工作的。只要对眼睛的工作方式有个最基本的了解，就更容易理解数字图像是怎么构成的，因为数字图像背后的技术在很大程度上借鉴了人眼的工作方式。

你可以把人眼理解为一个光传感器，或者说光接收器。眼睛接收一定量的光作为输入，然后解读这些光里包含的颜色。如果没有光进入眼睛，眼睛就无法从中提取颜色，结果我们什么也看不见，更准确地说，我们看到的是一片漆黑。

所以一切都取决于光。我们实际看到的，是射进眼睛的光里反射出来的各种颜色（蓝、红、橙、绿、紫、黄等）。光是所有颜色的来源！ 这正是艾萨克·牛顿在 17 世纪 60 年代著名的棱镜实验2中发现的。

我们的眼睛里有一种特殊的细胞，叫”视锥细胞”。人眼里有三种不同类型（或者说三个不同版本）的视锥细胞。每一种视锥细胞都对光的某一段光谱特别敏感，更具体地说，分别对定义红、绿、蓝三种颜色的光谱敏感。总之，我们的眼睛里有专门的细胞，对这三种颜色（红、绿、蓝）高度敏感。

这些细胞负责感知射进眼睛的光里的颜色。因此，我们的眼睛把颜色感知为这三种颜色（红、绿、蓝）的混合。只要每种颜色取一定的量，再把它们混合起来，就能得到我们想要的任何其他可见颜色。所以我们看到的每一种颜色，都被感知为蓝、绿、红按特定比例的混合，比如 30% 的红，加 20% 的绿，再加 50% 的蓝。

当视锥细胞感知（或者说检测）到射进眼睛的光里的颜色时，它们会产生电信号并传给大脑。大脑解读这些电信号，用它们在脑海里形成我们看到的图像。

根据上面讨论的内容，下面这几条列出了人眼工作方式（一个非常简化的版本）中依次发生的事情：

  1. 光射进我们的眼睛。
  2. 视锥细胞感知这些光里的颜色。
  3. 视锥细胞产生电信号，描述它在光里感知到的颜色。
  4. 电信号被传给大脑。
  5. 大脑解读这些信号，根据这些电信号所标识的颜色形成图像。

15.2 数字图像是怎么工作的？

数字图像是我们用眼睛看到的图像的一种”数字表示”。换句话说，数字图像是我们借助光看到、感知到的那些颜色的”数字表示”。在数字世界里，图像分两类：矢量图像（vector image）和光栅图像（raster image）。这里不讲矢量图像，所以请记住，这里讨论的内容只涉及光栅图像，与矢量图像无关。

光栅图像是一种用二维像素矩阵表示的数字图像。换句话说，每张光栅图像本质上都是一个由像素组成的矩形，每个像素都有一种特定的颜色。所以光栅图像就是一个像素矩形，其中每个像素都以一种颜色显示在你的电脑屏幕上（或者任何其他设备的屏幕上，比如笔记本电脑、平板、智能手机等）。

Figure 15.3 演示了这个想法。随便拿一张光栅图像，把它放得非常大，你就会看到图像里一个个实际的像素。JPEG、TIFF 和 PNG 都是常用来存储光栅图像的文件格式。

图像的像素越多，能容纳的信息和细节就越多，图像看起来也就越精确、越清晰、越好看。这就是为什么相机通常会拍出很大的光栅图像，分辨率达到好几百万像素，好让最终的图像保留尽可能多的细节。举个例子，一张宽 1920 像素、高 1080 像素的数字图像，总共包含 \(1920 \times 1080 = 2073600\) 个像素。你也可以说这张图像的”总面积”是 2073600 个像素，不过在计算机图形学里，其实不怎么用”面积”这个概念。

如今我们看到的数字图像，大多使用 RGB 颜色模型。RGB 代表红（red）、绿（green）、蓝（blue）。所以这些光栅图像里每个像素的颜色，通常表示为红、绿、蓝三种颜色的混合，和我们的眼睛一样。也就是说，每个像素的颜色由一组三个不同的整数值来标识，每个整数值标识一种颜色（红、绿或蓝）的”量”。例如，(199, 78, 70) 这组值标识的颜色更接近红色：红 199、绿 78、蓝 70。相反，(129, 77, 250) 这组值描述的颜色更接近紫色。其他颜色依此类推。

15.2.1 图像从上到下显示

这不是铁律，但绝大多数数字图像都是从上到下、从左到右显示的。大多数电脑屏幕也遵循这个模式。所以图像里的第一批像素，就是位于图像左上角的那些。Figure 15.4 直观地展示了这个逻辑。

从 Figure 15.4 还可以看到，由于光栅图像本质上是一个二维像素矩阵，图像是按像素的行和列来组织的。列由水平的 x 轴确定，行由垂直的 y 轴确定。

Figure 15.4 中的每个像素（也就是那些灰色矩形）里面都有一个数字。这些数字是像素的索引。可以看到，第一批像素在左上角，而且这些像素的索引”往旁边增长”，换句话说，沿着水平 x 轴的方向增长。大多数光栅图像都是按像素行来组织的。因此在显示这些数字图像时，屏幕会先显示第一行像素，然后是第二行，然后是第三行，依此类推。

15.2.2 在代码中表示像素矩阵

好，我们已经知道光栅图像是用二维像素矩阵表示的。但 Zig 里没有二维矩阵这个概念。实际上，大多数低级语言（Zig、C、Rust 等）都没有这种概念。那么，在 Zig 或者其他低级语言里，该怎么表示这样的像素矩阵呢？遇到这种情况，大多数程序员的做法是直接用一个普通的一维数组来存储这个二维矩阵的值。换句话说，就是创建一个普通的一维数组，把两个维度上的所有值都存进这个一维数组。

举个例子，假设我们有一张尺寸为 4x3 的很小的图像。光栅图像用二维像素矩阵表示，而每个像素用 3 个”无符号 8 位”整数值表示，所以这张图像里总共有 12 个像素，由 \(3 \times 12 = 36\) 个整数值表示。因此，我们需要创建一个包含 36 个 u8 值的数组来存储这张小图像。

之所以用无符号 8 位整数（u8）而不是其他整数类型来表示每种颜色的量，是因为它们占用的空间尽可能少，或者说用的位数尽可能少。这有助于减小图像（也就是这个二维矩阵）的二进制大小。而且，尽管它们能表示的”颜色量”范围相对较小（0 到 255），却能提供相当高的颜色精度和细节。

回到最初那个 4x3 图像的例子，下面的 matrix 对象就可以是存储这张 4x3 图像数据的一维数组。

const matrix = [_]u8{
    201, 10, 25, 185, 65, 70,
    65, 120, 110, 65, 120, 117,
    98, 95, 12, 213, 26, 88,
    143, 112, 65, 97, 99, 205,
    234, 105, 56, 43, 44, 216,
    45, 59, 243, 211, 209, 54,
};

这个数组里的前三个整数值，是图像中第一个像素的颜色量。接下来的三个整数是第二个像素的颜色量，后面都按这个规律排下去。所以，存储光栅图像的数组，大小通常是 3 的倍数。在这个例子里，数组的大小是 36。

我说数组的大小通常是 3 的倍数，是因为在某些特定情况下，它也可能是 4 的倍数。当光栅图像里还包含透明度的量时，就会出现这种情况。换句话说，有些类型的光栅图像使用另一种颜色模型，也就是 RGBA（红、绿、蓝和 alpha）颜色模型。“alpha”对应像素的透明度。所以 RGBA 图像里的每个像素，都由红、绿、蓝和 alpha 四个值表示。

大多数光栅图像使用标准的 RGB 模型，所以多数时候，你看到的数组大小都是 3 的倍数。但有些图像，特别是存储在 PNG 文件里的图像，可能使用 RGBA 模型，因此表示它们的数组大小是 4 的倍数。

就我们这里来说，项目的示例图像（Figure 15.1）是一张存储在 PNG 文件里的光栅图像，而这张图像用的正是 RGBA 颜色模型。因此，图像中的每个像素由 4 个不同的整数值表示；这样一来，要在 Zig 代码里存储这张图像，就需要创建一个大小为 4 的倍数的数组。

15.3 我们要用的 PNG 库

我们先从编写读取 PNG 文件数据所需的 Zig 代码开始这个项目。换句话说，我们要读取 Figure 15.1 所示的 PNG 文件，解析它的数据，提取出表示这张图像的二维像素矩阵。

正如 Section 15.2.2 中讨论的，这里用作示例的图像是一个使用 RGBA 颜色模型的 PNG 文件，因此图像的每个像素由 4 个整数值表示。你可以到本书官方仓库3的 ZigExamples/image_filter 文件夹下载这张图像。这个文件夹里还有我们在这里开发的这个小项目的完整源码。

有一些现成的 C 库可以用来读取和解析 PNG 文件。其中最有名、用得最多的是 libpng，它是读写 PNG 文件的”官方库”。虽然大多数操作系统上都有这个库，但它出了名地复杂、难用。

所以，在这个项目里我会用一个更现代的替代品，也就是 libspng 库。我选这个 C 库，是因为它比 libpng 简单得多，而且各种操作的性能都很好。想进一步了解它，可以看看这个库的官网4。你在那里还能找到一些文档，可能有助于理解和跟上这里给出的代码示例。

首先，记得在你的系统里构建并安装这个 libspng。如果不做这一步，zig 编译器就找不到你电脑上这个库的文件和资源，也就没法把它们和我们一起编写的这些 Zig 源码链接起来。这个库文档的构建一节5里，有关于如何构建和安装这个库的详细说明。

15.4 读取 PNG 文件

要从 PNG 文件里提取像素数据，我们需要读取并解码这个文件。PNG 文件只是一个按”PNG 格式”写成的二进制文件。好在 libspng 库提供了一个叫 spng_decode_image() 的函数，能替我们完成所有这些繁重的工作。

不过，libspng 是一个 C 库，所以这个库里的大部分文件和 I/O 操作都是通过 C 的 FILE 指针完成的。因此，用 C 函数 fopen() 打开 PNG 文件，大概比用 Chapter 13 中介绍的 openFile() 方法更合适。这就是为什么我在这个项目里导入了 C 头文件 stdio.h，并用 C 函数 fopen() 来打开文件。

看下面这段代码，可以看到我们做了这几件事：

  1. 用 fopen() 打开 PNG 文件。
  2. 用 spng_ctx_new() 创建 libspng 的上下文。
  3. 用 spng_set_png_file() 指定读取我们要用的那个 PNG 文件的 FILE 对象。

libspng 里的每个操作都要通过一个”上下文对象”来完成。在下面的代码里，这个对象就是 ctx。另外，要对 PNG 文件执行某个操作，就得指明我们指的到底是哪个 PNG 文件。这正是 spng_set_png_file() 的工作。我们用这个函数来指定读取目标 PNG 文件的那个文件描述符对象。

const c = @cImport({
    @cDefine("_NO_CRT_STDIO_INLINE", "1");
    @cInclude("stdio.h");
    @cInclude("spng.h");
});

const path = "pedro_pascal.png";
const file_descriptor = c.fopen(path, "rb");
if (file_descriptor == null) {
    @panic("Could not open file!");
}
const ctx = c.spng_ctx_new(0) orelse unreachable;
_ = c.spng_set_png_file(
    ctx, @ptrCast(file_descriptor)
);

继续之前，有一点要特别强调：既然我们是用 fopen() 打开的文件，就得记得在程序结束时用 fclose() 关闭它。换句话说，在用 PNG 文件 pedro_pascal.png 做完所有想做的事之后，我们需要对文件描述符对象调用 fclose()，把这个文件关掉。如果愿意，也可以借助 defer 关键字来完成这件事。下面这段代码演示了这一步：

if (c.fclose(file_descriptor) != 0) {
    return error.CouldNotCloseFileDescriptor;
}

15.4.1 读取图像头部分

现在，上下文对象 ctx 已经知道我们的 PNG 文件 pedro_pascal.png 了，因为它能访问这个文件的文件描述符对象。我们要做的第一件事，是读取这个 PNG 文件的”图像头部分”。“图像头部分”是文件中包含 PNG 文件基本信息的那一部分，比如图像像素数据的位深、文件所用的颜色模型、图像的尺寸（以像素数表示的高和宽）等。

为了方便，我会把这个”读取图像头”的操作封装成一个简洁的小函数，叫 get_image_header()。这个函数只需要调用 spng_get_ihdr() 函数。libspng 里的这个函数负责读取图像头数据，并把它存进一个名为 spng_ihdr 的 C 结构体。所以，spng_ihdr 类型的对象就是一个包含 PNG 文件图像头部分数据的 C 结构体。

由于这个 Zig 函数接收一个 C 对象（libspng 的上下文对象）作为输入，我按照 Section 14.5 中讨论的建议，把函数参数 ctx 标注为”指向上下文对象的指针”（*c.spng_ctx）。

fn get_image_header(ctx: *c.spng_ctx) !c.spng_ihdr {
    var image_header: c.spng_ihdr = undefined;
    if (c.spng_get_ihdr(ctx, &image_header) != 0) {
        return error.CouldNotGetImageHeader;
    }
    return image_header;
}

var image_header = try get_image_header(ctx);

还要注意，在这个函数里，我检查了 spng_get_ihdr() 函数调用返回的整数值是不是非零。libspng 库里的大多数函数都会返回一个状态码作为结果，状态码”零”表示”成功”。所以任何非零的状态码都表示运行 spng_get_ihdr() 时出了错。这就是为什么在函数返回的状态码不为零时，我会让这个函数返回一个错误值。

15.4.2 为像素数据分配空间

在从 PNG 文件读取像素数据之前，我们需要分配足够的空间来存放这些数据。但要分配这块空间，首先得知道需要分配多大。计算这块空间的大小显然需要用到图像的尺寸，不过还有别的因素也会影响这个数字，比如图像所用的颜色模型、位深等。

总之，这一切都说明，计算所需空间的大小并不是一件简单的事。这就是为什么 libspng 库提供了一个工具函数 spng_decoded_image_size()，替我们算出这个大小。我同样会把围绕这个 C 函数的逻辑封装成一个简洁的小 Zig 函数，叫 calc_output_size()。可以看到，这个函数返回一个整数值作为结果，告诉我们需要分配的空间大小。

fn calc_output_size(ctx: *c.spng_ctx) !u64 {
    var output_size: u64 = 0;
    const status = c.spng_decoded_image_size(
        ctx, c.SPNG_FMT_RGBA8, &output_size
    );
    if (status != 0) {
        return error.CouldNotCalcOutputSize;
    }
    return output_size;
}

你可能会想，SPNG_FMT_RGBA8 这个值是什么意思。这个值其实是 C 头文件 spng.h 里定义的一个枚举值，这个枚举用来标识一种”PNG 格式”。更确切地说，它标识的是使用 RGBA 颜色模型、位深为 8 位的 PNG 文件。所以，把这个枚举值作为输入传给 spng_decoded_image_size() 函数，就是在告诉这个函数：按照遵循”RGBA 颜色模型、8 位位深”这种格式的 PNG 文件，来计算解码后像素数据的大小。

有了这个函数，就可以配合一个分配器对象，分配一个足够大的字节（u8 值）数组，用来存放图像解码后的像素数据。注意，我用 @memset() 把整个数组初始化为零。

const output_size = try calc_output_size(ctx);
var buffer = try allocator.alloc(u8, output_size);
@memset(buffer[0..], 0);

15.4.3 解码图像数据

现在我们有了存放图像解码后像素数据所需的空间，可以开始用 C 函数 spng_decode_image() 真正地解码图像、从中提取像素数据了。

下面的 Zig 函数 read_data_to_buffer() 概括了读取这些解码后的像素数据、并把它们存进输入缓冲区所需的步骤。注意，这个函数封装了围绕 spng_decode_image() 函数的逻辑。另外，我们再次用 SPNG_FMT_RGBA8 这个枚举值告诉相应的函数：正在解码的 PNG 图像使用 RGBA 颜色模型和 8 位位深。

fn read_data_to_buffer(ctx: *c.spng_ctx, buffer: []u8) !void {
    const status = c.spng_decode_image(
        ctx,
        buffer.ptr,
        buffer.len,
        c.SPNG_FMT_RGBA8,
        0
    );

    if (status != 0) {
        return error.CouldNotDecodeImage;
    }
}

有了这个函数，就可以把它用在我们的上下文对象上，以及上一节为存放图像解码后像素数据而分配的那个缓冲区对象上：

try read_data_to_buffer(ctx, buffer[0..]);

15.4.4 查看像素数据

现在像素数据已经存进我们的”缓冲区对象”里了，可以快速看一下这些字节。在下面的例子里，我们查看的是解码后像素数据的前 12 个字节。

仔细看这些值，你可能会发现，这个序列里每隔 4 个字节就有一个 255。巧的是，这正是 u8 值能表示的最大整数值。所以，如果把 0 到 255 这个范围（也就是 u8 值能表示的整数范围）看作一个从 0% 到 100% 的刻度，这些 255 在这个刻度上就相当于 100%。

回想一下 Section 15.2.2，我在那一节里说过，我们的 PNG 文件 pedro_pascal.png 使用 RGBA 颜色模型，这种模型会给图像里的每个像素加上一个 alpha（也就是透明度）字节。因此，图像里的每个像素由 4 个字节表示。这里我们查看的是图像的前 12 个字节，也就是说，看到的是图像中前 \(12 / 4 = 3\) 个像素的数据。

所以，根据这前 12 个字节（也就是这 3 个像素）的样子，每隔 4 个字节就是一个 255，可以说图像里每个像素的 alpha（也就是透明度）很可能都设成了 100%。这不一定对，但是可能性最大的情况。而且，如果看看图像本身（回想一下，它就是 Figure 15.1），可以看到整张图像的透明度没有变化，这也印证了这个推测。

try stdout.print("{any}\n", .{buffer[0..12]});
try stdout.flush();
{
    200, 194, 216, 255, 203, 197,
    219, 255, 206, 200, 223, 255
}

从上面的结果可以看到，这张图像的第一个像素是红 200、绿 194、蓝 216。我怎么知道这些颜色在序列里出现的顺序？如果你还没猜到，答案就在缩写 RGB 里：先是红（RED），然后是绿（GREEN），最后是蓝（BLUE）。如果按照我们那个 0% 到 100%（0 到 255）的刻度换算这些整数值，就得到 78% 的红、76% 的绿和 85% 的蓝。

15.5 应用图像滤镜

现在我们有了图像里每个像素的数据，可以专心把图像滤镜应用到这些像素上了。别忘了，我们的目标是给这张图像加上灰度滤镜。灰度滤镜就是把彩色图像变成灰度图像的滤镜。

把彩色图像变成灰度图像，有各种不同的公式和策略。但这些策略通常都要对每个像素的颜色做一些数学运算。在这个项目里，我们要用最通用的那个公式，如下所示。这个公式里，\(r\) 表示像素的红色，\(g\) 表示绿色，\(b\) 表示蓝色，\(p'\) 表示像素的线性亮度（linear luminance）。

\[ p' = (0.2126 \times r) + (0.7152 \times g) + (0.0722 \times b) \tag{15.1}\]

Equation 15.1 是计算像素线性亮度的公式。值得注意的是，这个公式只适用于像素使用 sRGB 色彩空间的图像，sRGB 是网络上的标准色彩空间。所以，理想情况下，网络上的所有图像都应该使用这个色彩空间。幸运的是，我们这里正是这种情况：pedro_pascal.png 这张图像用的就是 sRGB 色彩空间，因此我们可以使用 Equation 15.1。关于这个公式，可以在维基百科的灰度（grayscale）词条里进一步了解 (Wikipedia 2024)。

（译注：按维基百科灰度词条的说法，这组权重严格来说要作用在线性 RGB 值上：先对 sRGB 编码的分量做伽马展开（gamma expansion）得到线性值，按 Equation 15.1 算出线性亮度后，再把结果压缩回 sRGB。下面的代码直接把权重用在 sRGB 编码的像素值上，得到的是一种常见的近似结果，并不是严格意义上的线性亮度。）

下面的 apply_image_filter() 函数概括了把 Equation 15.1 应用到图像像素上所需的步骤。我们只需把这个函数用在包含像素数据的缓冲区对象上，这样一来，这个缓冲区对象里存储的像素数据，就应该表示我们这张图像的灰度版本了。

fn apply_image_filter(buffer: []u8) !void {
    const len = buffer.len;
    const red_factor: f16 = 0.2126;
    const green_factor: f16 = 0.7152;
    const blue_factor: f16 = 0.0722;
    var index: u64 = 0;
    while (index < len) : (index += 4) {
        const rf: f16 = @floatFromInt(buffer[index]);
        const gf: f16 = @floatFromInt(buffer[index + 1]);
        const bf: f16 = @floatFromInt(buffer[index + 2]);
        const y_linear: f16 = (
            (rf * red_factor) + (gf * green_factor)
            + (bf * blue_factor)
        );
        buffer[index] = @intFromFloat(y_linear);
        buffer[index + 1] = @intFromFloat(y_linear);
        buffer[index + 2] = @intFromFloat(y_linear);
    }
}

try apply_image_filter(buffer[0..]);

15.6 保存图像的灰度版本

现在缓冲区对象里存的已经是图像的灰度版本了，我们需要把这个缓冲区对象重新编码成”PNG 格式”，再把编码后的数据存进文件系统里的一个新 PNG 文件，这样才能打开并看到这个小程序生成的灰度图像。

要做到这一点，libspng 库再次帮了我们：它提供了一个”把数据编码成 PNG”的函数，也就是 spng_encode_image()。不过，要用 libspng “把数据编码成 PNG”，我们需要创建一个新的上下文对象。这个新的上下文对象必须使用”编码器上下文”，由枚举值 SPNG_CTX_ENCODER 标识。

下面的 save_png() 函数概括了把图像的灰度版本保存到文件系统中一个新 PNG 文件所需的全部步骤。默认情况下，这个函数会把灰度图像保存到当前工作目录（CWD）下一个名为 pedro_pascal_filter.png 的文件里。

注意，在这个代码示例里，我们用的是之前通过 get_image_header() 函数取得的同一个图像头对象（image_header）。别忘了，这个图像头对象是一个 C 结构体（spng_ihdr），包含我们这个 PNG 文件的基本信息，比如图像的尺寸、所用的颜色模型等。

如果我们想在这个新 PNG 文件里保存一张完全不同的图像，比如尺寸不同的图像，或者颜色模型、位深等不同的图像，就得新建一个图像头（spng_ihdr）对象，用它来描述这张新图像的属性。

但我们这里保存的本质上还是最初那张图像（图像的尺寸、颜色模型等都没变）。两张图像唯一的区别是像素的颜色，现在它们都是”深浅不一的灰色”。因此，我们可以放心地在这个新 PNG 文件里使用完全相同的图像头数据。

fn save_png(image_header: *c.spng_ihdr, buffer: []u8) !void {
    const path = "pedro_pascal_filter.png";
    const file_descriptor = c.fopen(path.ptr, "wb");
    if (file_descriptor == null) {
        return error.CouldNotOpenFile;
    }
    const ctx = (
        c.spng_ctx_new(c.SPNG_CTX_ENCODER)
        orelse unreachable
    );
    defer c.spng_ctx_free(ctx);
    _ = c.spng_set_png_file(ctx, @ptrCast(file_descriptor));
    _ = c.spng_set_ihdr(ctx, image_header);

    const encode_status = c.spng_encode_image(
        ctx,
        buffer.ptr,
        buffer.len,
        c.SPNG_FMT_PNG,
        c.SPNG_ENCODE_FINALIZE
    );
    if (encode_status != 0) {
        return error.CouldNotEncodeImage;
    }
    if (c.fclose(file_descriptor) != 0) {
        return error.CouldNotCloseFileDescriptor;
    }
}

try save_png(&image_header, buffer[0..]);

执行完这个 save_png() 函数后，当前工作目录里应该会多出一个名为 pedro_pascal_filter.png 的新 PNG 文件。打开这个 PNG 文件，就会看到 Figure 15.2 所示的那张图像。

15.7 构建项目

代码已经写好了，下面来讨论怎样构建（编译）这个项目。为此，我会在项目的根目录下创建一个 build.zig 文件，然后运用 Chapter 9 中学到的知识，开始编写编译这个项目所需的代码。

我们先为可执行文件创建构建目标，这个可执行文件负责运行我们的 Zig 代码。假设所有 Zig 代码都写在一个名为 image_filter.zig 的 Zig 模块里。下面构建脚本中的 exe 对象，描述的就是这个可执行文件的构建目标。

由于我们在 Zig 代码里用到了 libspng 库中的一些 C 代码，所以需要把我们的 Zig 代码（也就是 exe 构建目标里的代码）同时链接到 C 标准库和 libspng 库。我们通过调用 exe 构建目标的 linkLibC() 和 linkSystemLibrary() 方法来做到这一点。（译注：在本书使用的 Zig 0.17 里，构建目标上已经没有 linkLibC() 方法了。下面的脚本是在 b.createModule() 里设置 .link_libc = true 来链接 C 标准库的；linkSystemLibrary() 则是在 exe.root_module 上调用的。）

const std = @import("std");
pub fn build(b: *std.Build) void {
    const exe = b.addExecutable(.{
        .name = "image_filter",
        .root_module = b.createModule(.{
            .root_source_file = b.path("src/image_filter.zig"),
            .target = b.graph.host,
            .link_libc = true
        })
    });
    // 链接 libspng 库：
    exe.root_module.linkSystemLibrary("spng", .{});
    // 链接数学库：
    exe.root_module.linkSystemLibrary("m", .{});
    b.installArtifact(exe);
}

由于我们用的是 linkSystemLibrary() 方法，这意味着会在你的系统里搜索 libspng 的库文件，再把它们和 exe 构建目标链接起来。如果你还没在系统里构建并安装 libspng 库，这个链接步骤多半会失败，因为它在你的系统里找不到这个库的文件。

所以，要构建这个项目，记得先在系统里安装 libspng。写好上面这个构建脚本后，我们终于可以在终端里运行 zig build 命令来构建项目了。

zig build
