9  构建系统（Build System）

在本章中，我们将探讨 Zig 的构建系统（Build System），以及如何在 Zig 中构建完整的工程项目。 Zig 的一大核心优势在于它将构建系统直接内嵌到了语言自身之中。这意味着你无需依赖独立于编译器的外部第三方工具，仅用纯正的 Zig 语言就能编写构建脚本（build.zig）并构建项目。

想深入了解构建系统的读者，还可以翻阅 Zig 官网的《构建系统专题指南》1以及社区开发者 Felix 撰写的系列文章2。

构建代码是 Zig 最擅长的事情之一。在 C/C++ 甚至 Rust 里，把源码交叉编译（Cross-compilation）到多个目标（比如多种计算机架构和操作系统）是一件特别困难的事，而 zig 编译器被公认为完成这项任务最好的现有软件之一。

9.1 源码是如何被构建出来的？

我们在 Section 1.2.1 中已经讨论过底层语言在构建源码时面临的挑战。在底层编译型语言中，构建本质上就是让编译器将我们写的源码翻译为 CPU 机器指令。 在 Zig 中，一个典型的编译构建流程包含这几个核心输入：

  • 包含源码的 Zig 模块（Modules）；
  • 外部依赖库文件（动态库 .so/.dll 或静态库 .a/.lib）；
  • 决定优化等级与平台目标的编译选项/参数。

所有的构建调度规则，统一编写在项目根目录下的 build.zig 脚本里。

这个构建脚本的核心是围绕构建目标对象（Target Objects）展开的。所谓 Target（目标），就是你希望 zig 编译器最终为你构建出来的产物——这一概念在大多数主流构建系统（尤其是 CMake3）中都普遍存在。

在 Zig 中，你可以构建以下四种类型的目标对象（我们将在 Section 9.3 中详细展开）：

  1. 独立可执行程序（Executable）（Windows 上的 .exe，Linux 上的 ELF 二进制）；
  2. 动态共享库（Shared Library）（Linux 上的 .so，Windows 上的 .dll）；
  3. 静态库（Static Library）（Linux 上的 .a，Windows 上的 .lib）；
  4. 单测可执行文件（Test Executable）。

9.2 认识唯一的构建主入口：build() 函数

Zig 中的构建脚本必须包含一个顶层的公开 build() 函数声明。它就像我们在 Section 1.2.3 中讨论的应用程序主入口 main() 函数一样，是整个构建流程的入口点。

该 build() 函数接收一个指向 std.Build 结构体的指针 b: *std.Build 作为输入，返回值类型固定为 void。我们通过调用 b 上的各种方法来完成构建步骤的编排。

看一个最基础的最小构建脚本：

const std = @import("std");
pub fn build(b: *std.Build) void {
    const exe = b.addExecutable(.{
        .name = "hello",
        .root_module = b.createModule(.{
            .root_source_file = b.path("hello.zig"),
            .target = b.graph.host
        })
    });
    b.installArtifact(exe);
}

9.3 核心构建目标对象（Target Objects）

正如前文所述，构建脚本是围绕目标对象（Target Objects）组织的。你可以在一个构建脚本中定义多个目标对象，甚至针对不同的操作系统（Windows、Linux 等）分别定义目标对象，从而让 zig 编译器一次性交叉编译出多平台二进制产物（Zig 官方构建系统文档提供了演示这一跨平台构建策略的优秀代码示例4）。

通过我们在 Section 9.2 中介绍的 std.Build 指针 b，可以调用以下方法创建目标对象：

  • b.addExecutable(...)：声明生成一个可执行文件；
  • b.addSharedLibrary(...)：声明生成一个动态链接库；
  • b.addStaticLibrary(...)：声明生成一个静态链接库；
  • b.addTest(...)：声明生成单测运行二进制。

在参数配置中，有两个最关键的必填项： - name：生成产物的名称（通常设为你的工程名）； - root_module：定义模块配置。其中 root_source_file 指定该模块的入口文件（比如 b.path("src/main.zig")）。

const exe = b.addExecutable(.{
    .name = "hello",
    .root_module = b.createModule(.{
        .root_source_file = b.path("hello.zig"),
        .target = b.graph.host
    })
});

9.3.1 自动发现项目中的 Zig 模块

root_source_file 指定的是项目的根 Zig 模块，也就是包含程序入口（main() 函数）或者库的主要 API 的那个模块。这也意味着，组成项目的所有 Zig 模块，都会通过这个“根源文件”里的 import 语句被自动发现。zig 编译器能通过 import 语句看出哪个 Zig 模块依赖哪个，从而找出项目用到的全部 Zig 模块。

这很方便，也和其他构建系统的做法不同。比如在 CMake 里，你必须显式列出所有要参与构建的源文件的路径。这大概是 C 和 C++ 编译器“缺少条件编译”的一种表现：因为缺少这个功能，你必须明确选出哪些源文件要交给 C/C++ 编译器，毕竟不是每段 C/C++ 代码都能移植、都能在每个操作系统上编译，否则 C/C++ 编译器就会报编译错误。

（译注：这里的自动发现只针对 Zig 模块。C/C++ 源文件仍然要像 Section 9.11 中那样，用 addCSourceFiles() 显式列出。）

9.3.2 安装构建产物：b.installArtifact()

关于构建过程有一个非常重要的细节：你必须使用 Build 结构体的 installArtifact() 方法，显式安装你在构建脚本中创建的目标对象。

每次调用 zig build 时，项目根目录下都会创建一个 zig-out 目录用于存放构建输出。 构建系统在编译完成后，默认会把中间产物放在临时缓存区；只有被 installArtifact 标记的最终产物，才会被拷贝并安装到根目录的 zig-out/ 输出目录中！

const exe = b.addExecutable(.{
    .name = "hello",
    .root_module = b.createModule(.{
        .root_source_file = b.path("hello.zig"),
        .target = b.graph.host
    })
});

b.installArtifact(exe); // 必须有这句！

9.4 设置构建模式

前面介绍了创建目标对象时要设置的三个基本选项。此外还有第四个选项 optimize，用来设置目标对象的构建模式。这个选项之所以叫 optimize（优化），是因为 Zig 把构建模式更多地看作“优化与安全如何取舍”的问题，所以优化在这里很重要。

Zig 有下面四种构建模式，各有各的特点。正如我们在 Section 5.2.1 中所述，如果不显式选择构建模式，zig 编译器默认使用 Debug 模式。

  • Debug：在构建产物（也就是目标对象定义的二进制文件）中生成并包含调试信息；
  • ReleaseSmall：尽量生成体积小的二进制文件；
  • ReleaseFast：尽量优化代码，让生成的二进制文件跑得尽可能快；
  • ReleaseSafe：尽可能加入安全保护，让代码尽量安全。

所以在构建项目时，你可以把目标对象的构建模式设为 ReleaseFast，让 zig 编译器对代码做重要的优化。这样生成的二进制文件包含优化程度更高的代码，在大多数情况下跑得更快。但代价通常是失去一些安全特性：最终的二进制文件里去掉了部分安全检查，代码跑得更快，但没那么安全了。

（译注：按 Zig 0.17.1 zig build-exe --help 中的说明，ReleaseFast 和 ReleaseSmall 会关闭全部运行时安全检查，不只是去掉一部分；ReleaseSafe 则同时开启安全检查和机器码优化。Debug 模式同样开启安全检查，而且编译最快。）

怎么选取决于你当前优先考虑什么。如果你在开发密码学或银行系统，可能更看重安全，会选择 ReleaseSafe 模式：它运行起来稍慢一些，但安全得多，因为构建出的二进制文件里包含了所有可能的运行时安全检查。反过来，如果你在写游戏，可能更看重性能而不是安全，会选择 ReleaseFast 模式，让玩家得到更高的帧率。

在下面的例子中，我们创建的还是前面用过的那个目标对象，但这次把它的构建模式设为 ReleaseSafe：

const exe = b.addExecutable(.{
    .name = "hello",
    .root_module = b.createModule(.{
        .root_source_file = b.path("hello.zig"),
        .target = b.graph.host,
        .optimize = .ReleaseSafe
    })
});
b.installArtifact(exe);

9.5 声明构建版本号（语义化版本）

每次在构建脚本中定义目标对象时，你都可以遵循语义化版本规范（Semantic Versioning，详见 语义化版本官网5）通过 version 选项为其指定一个 SemanticVersion 版本号结构体：

const exe = b.addExecutable(.{
    .name = "hello",
    .root_module = b.createModule(.{
        .root_source_file = b.path("hello.zig"),
        .target = b.graph.host
    }),
    .version = .{
        .major = 2, .minor = 9, .patch = 7
    }
});
b.installArtifact(exe);

9.6 在构建脚本中探测操作系统

根据不同操作系统走不同构建逻辑是日常刚需。在构建脚本里引入 @import("builtin")，就能随时探测当前的目标平台：

const builtin = @import("builtin");
if (builtin.target.os.tag == .windows) {
    // 只在目标是 Windows 时执行的特定构建逻辑
}

9.7 为构建系统添加“一键运行”步骤（Run Step）

在 Rust 中，开发者可以通过 cargo run 一条命令同时完成编译与运行；我们在 Section 1.2.6 中也介绍过如何使用 zig run 命令直接编译并运行单个 Zig 源码文件。那么在 build.zig 构建脚本中，如何同时构建并运行目标对象所生成的可执行文件呢？

答案是在构建脚本中引入一个“运行工件（Run Artifact）”并为其绑定构建步骤（Step）：

  1. 首先，调用 b.addRunArtifact(exe) 为目标可执行对象创建一个运行工件：
const exe = b.addExecutable(.{
    .name = "hello",
    .root_module = b.createModule(.{
        .root_source_file = b.path("src/hello.zig"),
        .target = b.graph.host
    })
});
b.installArtifact(exe);
const run_arti = b.addRunArtifact(exe);
  1. 接着，调用 b.step() 在构建脚本中声明一个名为 "run" 的构建步骤（Step）：
const run_step = b.step(
    "run", "Run the project"
);
  1. 最后，调用 run_step.dependOn() 建立该构建步骤与运行工件之间的依赖关系（完整源码参见本书官方仓库中的 build_and_run.zig 模块6）：
run_step.dependOn(&run_arti.step);

敲下 zig build --help，你就能看到刚才注册的自定义指令：

zig build --help
Steps:
  ...
  run   Run the project
  ...

随后在终端敲一行：

zig build run

编译、链接、自动拉起运行一气呵成！

9.8 集成单测构建步骤：zig build tests

我们在 Chapter 8 中详细讨论过如何编写单元测试并用 zig test 运行它们。同样地，我们可以在构建脚本中使用 Section 9.3 介绍过的 b.addTest() 方法创建一个“单元测试目标对象”，它会收集项目中所有的 test 代码块并将其编译为专门的测试可执行文件：

const test_exe = b.addTest(.{
    .name = "unit_tests",
    .root_module = b.createModule(.{
        .root_source_file = b.path("src/main.zig"),
        .target = b.graph.host
    })
});

b.installArtifact(test_exe);

接着，结合上一节学到的 Run Step 机制，我们可以注册一个名为 "tests" 的构建步骤来一键运行这些单元测试（完整脚本见官方仓库的 build_tests.zig 模块7）：

const run_arti = b.addRunArtifact(test_exe);
const run_step = b.step("tests", "Run unit tests");
run_step.dependOn(&run_arti.step);

现在只需在终端运行以下命令即可一键编译并执行项目单元测试：

zig build tests

9.9 接收命令行自定义参数（User-provided Options）

很多时候我们希望构建过程可以通过命令行参数动态定制（例如是否启用某套特性）： 使用 b.option(Type, name, description) 即可！

定义好的选项会自动成为 zig build 的 -D<name> 命令行参数：

const std = @import("std");
pub fn build(b: *std.Build) void {
    const use_zlib = b.option(
        bool,
        "use_zlib",
        "Should link to zlib?"
    ) orelse false;
    const exe = b.addExecutable(.{
        .name = "hello",
        .root_module = b.createModule(.{
            .root_source_file = b.path("example.zig"),
            .target = b.graph.host
        })
    });
    if (use_zlib) {
        exe.root_module.linkSystemLibrary("zlib", .{});
    }
    b.installArtifact(exe);
}

命令行调用方式：

zig build -Duse_zlib=false

9.10 链接外部库

链接阶段是每个构建过程中都不可或缺的一部分。这个阶段负责把代表你代码的多个目标文件合并成一个可执行文件。如果你的代码用到了外部库，链接阶段还会把这个可执行文件与这些外部库链接起来。

在 Zig 中，“库”有两种概念：1）系统库；2）本地库。系统库就是已经安装在你系统中的库；本地库则属于当前项目，它位于项目目录中，并且和项目源码一起构建。

两者的基本区别在于，系统库（按理说）已经构建好并安装在你的系统中，你只需要把源码与这个库链接起来就能开始使用它。我们通过 Compile.root_module 对象的 linkSystemLibrary() 方法来做到这一点。这个方法接收一个字符串形式的库名作为输入。还记得 Section 9.3 中讲过，Compile 对象就是你在构建脚本中声明的目标对象。

当你把某个目标对象与系统库链接时，zig 编译器会使用 pkg-config 在你的系统中查找这个库的二进制文件和头文件。找到这些文件后，zig 编译器中的链接器会把你的目标文件与这个库的文件链接起来，为你生成一个单独的二进制文件。

在下面的例子中，我们创建了一个名为 image_filter 的可执行文件，并通过把 link_libc 选项设为 true，将它与 C 标准库链接。同时，我们还把这个可执行文件与我系统中当前已安装的 C 库 libpng 链接起来。

const std = @import("std");
pub fn build(b: *std.Build) void {
    const exe = b.addExecutable(.{
        .name = "image_filter",
        .root_module = b.createModule(.{
            .root_source_file = b.path("src/main.zig"),
            .target = b.graph.host,
            .link_libc = true,
        })
    });
    exe.root_module.linkSystemLibrary("png", .{});
    b.installArtifact(exe);
}

（译注：英文原文中 .target = b.graph.host 之后缺少逗号，无法通过编译，译文已补上。）

如果你的项目要链接某个 C 库，通常最好也把代码与 C 标准库链接起来，因为这个 C 库很可能在某处用到了 C 标准库的功能。C++ 库也是同理：如果要链接 C++ 库，最好把 link_libcpp 选项设为 true，将项目与 C++ 标准库链接。

另一方面，当你想链接一个本地库时，应该使用 Compile.root_module 对象的 linkLibrary() 方法。这个方法需要接收另一个 Compile 对象作为输入，也就是你在构建脚本中用 addStaticLibrary() 或 addSharedLibrary() 方法定义的另一个目标对象，它定义了一个要构建的库。

正如前面所讨论的，本地库是属于你项目本身、并与项目一起构建的库。因此，你需要在构建脚本中创建一个目标对象来构建这个本地库，然后把项目中相关的目标对象与标识这个本地库的目标对象链接起来。

看看下面这个摘自 libxev 库8构建脚本的例子。可以看到，这段代码先用 c_api.zig 模块声明了一个共享库文件；然后在构建脚本的后面，又声明了一个名为 "dynamic-binding-test" 的可执行文件，它链接到前面定义的这个共享库。

const dynamic_lib = b.addSharedLibrary(.{
    .name = dynamic_lib_name,
    .root_module = b.createModule(.{
        .root_source_file = b.path("src/c_api.zig"),
        .target = b.graph.host
    })
});
b.installArtifact(dynamic_lib);
// ... more lines in the script
const dynamic_binding_test = b.addExecutable(.{
    .name = "dynamic-binding-test",
    .root_module = b.createModule(.{
        .root_source_file = b.path("src/test.zig"),
        .target = b.graph.host
    })
});
dynamic_binding_test.root_module.linkLibrary(
    dynamic_lib
);

（译注：在 Zig 0.17.1 中，std.Build 已经没有 addSharedLibrary() 和 addStaticLibrary() 方法，统一改为 addLibrary()，并通过 .linkage 字段指定静态或动态链接。本章沿用原文的写法。）

9.11 编译 C 语言代码

zig 编译器内嵌了一个 C 编译器。换句话说，你可以用 zig 编译器来构建 C 项目。这个 C 编译器可以通过 zig 编译器的 cc 命令使用。

举个例子，我们以著名的 FreeType 库9为例。FreeType 是世界上使用最广泛的软件之一。它是一个用于生成高质量字体的 C 库，同时也在业界被大量用于在计算机屏幕上原生渲染文本和字体。

在本节中，我们将一步一步地编写一个能够从源码构建 FreeType 项目的构建脚本。你可以在 GitHub 上的 freetype-zig 仓库10中找到这个构建脚本的源码。

从官网下载 FreeType 的源码11之后，就可以开始编写 build.zig 模块了。我们首先定义目标对象，它描述了我们要编译的二进制文件。

作为示例，我会使用 addStaticLibrary() 方法创建目标对象，把项目构建为一个静态库文件。另外，由于 FreeType 是一个 C 库，我还会通过 link_libc 选项把这个库与 libc 链接，以确保编译过程中对 C 标准库的任何使用都能得到满足。

const lib = b.addStaticLibrary(.{
    .name = "freetype",
    .root_module = b.createModule(.{
        .target = b.graph.host,
        .link_libc = true
    })
});

9.11.1 配置 C 编译器标志（Compiler Flags）

编译器标志在业内也被很多开发者称作“编译器选项（Compiler options）”，或者 GCC 官方文档中的“命令选项（Command options）”。本质上，它们就是传递给 C 编译器的命令行开关参数。通常我们利用编译器标志来开启或关闭特定语言特性、设定告警级别，或者针对具体项目调整编译行为。

在用 Zig 编写的构建脚本中，我们通常将传递给 C 编译器的选项统一定义在一个简单的字符串切片数组中：

const c_flags = [_][]const u8{
    "-Wall",
    "-Wextra",
    "-Werror",
};

从技术上讲，你当然也可以在这个数组里通过 -I 传递头文件包含路径、通过 -L 传递库搜索路径。但 Zig 提供了更加严谨规范的原生 API 来专门处理这类路径（分别在后文 Section 9.11.5 与 Section 9.11.4 中剖析）。

在 Zig 中，我们通常借助 addCSourceFile() 或 addCSourceFiles() 方法，将编译标志与待编译的 C 源文件一并打包加入构建流程中。在上面的代码中，我们只是先声明了希望使用的编译标志数组。

9.11.2 列出待编译的 C 源文件列表

在跨平台 C 项目中，通常有一部分 C 源码是与具体操作系统平台无关的“全平台通用代码”。在 FreeType 中，这部分被所有支持平台默认引入的通用 C 文件被归拢在 c_source_files 数组中。由于 FreeType 的源文件数量极其庞大，为了节省篇幅，下面的代码仅列出其中几个代表性文件：

const c_source_files = [_][]const u8{
    "src/autofit/autofit.c",
    "src/base/ftbase.c",
    // ... 以及其他众多通用 C 源文件
};

除了通用代码，FreeType 内部还包含部分平台专用的 C 文件——这些源码只能在特定操作系统下成功编译。针对 Windows 和 Linux，我们分别列出它们对应的专属源文件：

const windows_c_source_files = [_][]const u8{
    "builds/windows/ftdebug.c",
    "builds/windows/ftsystem.c"
};
const linux_c_source_files = [_][]const u8{
    "src/base/ftsystem.c",
    "src/base/ftdebug.c"
};

声明好源文件列表与编译器标志后，我们便可以调用 addCSourceFiles() 方法将它们挂载到代表 FreeType 库的目标对象上。 addCSourceFiles() 支持一次性批量注册多个 C 文件；若需针对某一个特殊文件单独定制编译参数，也可以使用单文件版本的 addCSourceFile()。

注意在下面的代码中，我们巧妙结合了在 Section 9.6 中学到的 target.os.tag 平台探测技巧，根据编译目标操作系统有针对性地注入平台专用 C 文件：

const builtin = @import("builtin");
lib.root_module.addCSourceFiles(.{
    .files = &c_source_files,
    .flags = &c_flags
});

switch (builtin.target.os.tag) {
    .windows => {
        lib.root_module.addCSourceFiles(.{
            .files = &windows_c_source_files,
            .flags = &c_flags
        });
    },
    .linux => {
        lib.root_module.addCSourceFiles(.{
            .files = &linux_c_source_files,
            .flags = &c_flags
        });
    },
    else => {},
}

（译注：英文原文里写的是 addCSourceFiles({ ... })，少了结构体字面量前面的 .，无法通过编译，译文已改为 addCSourceFiles(.{ ... })。）

9.11.3 定义 C 语言预处理宏（C Macros）

C 语言宏定义是 C 工程构建中不可或缺的组成部分，传统上通常通过 C 编译器的 -D 参数传递。 在 Zig 中，我们可以直接调用目标对象根模块的 addCMacro() 方法来便捷定义 C 宏。

在下面的示例中，我们用前几节定义的 lib 对象，为 FreeType 的编译过程定义了一些 C 宏。这些宏用来指定 FreeType 是否要引入各个外部库的功能：

lib.root_module.addCMacro("FT_DISABLE_ZLIB", "TRUE");
lib.root_module.addCMacro("FT_DISABLE_PNG", "TRUE");
lib.root_module.addCMacro("FT_DISABLE_HARFBUZZ", "TRUE");
lib.root_module.addCMacro("FT_DISABLE_BZIP2", "TRUE");
lib.root_module.addCMacro("FT_DISABLE_BROTLI", "TRUE");
lib.root_module.addCMacro("FT2_BUILD_LIBRARY", "TRUE");

9.11.4 添加库文件搜索路径（Library Paths）

所谓库搜索路径（Library Paths），是指操作系统中 C 编译器寻找待链接二进制库文件（.so/.a/.lib）所在的目录集合。 默认情况下，编译器会预置扫描一些系统标准路径（如 /usr/lib 或 Windows SDK 目录）；但如果你的依赖库安装在一个非标准或自定义路径下，就必须显式将该目录加入搜索范围。

在 Zig 中，我们可以通过 root_module.addLibraryPath() 方法将自定义路径加入扫描清单。该方法接收一个 std.Build.LazyPath 对象作为参数：

const lib_path: std.Build.LazyPath = .{
    .cwd_relative = "/usr/local/lib/"
};
lib.root_module.addLibraryPath(lib_path);

9.11.5 添加头文件包含路径（Include Paths）

与库路径类似，预处理器头文件搜索路径（通常简称为“Include 路径”）指代 C 编译器在处理源码中的 #include <...> 语句时所扫描的目录范围。在传统 C 编译中，通常通过 -I 参数配置。

在 Zig 中，可以调用目标对象 root_module 的 addIncludePath() 方法，往这组路径里添加新的路径。这个方法同样接收一个 LazyPath 对象：

const inc_path: std.Build.LazyPath = .{
    .path = "./include"
};
lib.root_module.addIncludePath(inc_path);
