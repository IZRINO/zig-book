14  Zig 与 C 语言的无缝互操作（C Interoperability）

在系统级编程世界里，C 语言依然是绝对的通用“世界语”。几乎所有成熟的底层操作系统 API、音视频编解码器、图形驱动和密码学库，都是以 C 语言形式存在的。 在前面的 Section 9.11 中，我们已经了解了如何直接使用 zig 编译器内置的 Clang 引擎去构建编译 C 代码。 而在本章中，我们将聚焦于最核心的互操作命题：如何在 Zig 源码中直接调用并无缝使用 C 语言代码与库。

这是本章的核心主题。在接下来的下一个实战项目（图像滤镜系统）中，我们也将亲自动手引入并调用一个真实的 C 语言图像编解码库，本章的所有知识都将在那里化为趁手的实战武器。

14.1 如何在 Zig 中调用 C 代码

跨语言调用 C 代码（FFI, Foreign Function Interface）其实并不新鲜。几乎所有主流高级语言都有自己的 FFI 方案：例如 Python 有 Cython，R 有 .Call()，JavaScript 有 ccall()（译注：ccall() 是 Emscripten 提供的函数）等。 但 Zig 与 C 的集成更加深入，它不仅影响 C 代码的调用方式，还影响这些 C 代码如何被编译并纳入你的 Zig 项目。

简而言之，Zig 与 C 的互操作性很好。在 Zig 中调用任何 C 代码，通常只需遵循以下两个基准步骤：

  1. 将 C 语言头文件引入（Import）到 Zig 代码中；
  2. 在构建编译时，将 Zig 代码与对应的 C 库进行链接（Linking）。

14.1.1 引入 C 头文件的两种核心策略

无论调用何种 C 代码，上述两个步骤都是必经之路。而具体落实到第一步“如何引入 C 头文件”时，Zig 目前提供了两条殊途同归的实现路径：

  • 策略一：利用 zig translate-c 工具将 C 头文件直接转译为 Zig 模块，然后在 Zig 中像导入常规模块一样 @import 并使用它；
  • 策略二：在 Zig 源码中直接借助内置函数 @cImport() 现场引入 C 头文件。

如果你对 translate-c 还不熟悉，它是 zig 编译器中的一个子命令，接收 C 文件作为输入，输出这些 C 文件中 C 代码的 Zig 表示。 换句话说，这个子命令的作用类似于转译器（transpiler）：它接收 C 代码，并把它翻译为等价的 Zig 代码。

有人可能会把它类比为 Rust 社区的 rust-bindgen 工具1。虽然两者都是为了抹平 C 绑定，但 translate-c 的设计野心远不止是生成黏合层胶水代码，它的目标是真正将 C 代码语义原汁原味地翻译为 Zig 语言本身。

表面上看，@cImport() 与 translate-c 似乎是两种截然不同的策略，但其底层本质完全是一模一样的！ 因为在编译器底层，@cImport() 实际上就是对 translate-c 的一行快捷内联封装。两者的核心转译引擎是同一套代码。当你使用 @cImport() 时，zig 编译器在后台默默执行的工作，就是现场把 C 头文件翻译为一段虚拟的 Zig 内存代码，并将其导入进你当前的模块空间。

在当前的 Zig 语言演进规划中，官方已批准了一项提案（Proposal #20630）2，计划在未来将 @cImport() 彻底迁移至 Zig 构建系统 build.zig 中。一旦该提案完全落地，使用 @cImport() 的策略将被规范化为在 build.zig 中调用转译构建步（Translate C step），从而使得头文件转译在工程构建阶段统一缓存处理，而业务源码中只需干干净净地直接 @import 转译产物即可。

14.1.2 将 Zig 代码与 C 库链接

无论你选用上述哪种策略引入头文件，只要你在 Zig 中真正调用了 C 函数，就必须在编译阶段将 Zig 代码与目标 C 库完成物理链接！

换句话说，每当你在 Zig 代码中引入 C 函数时，你的构建流程中就引入了一项物理依赖。 这对于任何熟悉 C/C++ 的开发者而言都是理所当然的常识。因为头文件（Header file）仅仅提供了函数的声明（Declaration，即函数名、入参和返回值签名），而并不包含函数的机器码定义（Definition）。为了让最终生成的可执行文件能够找到函数的真实机器指令，zig 编译器必须在构建时将代码链接到对应的静态库（.a/.lib）或动态库（.so/.dll/.dylib）上。

正如我们在 Chapter 9 中系统探讨的，根据 C 库的来源不同，链接方式也有所区别： 如果这是一个第三方开源 C 库源码，你可以在 build.zig 中指挥编译器先编译该 C 库再进行链接； 如果该库已经作为系统库预装在你的操作系统环境中，则只需通过 linkSystemLibrary() 或编译器命令行参数进行链接。

14.2 引入 C 头文件实战

在 Section 14.1.1 中我们介绍了引入 C 头文件的两种核心策略，接下来我们结合在 Section 14.1.2 中讨论的链接规则，逐一拆解它们的实际操作细节。

14.2.1 策略一：使用 zig translate-c 静态转译

在此策略下，我们首先在命令行终端中调用 zig translate-c 工具，将目标 C 头文件预先转译成独立的 .zig 文件。 例如，假设我们希望使用 C 标准库 stdio.h 中的 fopen() 或 printf() 函数，可以在终端中执行如下命令：

zig translate-c /usr/include/stdio.h \
    -lc -I/usr/include \
    -D_NO_CRT_STDIO_INLINE=1 > c.zig \

注意，在这条 bash 命令中，我们传入了编译和使用 stdio.h 头文件所需的编译器参数（-D 用于定义宏，-l 用于链接库，-I 用于添加”包含路径”）。还要注意，我们把翻译结果保存在一个名为 c.zig 的 Zig 模块中。

转译完成后，在你的业务代码中，只需像引入普通 Zig 模块一样 @import("c.zig") 即可直接调用其中的 C 函数。 请注意：在编译此代码时，必须附带 -lc 参数以告知编译器链接系统的 C 标准库 libc：

const c = @import("c.zig");
pub fn main() !void {
    const x: f32 = 1772.94122;
    _ = c.printf("%.3f\n", x);
}
1772.941

14.2.2 策略二：使用 @cImport() 直接内联导入

在日常快速开发中，更便捷、也最常用的是借助内置函数 @cImport() 与 @cInclude() 现场内联引入。 在 @cImport() 的花括号代码块内部，我们可以调用 @cInclude() 来包含头文件，必要时还可以调用 @cDefine() 来定义宏常量。

@cInclude() 在语义上完全等价于 C 语言的 #include 预编译指令。 我们将 @cImport() 的调用结果赋给一个常量对象（通常约定命名为 c），随后该 C 头文件中声明的全部 C 函数、结构体、宏常量和枚举，便都可以通过该命名空间自由调用！

在下面的代码中，我们同时引入了 C 标准 I/O 库 stdio.h（用于 printf()3）以及 C 数学函数库 math.h（用于浮点幂运算 powf()4）。 在编译此程序时，我们需要向编译器同时传入 -lc（链接 libc）与 -lm（链接 libm 数学库）标志：

const c = @cImport({
    @cDefine("_NO_CRT_STDIO_INLINE", "1");
    @cInclude("stdio.h");
    @cInclude("math.h");
});

pub fn main() !void {
    const x: f32 = 15.2;
    const y = c.powf(x, @as(f32, 2.6));
    _ = c.printf("%.3f\n", y);
}
1182.478

14.3 向 C 函数传递 Zig 值

虽然 Zig 与 C 的兼容度极高，但两种语言的对象模型在底层依然存在着本质差异。 最显著的鸿沟莫过于字符串模型（我们在 Section 1.8 中曾深入探讨）： - Zig 字符串：是一个携带了显式长度数值的连续字节数组切片（胖指针）； - C 语言字符串：仅仅是一个指向任意内存字节的裸指针，物理上必须依赖末尾的空字符（Null-terminator, \0）来界定字符串终点。

正因如此，当你把 Zig 变量传递给 C 语言函数时，并非所有类型都能无脑直接扔进去。 除了我们将在 Section 14.4 中单独介绍的“在 Zig 中直接创建 C 对象并传给 C 函数”外，当传递原生 Zig 对象时通常会出现两种典型场景：自动转换场景（Auto-conversion） 与 需要手动转换场景（Need-conversion）。

14.3.1 1. 自动转换场景（Auto-conversion）

所谓自动转换场景，是指 zig 编译器能够在编译期自动识别并妥善处理类型映射，无需开发者做任何多余代码转换。 这主要覆盖两大领域： 1. 源码字面量（Literal values）； 2. 所有在 Section 1.5 中介绍的原生基础类型（Primitive data types）。

对于基础标量类型，zig 编译器完全清楚如何将 Zig 的 i16 映射为 C 语言的 signed short、将 u8 映射为 unsigned char、将 f32 映射为 float 等。 而对于字符串字面量（如 "foo.txt"），只要开发者没有为该字面量显式打上固定的 Zig 类型注解，zig 编译器就会根据调用上下文推导其类型。当编译器检测到你正在将字符串字面量传给一个 C 函数时，它会自动在编译期将其解释并包装为标准的 C 语言以 null 结尾的字符串！

看看下面这个调用 C 语言 fopen() 打开文件的例子：fopen() 在 C 规范中接收两个以 null 结尾的 C 字符串指针作为入参。也就是说，我们没有做任何从 Zig 字符串到 C 字符串的转换，只是把 Zig 字符串字面量直接作为输入传给 C 函数，而它运行得很好！因为编译器会根据当前上下文，把字符串 "foo.txt" 解释为 C 字符串。

const c = @cImport({
    @cDefine("_NO_CRT_STDIO_INLINE", "1");
    @cInclude("stdio.h");
});

pub fn main() !void {
    const file = c.fopen("foo.txt", "rb");
    if (file == null) {
        @panic("Could not open file!");
    }
    if (c.fclose(file) != 0) {
        return error.CouldNotCloseFileDescriptor;
    }
}

我们来做几个实验，用不同的方式编写同样的代码，看看这会对程序产生什么影响。首先，我们把字符串 "foo.txt" 存入一个 Zig 对象，比如下面的 path 对象，然后把这个 Zig 对象作为输入传给 C 函数 fopen()。

这样做，程序仍然能成功编译并运行。注意，在下面的例子中我省略了大部分代码，这只是为了简洁，因为程序的其余部分没有变化。这个例子与上一个例子的唯一区别，就是下面这两行。

    const path = "foo.txt";
    const file = c.fopen(path, "rb");
    // Remainder of the program

那么，如果给 path 对象一个显式的数据类型会怎样？如果我通过给 path 对象标注 []const u8 数据类型，强制 zig 编译器把它解释为 Zig 字符串对象，就会得到一个编译错误，如下所示。我们之所以得到这个编译错误，是因为我现在强制 zig 编译器把 path 解释为 Zig 字符串对象。

根据错误信息，C 函数 fopen() 期望接收的输入值类型是 [*c]const u8（C 字符串），而不是 []const u8（Zig 字符串）。更具体地说，[*c]const u8 这个类型实际上就是 C 字符串在 Zig 中的类型表示。类型中的 [*c] 部分表示一个 C 指针。所以这个 Zig 类型的含义本质上是：一个指向常量字节（const u8）数组的 C 指针（[*c]）。

    const path: []const u8 = "foo.txt";
    const file = c.fopen(path, "rb");
    // Remainder of the program
t.zig:2:7 error: expected type '[*c]const u8', found '[]const u8':
    const file = c.fopen(path, "rb");
                         ^~~~

因此，单就字符串字面量而言，只要你不给这些字符串字面量显式指定数据类型，zig 编译器就应当能够根据需要自动把它们转换为 C 字符串。

那么，如果使用 Section 1.5 中介绍的某种基础数据类型呢？以下面的代码为例。这里我们把几个浮点数字面量作为输入传给 C 函数 powf()。注意，这个代码示例能够成功编译并运行。

const std = @import("std");
const cmath = @cImport({
    @cInclude("math.h");
});

pub fn main(init: std.process.Init) !void {
    var stdout_buffer: [1024]u8 = undefined;
    var stdout_writer = std.Io.File.stdout().writer(init.io, &stdout_buffer);
    const stdout = &stdout_writer.interface;
    const y = cmath.powf(15.68, 2.32);
    try stdout.print("{d}\n", .{y});
    try stdout.flush();
}
593.2023

同样，由于 zig 编译器起初并没有为字面量 15.68 和 2.32 绑定特定的数据类型，编译器可以在把它们传给 C 函数 powf() 之前，自动将这些值转换为对应的 C float（或 double）值。现在，即使我把这些字面量存入一个 Zig 对象，并显式标注这个对象的类型，从而给它们一个显式的 Zig 数据类型，代码仍然能成功编译并运行。

    const x: f32 = 15.68;
    const y = cmath.powf(x, 2.32);
    // The remainder of the program

14.3.2 “需要转换”的场景

所谓”需要转换”的场景，是指在把 Zig 对象作为输入传给 C 函数之前，需要手动把它们转换为与 C 兼容的值。把 Zig 字符串对象传给 C 函数时，你就会遇到这种情况。

我们在上一个 fopen() 例子中已经见过这种具体情形，下面再复现一次。可以看到，在这个例子中，我们给 path 对象指定了显式的 Zig 数据类型（[]const u8），结果就是强制 zig 编译器把 path 对象视为 Zig 字符串对象。因此，在把它传给 fopen() 之前，我们现在需要手动把这个 path 对象转换为 C 字符串。

    const path: []const u8 = "foo.txt";
    const file = c.fopen(path, "rb");
    // Remainder of the program
t.zig:10:26: error: expected type '[*c]const u8', found '[]const u8'
    const file = c.fopen(path, "rb");
                         ^~~~

把 Zig 字符串对象转换为 C 字符串有多种方法。其中一种解决办法是，不直接把 Zig 对象作为输入，而是提供指向其底层字节数组的指针。你可以通过 Zig 字符串对象的 ptr 属性访问这个指针。

下面的代码示例演示了这种策略。注意，通过 ptr 属性传入指向 path 底层数组的指针后，在使用 C 函数 fopen() 时就不会再出现编译错误。

    const path: []const u8 = "foo.txt";
    const file = c.fopen(path.ptr, "rb");
    // Remainder of the program

这个策略之所以可行，是因为 ptr 属性中这个指向底层数组的指针，在语义上与指向字节数组的 C 指针完全相同，也就是一个类型为 *unsigned char 的 C 对象。这就是为什么这种做法同样解决了把 Zig 字符串转换为 C 字符串的问题。

（译注：把 .ptr 传给期望 C 字符串的函数，前提是底层字节数组以 \0 结尾，比如字符串字面量。如果切片是从更长的字符串中截取出来的，末尾没有 \0，C 函数就会越界读取，导致未定义行为。）

另一种做法是使用内置函数 @ptrCast()，显式地把 Zig 字符串对象转换为 C 指针。用这个函数，我们可以把 []const u8 类型的对象转换为 [*c]const u8 类型的对象。正如我在上一节所述，类型中的 [*c] 部分表示这是一个 C 指针。这种策略并不推荐，但可以用来演示 @ptrCast() 的用法。

你可能还记得 Section 2.5 中的 @as() 和 @ptrCast()。简单回顾一下，内置函数 @as() 用于把一个 Zig 值从类型”x”显式转换（或强制转换）为类型”y”的值。但这里我们转换的是一个指针对象。在 Zig 中，只要”类型转换操作”涉及指针，就要用到 @ptrCast() 函数。

在下面的例子中，我们用这个函数把 path 对象转换为一个指向字节数组的 C 指针，然后把这个 C 指针作为输入传给 fopen() 函数。注意，这个代码示例能够成功编译，没有任何错误。

    const path: []const u8 = "foo.txt";
    const c_path: [*c]const u8 = @ptrCast(path);
    const file = c.fopen(c_path, "rb");
    // Remainder of the program

14.4 在 Zig 中创建与使用 C 结构体

在 Zig 源码中实例化并操控 C 语言的结构体（Structs）极其自然。 首先按照我们在 Section 14.2 中介绍的方式导入声明了目标结构体的 C 头文件，随后就可以在 Zig 代码中将其作为普通类型来创建实例。

假设我们有一个名为 user.h 的 C 头文件，里面声明了如下 User 结构体：

#include <stdint.h>

typedef struct {
    uint64_t id;
    char* name;
} User;

该结构体包含一个 64 位无符号整数 id 以及一个 C 字符串指针 name。 在 Zig 中，我们可以像下面这样声明并初始化该结构体实例：

const std = @import("std");
const c = @cImport({
    @cInclude("user.h");
});

pub fn main() !void {
    var gpa = std.heap.DebugAllocator(.{}){};
    const allocator = gpa.allocator();

    // 声明一个未初始化的 C 结构体实例（等价于 C 语言的 User new_user;）
    var new_user: c.User = undefined;
    new_user.id = 1;

    // 手动开辟内存填充以 null 结尾的 C 字符串
    var user_name = try allocator.alloc(u8, 12);
    defer allocator.free(user_name);
    @memcpy(user_name[0..(user_name.len - 1)], "pedropark99");
    user_name[user_name.len - 1] = 0; // 显式写入 null 终止符 '\0'
    new_user.name = user_name.ptr;
}

这里我们使用 undefined 声明了 new_user。这在底层物理上与 C 语言直接写 User new_user; 完全等价——其内存在声明之初由未初始化的垃圾字节填充，随后由我们逐个字段手动赋值规范。

不过，在 Zig 代码中使用 C 库时，我们很少需要像上面那样手动实例化 C 结构体，因为 C 库通常会在公共 API 中提供”构造函数”。因此，我们通常依靠这些构造函数来正确初始化 C 结构体及其字段。

以 HarfBuzz 这个 C 库为例。它是一个文字塑形（text shaping）库，围绕一个”缓冲区对象”工作，更具体地说，就是 C 结构体 hb_buffer_t 的一个实例。所以，如果要使用这个 C 库，就需要创建这个 C 结构体的一个实例。好在这个库提供了 hb_buffer_create() 函数，可以用来创建这样的对象。因此，创建这个对象所需的 Zig 代码大概是这样的：

const c = @cImport({
    @cInclude("hb.h");
});
var buf: c.hb_buffer_t = c.hb_buffer_create();
// Do stuff with the "buffer object"

因此，我们不需要在这里手动创建 C 结构体 hb_buffer_t 的实例，也不需要手动为这个 C 结构体的每个字段赋予有效的值，因为构造函数 hb_buffer_create() 替我们完成了这项繁重的工作。

由于这个 buf 对象，以及前面例子中的 new_user 对象，都是 C 结构体的实例，所以这些对象本身就是与 C 兼容的值。它们是在 Zig 代码中定义的 C 对象。因此，你可以把这些对象自由地作为输入传给任何期望接收这种 C 结构体的 C 函数，不需要使用任何特殊语法，也不需要以任何特殊方式转换它们。这就是在 Zig 代码中创建和使用 C 对象的方法。

14.5 在 Zig 函数之间传递 C 结构体

正如我们在 Section 14.4 中所述，在 Zig 中创建的 C 对象可以直接传给 C 函数；但如果要在不同的 Zig 函数之间传递这些 C 结构体对象（例如我们在 Section 14.4 中使用的 user.h 里的 User 结构体），应该注意什么呢？

本质上，这种情况只需要对 Zig 函数的声明做一个小调整：确保把 C 对象按引用传给函数，而不是按值传递。为此，需要把接收这个 C 对象的函数参数的数据类型标注为”指向 C 结构体的指针”，而不是”C 结构体的实例”（即加上星号 *，如 *c.User）。（译注：按值传递 C 结构体在 Zig 中同样可以编译。这里传指针，是因为函数需要修改调用方的那个对象。）

看看下面这个通过 Zig 函数修改 C 结构体成员的规范范例： 我们定义了 set_user_id() 函数，该函数接收 id 以及一个指向 c.User 的指针 user: *c.User。 在函数体内部，我们借助在 Chapter 6 学到的 .* 语法对指针执行解引用，并修改其内部字段：

const std = @import("std");
const c = @cImport({
    @cInclude("user.h");
});

fn set_user_id(id: u64, user: *c.User) void {
    user.*.id = id;
}

pub fn main(init: std.process.Init) !void {
    var stdout_buffer: [1024]u8 = undefined;
    var stdout_writer = std.Io.File.stdout().writer(init.io, &stdout_buffer);
    const stdout = &stdout_writer.interface;
    var gpa = std.heap.DebugAllocator(.{}){};
    const allocator = gpa.allocator();

    var new_user: c.User = undefined;
    new_user.id = 1;
    var user_name = try allocator.alloc(u8, 12);
    defer allocator.free(user_name);
    @memcpy(user_name[0..(user_name.len - 1)], "pedropark99");
    user_name[user_name.len - 1] = 0;
    new_user.name = user_name.ptr;

    set_user_id(25, &new_user);
    try stdout.print("New ID: {any}\n", .{new_user.id});
    try stdout.flush();
}
New ID: 25

因为我们把函数参数改成了指针，所以在函数体内无论出于什么原因需要访问这个输入指针所指向的值（比如读取、更新或删除这个值），都必须用 Chapter 6 中学到的 .* 语法对指针解引用。
