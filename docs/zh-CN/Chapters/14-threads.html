16  Zig 多线程与并行计算

在现代软件工程中，充分榨干多核 CPU 的计算潜能已是高性能架构的标配。 在本章中，我们将系统探讨操作系统线程的核心本质，以及如何在 Zig 中利用标准库提供的跨平台原语启动线程、实现并行加速、协调资源同步，并规避死锁与数据竞争等经典并发陷阱。

16.1 什么是线程？

简单来说，线程（Thread）是操作系统内核能够独立调度的最小执行上下文（Context of execution）。 在程序中引入线程的核心目的，就是实现并行计算（Parallelism）——让计算机在同一时刻并行处理多项不同任务，从而大幅缩短整体运行耗时、成倍提升处理吞吐。

默认情况下，绝大多数常规程序都是单线程（Single-threaded）的。这意味着整个程序内部只有一个唯一的执行上下文。当仅有一条线程在跑时，程序根本不具备并行能力，所有指令与函数调用只能按部就班地串行执行（Sequential execution）——上一条指令没跑完，下一条指令就必须原地苦苦等待。而一旦我们在程序内部开辟出多个并发线程，计算机便能真正调动多颗 CPU 核心同时执行多条不同的指令流。

在真实软件工业界中，多线程技术的应用几乎无处不在。许多大型复杂软件天生就是为并行计算量身定制的：例如视频剪辑与图像渲染软件（如 Adobe Photoshop、DaVinci Resolve）、3A 级大型游戏（如《巫师 3》），以及我们每天都在使用的现代网页浏览器（Google Chrome、Firefox、Microsoft Edge 等）。

以网页浏览器为例：浏览器中每一个打开的标签页（Tab），通常作为浏览器主进程中的独立线程运行。（译注：这是原文的说法。Chrome、Firefox 等现代浏览器实际上采用多进程架构，标签页通常运行在独立的渲染进程中。） 将各个标签页放进独立线程中并发调度，才使得所有打开的页面能够彼此独立、互不干扰地同时运行： 比如你可以在一个标签页里打开 YouTube 或 Spotify 播放播客音乐，同时在另一个标签页里打开 Google Docs 撰写技术报告。即便你的视线和鼠标焦点完全停留在 Google Docs 的标签页上，耳朵里依然能流畅听到背景音乐——这完全得益于 YouTube 播放线程与你的文档编辑线程正在底层 CPU 上齐头并进地并行运转！

设想一下：如果没有多线程机制，浏览器唯一的替代方案就是为每一个新标签页都启动一个完整独立的操作系统新进程。但这将带来极其灾难性的资源负担——创建和维护进程的开销远比线程昂贵数倍，随便开几个网页整台电脑的物理内存和 CPU 就会被消耗殆尽，用户会遭遇严重的卡顿与掉帧。相比之下，线程创建极其迅速，且与宿主进程共享大部分底层资源，系统开销极其轻微。现代浏览器多标签页流畅并发的体验，正是建立在多线程基石之上的。

此外，多线程架构在服务请求处理（Serving requests or orders）场景下也有着不可替代的优势。 因为处理一项外部请求往往需要消耗漫长的等待时间（例如等待网络 I/O、磁盘读写或第三方响应），程序在大部分时间里其实处于无所事事的空转（Idle）状态。

我们可以用一家餐厅的日常点单出餐流程来打个形象的比方： 在一家餐厅里，服务一桌顾客通常包含以下环节： 1. 餐厅服务员接收顾客的点单； 2. 服务员把菜单送进后厨，等待厨师把菜烹饪做好； 3. 后厨厨师开始起火做菜； 4. 菜肴彻底做好后，服务员端菜上桌交付给顾客。

细品上述流程你会发现：在第 2 步中存在着一段巨大的“空闲等待期”——在厨师切菜掌勺的这段时间里，如果服务员啥也不干、原地傻站着干等饭菜出锅，这无疑是极大的资源浪费。

如果我们用单线程程序来模拟这家餐厅，代码就会显得极其低效。因为程序在“轮询检查饭菜是否出锅”的步骤上会被迫陷入长时间的空转阻塞：

const order = Order.init("Pizza Margherita", n = 1);
const waiter = Waiter.init();
waiter.receive_order(order);
waiter.ask_kitchen_to_cook();
var food_not_ready = true;
// 单线程下被死循环检查活活卡死！
while (food_not_ready) {
    food_not_ready = waiter.is_food_ready();
}
const food = waiter.get_food_from_kitchen();
waiter.send_food_to_client(food);

这段单线程代码的致命硬伤就在于那个 while 循环。服务员被死死绑在厨房门口寸步难行，既不能接待新进门的客人，也不能处理其他桌的催单。 更合理的做法显然是：服务员把点菜单交到后厨后，便立刻转身去前厅接待其他客人、记录新的订单！

这正是多线程的用武之地！我们可以开辟一条专门的后台线程把做菜和送餐任务剥离出去，让主线程上的服务员彻底从无休止的“等待苦差”中解脱出来：

fn cook_and_deliver_order(order: *Order) void {
    const chef = Chef.init();
    const food = chef.cook(order.*);
    chef.deliver_food(food);
}

fn send_order(order: Order) void {
    // 为后厨做菜专门派生一条独立的后台线程并将其分离（detach）
    const cook_thread = Thread.spawn(
        .{}, cook_and_deliver_order, .{&order}
    );
    cook_thread.detach();
}

const waiter = Waiter.init();
while (true) {
    const order = waiter.get_new_order();
    if (order) {
        // 瞬间派发，主线程立刻继续向下接客，绝不阻塞！
        send_order(order);
    }
}

在多线程版本中，服务员每收到一张订单就调用 send_order()。该函数仅仅是在后台派生一条新线程并使其分离自理，创建线程只需几微秒，函数瞬间返回。服务员完全无需为后厨做菜的漫长耗时操心，主循环片刻不停地接着接待下一波客人。而后台新线程中，厨师有条不紊地炒菜出餐，端上餐桌，整个餐厅的周转吞吐量提升了数倍！

16.2 线程与进程（Threads versus processes）

当我们在操作系统中运行一个可执行程序时，操作系统内核会为其创建一个独立的进程（Process）。 程序与进程是一对一的关系——每一个被启动的应用程序在操作系统内部都是一个独立的进程实例。 但与此同时，正如我们在 Section 16.1 中所述，每一个进程内部又可以自由创建并容纳多条并发线程。因此，进程与线程呈现出一对多的关系。

这也意味着：你在代码中创建的任何一条线程，在生命周期上都严格隶属于宿主进程。线程是宿主进程的子集与派生单元。 所有同属于一个进程的各条线程，都会共享该进程所持有的绝大部分底层系统资源。正因如此，同进程内各线程之间的通信与数据交换，远比两个独立进程之间轻量得多。

设想一下：当你开发一个庞大复杂的应用系统时，有时会发现将其拆解为两个模块协同推进心智负担会小很多。 在传统架构下，部分架构师会选择将它们彻底拆写为两个互不相干的独立二进制程序，然后架设复杂的进程间通信（IPC, Inter-Process Communication）机制（如管道、消息队列、共享内存段或本地 Socket）让它们彼此对话。 然而 IPC 的编写、编解码与同步协议往往极其繁琐晦涩。

此时，基于多线程的设计便展现出无与伦比的优雅：主逻辑作为主线程驻留进程，后台任务则通过 Thread.spawn 派生独立线程执行。 由于处于同一个进程地址空间内，各线程天生共享着同一张操作系统文件描述符表（stdout、stdin、stderr）、完全共享着进程的堆内存空间（Heap）以及全局数据段（Global Data Section），因此进程和线程之间可以很方便地通过控制流和数据相互通信。

深入到内存微观布局，每个线程在创建时，操作系统都会为其专门开辟一块专属独立的调用栈帧空间（Stack frame）。 这意味着： - 你在线程内部创建的每个局部对象，都局限于这个线程，也就是说其他线程看不到这个局部对象； - 除非你创建的对象位于堆上。换句话说，如果这个对象所关联的内存在堆上，其他线程就有可能访问它。

（译注：同一进程中的所有线程共享同一个地址空间，栈本身并没有隔离。如果把栈上对象的指针传给另一个线程，比如后文示例中把 &id1 传给新线程，另一个线程同样可以访问它。所以更准确的说法是：其他线程通常不会引用栈上的局部对象，除非你把它的指针传出去。）

总结一下：各线程拥有各自独立的栈，但齐心共享同一个堆、同一批标准 I/O 描述符以及同一套全局静态变量。

16.3 创建并启动一个线程（Creating a thread）

在 Zig 中创建新线程，首先引入 std.Thread 结构体，随后调用其核心方法 spawn() 即可从当前进程派生出一条全新的执行线程。 该方法接收三个核心参数，依次为：

  1. SpawnConfig 配置对象：用于精细定制线程创建细节（如栈空间大小、内存分配器等）；
  2. 目标工作函数指针：即新线程启动后所要调用的业务函数名；
  3. 函数实参元组：以匿名元组结构体的形式，提供给第二个参数中目标函数的入参列表。

通过这三个参数，你可以全权掌控线程的启动姿态与工作内容。线程创建后，你传给 spawn() 的函数会被调用，从而在这个新线程上开始执行，第三个参数中的各个实参会按顺序传给该函数。

关于第一个配置参数 SpawnConfig，它是一个包含两个可选字段的配置结构体： - stack_size：传入一个 usize 数值，显式限定该线程私有调用栈的大小（以字节为单位）。默认情况下，标准库设定的缺省值为 \(16 \times 1024 \times 1024\)（即 16MB）； - allocator：传入一个分配器实例，专门用于为该线程结构体内部开辟底层管理数据。

如果你的业务场景不需要特殊定制、完全满意默认配置，直接传入一个空匿名结构体 .{} 即可。

下面看一个最基础但完整的单线程派生实例：

const std = @import("std");
const Thread = std.Thread;
const duration = std.Io.Duration.fromSeconds(1);
const clock: std.Io.Clock = .awake;

fn do_some_work(io: std.Io) !void {
    std.debug.print("Starting the work.\n", .{});
    try std.Io.sleep(io, duration, clock);
    std.debug.print("Finishing the work.\n", .{});
}

pub fn main(init: std.process.Init) !void {
    const thread = try Thread.spawn(.{}, do_some_work, .{init.io});
    thread.join();
}
Starting the work.
Finishing the work.

注意在调用 Thread.spawn() 时必须搭配 try 关键字——因为创建线程属于操作系统内核调度，如果当前系统并发线程数超出了操作系统的限额配额（Quota），或者内存空间告罄，内核就会拒绝并返回错误。

一旦线程派生成功，spawn() 会返回一个代表该线程的句柄对象（类型为 std.Thread）。 同时请注意：新线程一旦生成，其内部的工作函数便会立即开始后台并发执行！ 它不需要你再手动调用什么 start() 按钮。这与 C 语言 pthreads 库中的 pthread_create() 类似，它同样会在线程创建后立即开始执行。

16.4 线程的归宿：join 与 detach

既然线程一经创建便立即开始执行，那么主线程该如何与它协调收尾？ 在系统底层多线程体系中，控制线程向主进程/主线程同步收尾的核心操作只有两个：join() 与 detach()。

每一个被创建出来的线程，最终都必须且只能被归类为以下两种状态之一：可汇合的（Joinable） 或 已分离的（Detached）： - 调用 join()：将该线程置为汇合状态； - 调用 detach()：将该线程置为分离状态。

需要特别注意：一条线程绝不能既被 join 又被 detach！ 换言之，你绝不能对同一个线程句柄既调用 join() 又调用 detach()。 但反过来，你又必须在两者中二选一显式调用其一！ 如果在代码中创建了线程，却既不 join 也不 detach，就会直接诱发未定义行为与底层资源泄漏，导致所谓的僵尸线程（后文 Section 16.8.2 会对此专门展开分析）。

16.4.1 汇合线程

汇合（join）一个线程，本质上就是在说：“嘿！能不能先等这个线程执行完，你再继续往下执行？”例如，回到我们在 Zig 中创建线程的第一个、也是最简单的例子：我们在程序的 main() 函数中创建了一个线程，并在最后对它调用了 join()。下面复现了这部分代码。

因为我们是在 main() 的作用域中汇合这个新线程，这意味着 main() 函数的执行会暂时停下来，等待这个线程执行完毕。也就是说，main() 的执行会暂时停在调用 join() 的那一行，直到这个线程完成它的任务之后才会继续。

pub fn main() !void {
    const thread = try Thread.spawn(.{}, do_some_work, .{});
    thread.join();
}

因为我们在 main() 的作用域中汇合了这个新线程，所以可以保证这个新线程会在 main() 执行结束之前完成，因为 main() 一定会等待这个线程完成它的任务。

在上面的例子中，join() 调用之后没有其他表达式了，接下来就是 main() 作用域的结尾。因此，线程完成任务之后，程序就直接结束了，因为已经没有别的事情要做。但如果在 join() 调用之后还有其他事情要做呢？

为了演示这种情况，看下面这个例子。这里我们创建了一个 print_id() 函数，它接收一个 id 作为输入，并把它打印到 stdout。在这个例子中，我们先后创建了两个新线程。然后先汇合第一个线程，接着等待整整两秒，最后再汇合第二个线程。

这个例子想说明的是，最后一次 join() 调用要等到第一个线程完成任务（即第一次 join() 调用）并且经过两秒的延迟之后才会执行。如果你编译并运行这个例子，会发现大部分消息都很快被打印到 stdout，也就是说，它们几乎是立即出现在屏幕上的。但是最后一条消息（“Joining thread 2”）要过大约 2 秒才会出现在屏幕上。（译注：下面代码中的睡眠时长写的是 fromNanoseconds(1000)，即 1 微秒，而不是 2 秒，所以实际运行时看不到明显的停顿。要观察到正文描述的效果，可以把这一行改为 std.Io.Duration.fromSeconds(2)。）

const std = @import("std");
const Thread = std.Thread;
const clock: std.Io.Clock = .awake;

fn print_id(id: *const u8) !void {
    std.debug.print("Thread ID: {d}\n", .{id.*});
}

pub fn main(init: std.process.Init) !void {
    const id1: u8 = 1;
    const id2: u8 = 2;
    const thread1 = try Thread.spawn(.{}, print_id, .{&id1});
    const thread2 = try Thread.spawn(.{}, print_id, .{&id2});
    std.debug.print("Joining thread 1\n", .{});
    thread1.join();

    const duration = std.Io.Duration.fromNanoseconds(1000);
    try std.Io.sleep(init.io, duration, clock);

    std.debug.print("Joining thread 2\n", .{});
    thread2.join();
}
Thread ID: Joining thread 1
1
Thread ID: 2
Joining thread 2

这说明两个线程都很快就完成了它们的工作（即打印 ID），早于两秒的延迟结束。因此，最后一次 join() 调用几乎是立即返回的，因为在调用最后一次 join() 时，第二个线程已经完成了它的任务。

如果你编译并运行这个例子，还会注意到，在某些情况下，消息会相互交织在一起。换句话说，你可能会看到消息 “Joining thread 1” 插在了消息 “Thread 1” 中间，或者反过来。这是因为：

  • 这些线程基本上与程序的主进程（即 main() 函数）同时执行。
  • 这些线程与程序的主进程共享同一个 stdout，这意味着线程产生的消息与主进程产生的消息被发送到完全相同的地方。

这两点在前面的 Section 16.1 中都讲过。所以，由于这些消息大致在同一时间产生并发送到同一个 stdout，它们可能会交织在一起。总之，当你对一个线程调用 join() 时，当前进程会等待这个线程完成之后再继续；当线程完成任务时，与这个线程相关的资源会被自动释放。（译注：std.debug.print() 实际输出到的是 stderr 而不是 stdout。）

16.4.2 分离线程：thread.detach()

与 join() 紧密等候相反，thread.detach() 的语义好比“孩子长大成人、彻底独立门户”。 一旦调用了 detach()，该线程在运行完毕后会自动向操作系统自行交还全部资源，完全不需要任何其他线程前去汇合认领。

因此，当你完全不在乎该后台线程具体的结束时刻、也不需要获取它的任何返回值时，直接对其调用 detach() 放飞自流是最佳选择。 看看下面这个分离线程的代码片段：

const std = @import("std");
const Thread = std.Thread;

fn print_id(id: *const u8) !void {
    std.debug.print("Thread ID: {d}\n", .{id.*});
}

pub fn main() !void {
    const id1: u8 = 1;
    const thread1 = try Thread.spawn(.{}, print_id, .{&id1});
    thread1.detach();
    std.debug.print("Finish main\n", .{});
}
Finish main

细心的同学在运行此代码时会惊讶地发现：控制台上仅仅打印了主函数的 "Finish main"，而子线程中原本应该打印的 "Thread ID: 1" 居然凭空消失了！ 这是为什么？ 原因非常简单：因为线程被 detach 分离后，主线程根本不会停下来等它。主进程在微秒级时间内光速跑完了全部代码并直接退出，操作系统随之销毁了整个进程的内存空间，而彼时被分离的子线程甚至都还没来得及向控制台发起系统调用！ 如果给 main 稍加一点点延迟（例如睡眠几毫秒），你就能顺利看到子线程的输出了。

16.5 互斥锁（Mutexes）

在所有的多线程工具箱中，“互斥锁（Mutex，即 Mutually Exclusive Lock）”都是最核心的经典守卫机制。 互斥锁充当着特定临界代码区域的“看门人”，它与线程同步有关，更具体地说，它能防止程序中出现一些经典的竞态条件，进而防止那些通常难以追踪和理解的严重 bug 与未定义行为。

形象地说，互斥锁好比一间带单人安全插销的洗手间： 当某条线程成功上锁（lock()）后，洗手间的门就被反锁了；其他想要进入洗手间的线程必须在门外耐心排队等候，直到里面的人出来并打开插销（unlock()），下一条线程才能进入。

另一个经典比喻是会议室里的“发言接力牌”1：主持人手里有一块发言牌，拿到牌子的人才有权开麦说话，其余所有人必须闭嘴倾听；当发言完毕把牌子交还主持人，主持人再转交给下一位申请发言的人。

互斥锁的核心使命，就是保证在任何给定的微秒时刻，被其守护的代码段绝对只能有一条线程独占执行！ 它专门用于保护跨线程共享的内存数据（例如全局变量或堆上共享对象）。访问或修改线程局部对象的代码区域，通常不需要使用互斥锁。

16.5.1 临界区（Critical section）

与互斥锁紧密相伴的概念是“临界区（Critical section）”。 所谓临界区，指的就是代码中访问或修改多线程共享资源（共享变量、文件句柄等）的那一段核心代码片段。如果不对这段区域施加保护，多条并发线程就会在此正面相撞引发竞争态 (Geeks for Geeks 2024)。

在程序中使用互斥锁时，临界区就定义了我们想要加锁的代码区域。所以我们通常在临界区的开头锁定互斥锁对象，在临界区的结尾解锁。下面两条要点出自 GeeksforGeeks 的文章《Critical Section》，很好地概括了临界区在线程同步问题中所起的作用 (Geeks for Geeks 2024)：

  1. 临界区必须作为一个原子操作来执行。这意味着一旦某个线程或进程进入了临界区，其他所有线程或进程都必须等待，直到正在执行的线程或进程退出临界区。同步机制的目的就是确保同一时刻只有一个线程或进程能够执行临界区。
  2. 临界区的概念是计算机系统中同步问题的核心，因为必须确保多个线程或进程能够并发执行而互不干扰。信号量、互斥锁、监视器、条件变量等各种同步机制都被用来实现临界区，确保共享资源以互斥的方式被访问。

16.5.2 原子操作（Atomic operations）

在并发领域，另一个高频出现的词汇是“原子操作（Atomic operation）”。 所谓原子，取其“不可再分”之意。如果一项操作在执行过程中绝对不可能被操作系统的线程上下文切换打断，那它就是原子操作。它要么完整执行完毕，要么根本没发生，绝不存在“执行到一半被打断挂起”的中间态。

原子操作天然免疫任何数据竞争！ 在现代多核 CPU 体系下，单条汇编指令由于微架构的微任务拆解，在默认情况下并不天然等同于物理原子操作。 Zig 标准库在 std.atomic 模块中提供了原生的原子包装类型 std.atomic.Value(T)，它封装了硬件底层的原子加载（load）、原子写入（store）以及原子加法（fetchAdd）等指令。其定位对标 C++ 标准库的 std::atomic<T>，需要强调的是，在 Zig 中，只有基础数据类型（即 Section 1.5 中介绍的那些类型）支持这些原子操作。

16.5.3 数据竞争与竞争态（Data races and race conditions）

为了看清互斥锁的救命价值，我们必须亲手解剖并发领域的头号杀手——数据竞争（Data race）。 所谓数据竞争，是指两条或多条并发线程在同一物理时刻，对同一块内存地址同时执行读写操作，且其中至少有一个操作是写入。 当程序存在数据竞争时，最终的运算结果完全取决于谁的 CPU 核心抢先跑快了几纳秒（“看谁跑得快”的竞争态），导致程序每次运行得出的答案千奇百怪、不可捉摸。

看看下面这个典型的反例：我们定义了一个全局计数器 counter，在两个线程里各自执行一个 10 万次的累加循环：

const std = @import("std");
const Thread = std.Thread;
var counter: usize = 0;

fn increment() void {
    for (0..100000) |_| {
        counter += 1;
    }
}

pub fn main() !void {
    const thr1 = try Thread.spawn(.{}, increment, .{});
    const thr2 = try Thread.spawn(.{}, increment, .{});
    thr1.join();
    thr2.join();
    std.debug.print("Counter value: {d}\n", .{counter});
}
Counter value: 117254

（译注：英文原文的代码与输出中把 Counter 误拼为 Couter，译文已更正，本章后续示例同。）

为什么会这样？答案是：这个程序存在数据竞争问题。只有当第一个线程在第二个线程开始执行之前就完成它的任务时，这个程序才会打印出正确的数字 200000。但这种情况不太可能发生，因为创建线程的过程非常快，所以两个线程几乎是同时开始执行的。如果你修改这段代码，在第一次和第二次调用 spawn() 之间加上几纳秒的睡眠，就会提高程序得到”正确结果”的概率。

所以，数据竞争问题的发生，是因为两个线程几乎在同一时间读写同一个内存位置。在这个例子中，每个线程在 for 循环的每次迭代中，本质上都在执行三个基本操作：

  1. 读取 count 的当前值。
  2. 把这个值加 1。
  3. 把结果写回 count。

在理想的同步状态下（如 Table 16.1 所示），线程 1 的这三步连贯完成，随后线程 2 再读写，双方和谐递增：

16.5.4 在 Zig 中使用互斥锁

结合我们在 Section 16.5.1 中关于临界区的讨论，解决方法非常明确：将 counter += 1 这一行临界区代码用互斥锁保护起来！ 在 Zig 标准库中，互斥锁通过 std.Io.Mutex 提供。

我们将 increment() 改造为接收互斥锁指针，并在累加前后分别调用 mutex.lock() 与 mutex.unlock()：

const std = @import("std");
const Thread = std.Thread;
const Mutex = std.Io.Mutex;
const State = Mutex.State;
var counter: usize = 0;

fn increment(io: std.Io, mutex: *Mutex) !void {
    for (0..100000) |_| {
        try mutex.lock(io);
        counter += 1;
        mutex.unlock(io);
    }
}

pub fn main(init: std.process.Init) !void {
    var mutex: Mutex = .{
        .state = std.atomic.Value(State).init(.unlocked)
    };

    const thr1 = try Thread.spawn(.{}, increment, .{init.io, &mutex});
    const thr2 = try Thread.spawn(.{}, increment, .{init.io, &mutex});
    thr1.join();
    thr2.join();
    std.debug.print("Counter value: {d}\n", .{counter});
}
Counter value: 200000

16.6 读写锁（Read/Write locks）

虽然互斥锁威力强大，但在某些高频场景下，全局一刀切的互斥锁会成为严重的性能瓶颈。 例如：假设有一个系统配置缓存文件，有 100 条线程频繁从里面读取参数，只有偶尔 1 条线程会向里面写入新配置。 如果 100 条线程纯粹只是并发读取数据，彼此之间根本不会发生任何冲突与破坏，这种场景完全可以安全地全速并行！ 但如果强行套用互斥锁，这 100 条读取线程就只能极其憋屈地一个接一个单行排队，系统吞吐量呈断崖式下跌。

针对这种“读多写少”的经典混合场景，读写锁（Read/Write Lock, 简称 RwLock）应运而生！

16.6.1 独占锁 vs 共享锁

读写锁之所以比普通互斥锁更加灵活高效，关键在于它细分了两种维度的锁权限：独占锁（Exclusive Lock） 与 共享锁（Shared Lock）： - 独占锁（写锁）：其行为与常规互斥锁完全一致。一旦某条线程获取了写锁，其他任何线程（无论想读还是想写）都必须全部被排除在门外等候； - 共享锁（读锁）：是一种包容性锁。只要当前没有任何线程持有写锁、且没有等待写锁的排队线程，多条希望获取读锁的线程就可以同时携手进入临界区，全速并行读取！

当某个线程尝试获取读锁（即共享锁）时，当且仅当没有其他线程持有写锁、并且没有其他线程正在排队等待获取写锁时，它才能拿到共享锁。如果拿不到读锁，这个线程的执行会立即被阻塞，直到成功获取读锁后才会恢复执行。从这个角度看，读锁本质上是一种安全机制：只有在安全的时候，它才允许一个线程与其他线程一起运行。 但一旦有某条线程准备执行写入并申请了独占写锁，后续的所有读取请求都会被暂时拦截排队，直到写操作稳妥提交完毕。 通过这种“读共享、写独占”的精细分流，我们既守住了并发写时的数据安全底线，又最大限度释放了多核并发读取的极限性能。

16.6.2 在 Zig 中使用读写锁

Zig 标准库通过 std.Thread.RwLock 模块支持读写锁。（译注：在 Zig 0.17.1 中，std.Thread 下已经没有 RwLock，读写锁位于 std.Io.RwLock，本章示例代码使用的也是它。）其核心 API 规范如下： - 申请读锁：调用 lockShared() 或非阻塞的 tryLockShared()； - 释放读锁：调用 unlockShared()； - 申请写锁：调用 lock() 或非阻塞的 tryLock()； - 释放写锁：调用 unlock()。

看下面这个 3 读 1 写的实战代码：三个 reader 线程高频共享读取计数器，一个 writer 线程独占自增计数器：

const std = @import("std");
const Thread = std.Thread;
const RwLock = std.Io.RwLock;
const duration = std.Io.Duration.fromSeconds(2);
const clock: std.Io.Clock = .awake;
var counter: u32 = 0;

fn reader(io: std.Io, id: u32, lock: *RwLock) !void {
    while (true) {
        if (lock.tryLockShared(io)) {
            std.debug.print("Thread {d}: {d}\n", .{id, counter});
            _ = lock.unlockShared(io);
            try std.Io.sleep(io, duration, clock);
        }
    }
}

fn writer(io: std.Io, lock: *RwLock) !void {
    while (true) {
        if (lock.tryLock(io)) {
            counter += 1;
            _ = lock.unlock(io);
            try std.Io.sleep(io, duration, clock);
        }
    }
}

pub fn main(init: std.process.Init) !void {
    var lock: RwLock = .init;
    const thr1 = try Thread.spawn(.{}, reader, .{init.io, 1, &lock});
    const thr2 = try Thread.spawn(.{}, reader, .{init.io, 2, &lock});
    const thr3 = try Thread.spawn(.{}, reader, .{init.io, 3, &lock});
    const wthread = try Thread.spawn(.{}, writer, .{init.io, &lock});

    thr1.join();
    thr2.join();
    thr3.join();
    wthread.join();
}

16.7 让出 CPU 时间片：yield()

Thread 结构体还提供了一个特殊的控制原语：yield()。 调用 yield() 的物理含义是：当前线程主动提出放弃 CPU 本轮剩余的时间片配额，请求操作系统调度器把 CPU 算力优先腾给其他就绪线程去跑。

需要说明的是，让出线程是如今”不太常见”的线程操作。换句话说，在生产环境中使用让出操作的程序员并不多，原因很简单：这个操作很难用好，而且还有更好的替代方案。大多数程序员更倾向于使用 join()。实际上，大多数时候，当你在某个代码示例中看到有人使用这种”让出”操作时，他们通常是为了帮助调试应用中的竞态条件。也就是说，如今这种”让出”操作主要被当作一种调试工具。

总之，如果你想让出一个线程，只需调用 yield() 方法，像这样：

try Thread.yield();

（译注：英文原文写作 thread.yield();。在 Zig 0.17.1 中，yield() 是 std.Thread 上不接收实例参数的函数，返回类型为 YieldError!void，所以需要写成 try Thread.yield(); 才能通过编译。）

16.8 多线程常见问题与防范

16.8.1 1. 死锁（Deadlocks）

所谓死锁，是指两条或多条线程各自捏着对方梦寐以求的锁资源，同时原地死等对方松手，最终陷入全员永久僵死、程序直接卡死的僵局。

看看下面这个典型的死锁示例：线程 1 先锁住了 mut1，随后试图获取 mut2；而线程 2 恰好先锁住了 mut2，转头去申请 mut1。双方互相等待，程序将永久挂起：

const std = @import("std");
const Thread = std.Thread;
const clock: std.Io.Clock = .awake;
const duration = std.Io.Duration.fromSeconds(1);
const State = std.Io.Mutex.State;
var mut1: std.Io.Mutex = .{ .state = std.atomic.Value(State).init(.unlocked) };
var mut2: std.Io.Mutex = .{ .state = std.atomic.Value(State).init(.unlocked) };

fn do_some_work1(io: std.Io) !void {
    try mut1.lock(io);
    try std.Io.sleep(io, duration, clock);
    try mut2.lock(io); // 试图拿 mut2，却被线程 2 死死占着
    std.debug.print("Doing some work 1\n", .{});
    mut2.unlock(io);
    mut1.unlock(io);
}

fn do_some_work2(io: std.Io) !void {
    try mut2.lock(io);
    try std.Io.sleep(io, duration, clock);
    try mut1.lock(io); // 试图拿 mut1，却被线程 1 死死占着
    std.debug.print("Doing some work 2\n", .{});
    mut1.unlock(io);
    mut2.unlock(io);
}

pub fn main(init: std.process.Init) !void {
    const thr1 = try Thread.spawn(.{}, do_some_work1, .{init.io});
    const thr2 = try Thread.spawn(.{}, do_some_work2, .{init.io});
    thr1.join();
    thr2.join();
}

规避死锁的黄金法则：在全工程范围内，凡涉及多个互斥锁嵌套锁定时，必须严格保证所有线程均按全局完全一致的固定顺序进行加锁（例如一律先锁 mut1 再锁 mut2）！

16.8.2 2. 漏调 join 或 detach 的后果

如果你创建了一条线程，却在代码逻辑里既没有调用 join()、也没有调用 detach()，那么这条线程就会沦落为“僵尸线程（Zombie thread）”。 由于无人接管其生命周期终点，操作系统为其开辟的栈空间与内核控制块将永远无法得到释放，从而造成严重的系统级资源泄漏。切记：join() 或 detach() 必须择其一显式调用！

16.8.3 3. 优雅停机与安全取消线程

在 C 语言的 pthreads 库中，可以通过 pthread_kill() 函数向线程发送 SIGTERM 信号，以异步方式杀死或取消一个线程。 但这种粗暴的暴力终止是极其危险的反模式！因为你根本无法预料线程被击杀的那一瞬间手头捏着哪些没来得及释放的互斥锁与文件句柄，极易诱发整个进程的资源死锁与数据结构腐化。 因此，Zig 的线程实现没有类似的函数，也没有类似的方式来异步取消或杀死线程。

所以，如果你想在 Zig 中让一个线程在执行中途取消，一个不错的策略是结合使用控制流和 join()。 通过结合我们在 Section 16.5.2 学到的原子布尔标志位 std.atomic.Value(bool)，可以把线程设计成一个不断检查自己是否应该继续运行的 while 循环；到了该取消线程的时候，就让 while 循环跳出，再通过调用 join() 让线程与主线程汇合。下面的代码在一定程度上演示了这种策略：这里我们用控制流跳出 while 循环，让线程比原计划更早退出。

const std = @import("std");
const Thread = std.Thread;
const clock: std.Io.Clock = .awake;
const duration = std.Io.Duration.fromSeconds(2);
var running = std.atomic.Value(bool).init(true);
var counter: u64 = 0;

fn do_more_work(io: std.Io) !void {
    try std.Io.sleep(io, duration, clock);
}

fn work(io: std.Io) !void {
    while (running.load(.monotonic)) {
        for (0..10000) |_| {
            counter += 1;
        }
        if (counter > 15000) {
            std.debug.print("Time to cancel the thread.\n", .{});
            // 线程主动感知条件并下发停机通知
            running.store(false, .monotonic);
        } else {
            std.debug.print("Time to do more work.\n", .{});
            try do_more_work(io);
        }
    }
}

pub fn main(init: std.process.Init) !void {
    const thread = try Thread.spawn(.{}, work, .{init.io});
    thread.join();
}
