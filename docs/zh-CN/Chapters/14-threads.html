16  Zig 中的线程与并行简介

Zig 通过标准库里的 Thread 结构体提供线程。这个结构体表示一个内核线程，遵循 POSIX 线程的模式，也就是说，它的工作方式和 pthread C 库中的线程类似，这个库通常随 GNU C 编译器（gcc）的各个发行版一起提供。如果你还不熟悉线程，我们先来讲讲它背后的一些理论吧。

16.1 什么是线程？

线程基本上就是一个独立的执行上下文。 我们用线程给程序引入并行，大多数情况下这会让程序跑得更快，因为有多个任务在同时、彼此并行地执行。

程序默认通常是单线程的，也就是说每个程序通常只在一个线程，或者说一个执行上下文上运行。只有一个线程在运行时，就没有并行。而没有并行时，命令是顺序执行的，也就是同一时刻只执行一条命令，一条接一条。在程序里创建多个线程后，我们就开始同时执行多条命令了。

创建多个线程的程序在实际中非常常见，因为很多不同类型的应用都很适合并行。好的例子有视频和照片编辑应用（例如 Adobe Photoshop 或 DaVinci Resolve）、游戏（例如《巫师 3》），还有网页浏览器（例如 Google Chrome、Firefox、Microsoft Edge 等）。 比如在网页浏览器中，线程通常用来实现标签页。浏览器的标签页通常作为浏览器主进程中的独立线程运行。也就是说，你在浏览器里新打开的每个标签页，通常都运行在一个独立的执行线程上。（译注：这是原文的说法。Chrome、Firefox 等现代浏览器实际上采用多进程架构，标签页通常运行在独立的渲染进程中。）

让每个标签页在独立的线程中运行，浏览器里所有打开的标签页就能同时、彼此独立地运行。比如你可能在一个标签页里开着 YouTube 或 Spotify，正在听播客，同时在另一个标签页里用 Google Docs 写文章。即使你没在看 YouTube 那个标签页，也照样能听到播客，这正是因为这个 YouTube 标签页和运行 Google Docs 的另一个标签页在并行运行。

如果没有线程，另一种做法是把每个标签页都作为电脑上一个完全独立的进程来运行。但这是个糟糕的选择，因为只开几个标签页就会消耗电脑太多的电量和资源。换句话说，和创建一个新的执行线程相比，创建一个全新的进程开销非常大。而且你在使用浏览器时遇到卡顿和额外开销的可能性也会很大。线程创建起来更快，消耗的计算机资源也少得多，尤其是因为它们和主进程共享一部分资源。

所以，正是现代浏览器对线程的使用，让你能一边在 Google Docs 上写东西，一边听播客。 没有线程的话，浏览器大概只能有一个标签页。

线程也很适合用来处理任何涉及服务请求或订单的事情。因为处理一个请求需要时间，而且通常包含大量”等待时间”。 换句话说，我们会花很多时间空闲着，等某件事完成。 以餐厅为例，餐厅里处理订单通常包括以下步骤：

  1. 从顾客那里接收订单。
  2. 把订单交给厨房，等待饭菜做好。
  3. 在厨房里开始做菜。
  4. 饭菜完全做好后，把它送到顾客手上。

想一想上面这几点，你会发现整个过程中有一段很长的等待时间，就是饭菜在厨房里烹制的时候。饭菜在准备期间，服务员和顾客本人都在等饭菜做好、送上来。

如果我们写一个程序来表示这家餐厅，更具体地说，写一个单线程程序，那这个程序会非常低效。因为程序会在”检查饭菜好了没有”这一步上空闲等待相当长的时间。看看下面这段可能表示这样一个程序的代码片段。

这个程序的问题出在 while 循环上。程序会在这个 while 循环上花很多时间等待，除了检查饭菜好没好之外什么也不做。这是在浪费时间。服务员与其干等某件事发生，不如把订单送到厨房后就接着干别的，继续接收其他顾客的订单、往厨房送更多订单，而不是什么都不做、等饭菜做好。

const order = Order.init("Pizza Margherita", n = 1);
const waiter = Waiter.init();
waiter.receive_order(order);
waiter.ask_kitchen_to_cook();
var food_not_ready = true;
while (food_not_ready) {
    food_not_ready = waiter.is_food_ready();
}
const food = waiter.get_food_from_kitchen();
waiter.send_food_to_client(food);

这就是为什么线程非常适合这个程序。我们可以用线程把服务员从”等待的职责”中解放出来，让他们去做其他任务、接收更多订单。看看下一个例子，我把上面的程序改写成了另一个用线程来做菜和送餐的程序。

在这个程序中可以看到，服务员从顾客那里收到新订单时，会执行 send_order() 函数。 这个函数唯一做的事，就是创建一个新线程并把它分离。 由于创建线程是非常快的操作，send_order() 函数几乎立即返回，所以服务员几乎不用在这份订单上花时间，直接接着去拿顾客的下一份订单。

在新创建的线程里，厨师把订单做好，饭菜好了之后就送到顾客的餐桌上。

fn cook_and_deliver_order(order: *Order) void {
    const chef = Chef.init();
    const food = chef.cook(order.*);
    chef.deliver_food(food);
}
fn send_order(order: Order) void {
    const cook_thread = Thread.spawn(
        .{}, cook_and_deliver_order, .{&order}
    );
    cook_thread.detach();
}

const waiter = Waiter.init();
while (true) {
    const order = waiter.get_new_order();
    if (order) {
        send_order(order);
    }
}

16.2 线程与进程

我们运行一个程序时，这个程序会作为操作系统里的一个进程来执行。这是一对一的关系：你执行的每个程序或应用，在操作系统里都是一个单独的进程。但每个程序，或者说每个进程，都可以在内部创建并容纳多个线程。因此，进程和线程是一对多的关系。

这也意味着，我们创建的每条线程，总是和电脑上的某一个进程关联在一起。换句话说，线程总是某个已有进程的子集，从属于这个进程。一条线程从哪个进程创建出来，就会和那个进程共享一部分资源。正因为线程和进程共享资源，它们很适合让各项任务之间的通信变简单。

举个例子。假设你在开发一个又大又复杂的应用，如果能把它拆成两块，并让这两块彼此对话，事情会简单得多。有些程序员会真的把代码库的这两块写成两个完全独立的程序，然后用 IPC（inter-process communication，进程间通信）让这两个独立的程序（也就是进程）互相交谈、一起工作。

不过，有些程序员觉得 IPC 很难对付，于是更愿意把代码库的一块写成「程序的主体」，也就是作为操作系统里那个进程来运行的部分，另一块则写成要在一条新线程里执行的任务。进程和线程之间很容易通信，控制流可以，数据也可以，因为它们共享同一套标准文件描述符（stdout、stdin、stderr），也共享堆上的同一块内存空间，以及同一份全局数据区。

再说细一点。你创建的每条线程都有一块单独留给它的栈帧。这基本上意味着，你在这条线程内部创建的每个局部对象，都是这条线程局部的，其他线程看不到这个局部对象。除非你创建的这个对象住在堆上。换句话说，如果这个对象所关联的内存在堆上，其他线程就有可能访问它。

（译注：同一进程里的所有线程共享同一个地址空间，栈本身并没有隔离。如果把栈上对象的指针传给另一条线程，比如后文示例里把 &id1 传给新线程，另一条线程同样可以访问它。更准确的说法是：其他线程通常不会去用栈上的局部对象，除非你把指针传出去。）

因此，存在栈上的对象，对于创建它们的那条线程来说是局部的。存在堆上的对象，则有可能被其他线程访问到。这一切意味着：每条线程有自己单独的栈帧，但与此同时，所有线程共享同一个堆、同一套标准文件描述符（也就是共享同一个 stdout、stdin、stderr），以及程序里的同一份全局数据区。

16.3 创建线程

在 Zig 里创建新线程，要先把 Thread 结构体导入当前的 Zig 模块，然后调用这个结构体的 spawn() 方法。这个方法会从当前进程创建（或者说「派生」）出一条新的执行线程。这个方法有三个参数，依次是：

  1. 一个 SpawnConfig 对象，里面是这次派生过程的配置。
  2. 将要在这条新线程里执行（或者说将被「调用」）的函数的名字。
  3. 一份参数（或者说输入）列表，会传给第二个参数里的那个函数。

有了这三个参数，你就能控制线程如何被创建，也能指定这条新线程里要做哪些工作（或者说「任务」）。线程只是一个单独的执行上下文。我们通常在代码里创建新线程，是因为想在这个新的执行上下文里做一些工作。具体做什么工作、在这个上下文里走哪些步骤，是通过把一个函数的名字作为 spawn() 的第二个参数提供进去来指定的。

因此，这条新线程被创建出来时，你提供给 spawn() 方法的那个函数会在这条新线程里被调用，或者说被执行。这个函数被调用时拿到哪些参数、哪些输入，由你在 spawn() 的第三个参数里提供的那份参数（或者说输入）列表来控制。这些参数传给函数的顺序，和它们提供给 spawn() 的顺序相同。

另外，SpawnConfig 是一个结构体对象，只有两个可以设置的字段，或者说两个成员，用来调整派生行为。这两个字段是：

  • stack_size：你可以提供一个 usize 值，指定这条线程的栈帧大小（以字节为单位）。默认值是 \(16 \times 1024 \times 1024\)。
  • allocator：你可以提供一个分配器对象，在为这条线程分配内存时使用。

要用这两个字段（或者说「配置」）中的某一个，你只要新建一个 SpawnConfig 类型的对象，再把这个对象作为输入传给 spawn() 方法。如果你对这两种配置都不感兴趣，默认值就够用，那就可以在这个 SpawnConfig 参数的位置上直接放一个匿名结构体字面量（.{}）。

作为第一个、也是非常简单的例子，看看下面的代码。在同一个程序里，如果你愿意，可以创建多条执行线程。但在这第一个例子里，我们只创建一条执行线程，因为 spawn() 只调用了一次。

另外注意，这个例子里我们在新线程内部执行的是 do_some_work() 函数。由于这个函数不接收输入，因为它没有参数，所以这一次第三个参数传的是一份空列表，更准确地说，是一个空的匿名结构体（.{}）。

const std = @import("std");
const Thread = std.Thread;
const duration = std.Io.Duration.fromSeconds(1);
const clock: std.Io.Clock = .awake;

fn do_some_work(io: std.Io) !void {
    std.debug.print("Starting the work.\n", .{});
    try std.Io.sleep(io, duration, clock);
    std.debug.print("Finishing the work.\n", .{});
}

pub fn main(init: std.process.Init) !void {
    const thread = try Thread.spawn(.{}, do_some_work, .{init.io});
    thread.join();
}
Starting the work.Finishing the work.

（译注：上一段和这段代码对不上。do_some_work() 有一个 io: std.Io 参数，调用处第三个参数是 .{init.io}，并不是空的 .{}。）

注意调用 spawn() 方法时用了 try。这意味着这个方法在某些情况下会返回错误。其中一种情况是，你试图再创建一条新线程，但已经创建得太多了（也就是超过了系统里并发线程的配额）。

不过，如果新线程创建成功，spawn() 方法会返回一个指向这条新线程的句柄对象（这个对象的类型就是 Thread）。你可以用这个句柄对象实际控制这条线程的方方面面。

线程被创建出来时，你作为输入提供给 spawn() 的那个函数会被调用，从而在这条新线程上开始执行。换句话说，每次调用 spawn()，不只是创建了一条新线程，这条线程的「开始工作按钮」也会被自动按下。所以这条线程里的工作在线程创建出来的那一刻就开始了。这和 C 语言 pthreads 库里的 pthread_create() 类似，它同样会在线程创建之后立即开始执行。

16.4 从线程返回

上一节讲过，线程一旦创建，执行就会开始。现在来看在 Zig 里怎样「汇合」（join）或「分离」（detach）一条线程。join 和 detach 是用来控制线程如何返回到主线程，或者说返回到程序主进程的操作。

这些操作通过线程句柄对象的 join() 和 detach() 方法来做。你创建的每条线程都可以被标记为可汇合（joinable）或已分离（detached）(Linux man-pages 2024)。对线程句柄对象调用 detach() 方法，可以把一条线程变成已分离线程。如果调用的是 join() 方法，这条线程就变成可汇合线程。

一条线程不能既是可汇合的又是已分离的。这通常意味着，你不能对同一条线程既调用 join() 又调用 detach()。但一条线程必须是二者之一。也就是说，你总是应该对一条线程调用 join() 或 detach() 当中的一个。如果这两个方法你一个都没对线程调用，就会给程序引入未定义行为，Section 16.8.2 里有说明。

下面分别说这两个方法会对你的线程做什么。

16.4.1 汇合线程

汇合一条线程时，你本质上是在说：「嘿！能不能请你等这条线程做完，再继续往下执行？」比如回到我们在 Zig 里的第一个、也是最简单的线程例子：我们在程序的 main() 函数里创建了一条线程，并在末尾对这条线程调用了 join()。这段示例代码复述如下。

因为我们是在 main() 的作用域里汇合这条新线程，所以 main() 函数的执行会暂时停下来，等待这条线程的执行结束。也就是说，main() 的执行会暂时停在调用 join() 的那一行，只有这条线程做完它的任务之后才会继续。

pub fn main() !void {
    const thread = try Thread.spawn(.{}, do_some_work, .{});
    thread.join();
}

因为我们在 main() 的作用域里汇合了这条新线程，我们就有了一个保证：这条新线程会在 main() 的执行结束之前做完。因为可以保证 main() 会等这条线程做完它的任务。

上面的例子里，join() 调用之后没有更多的表达式了。我们只剩下 main() 作用域的结尾，因此线程做完任务之后，程序的执行也就结束了，因为没有别的事可做。可如果汇合调用之后还有别的事要做呢？

为了演示这另一种可能，看看下面的例子。这里我们创建一个 print_id() 函数，它只接收一个 id 作为输入，并把它打印到 stdout。（译注：std.debug.print() 实际写到的是 stderr，不是 stdout。本章后面几处把线程输出说成 stdout 的地方同。）在这个例子里，我们一前一后创建两条新线程。然后汇合第一条线程，接着等待整整两秒，最后再汇合第二条线程。

（译注：正文说的是等两秒，下面代码里的时长却是 std.Io.Duration.fromNanoseconds(1000)，也就是 1000 纳秒，不是两秒。后文说最后一条消息大约两秒才出现，对应的也是正文，不是这段代码。）

这个例子背后的想法是：最后一次 join() 调用，要等第一条线程做完它的任务（也就是第一次 join() 调用），再加上那两秒延迟之后，才会执行。如果你编译并运行这个例子，会注意到大多数消息都很快打印到 stdout，也就是几乎立刻出现在屏幕上。不过，最后一条消息（「Joining thread 2」）大约要 2 秒才会出现在屏幕上。

const std = @import("std");
const Thread = std.Thread;
const clock: std.Io.Clock = .awake;
fn print_id(id: *const u8) !void {
    std.debug.print("Thread ID: {d}\n", .{id.*});
}

pub fn main(init: std.process.Init) !void {
    const id1: u8 = 1;
    const id2: u8 = 2;
    const thread1 = try Thread.spawn(.{}, print_id, .{&id1});
    const thread2 = try Thread.spawn(.{}, print_id, .{&id2});
    std.debug.print("Joining thread 1\n", .{});
    thread1.join();

    const duration = std.Io.Duration.fromNanoseconds(1000);
    try std.Io.sleep(init.io, duration, clock);

    std.debug.print("Joining thread 2\n", .{});
    thread2.join();
}
Thread ID: Joining thread 1
1
Thread ID: 2
Joining thread 2

这说明两条线程都很快就做完了它们的工作（也就是打印 ID），早于那两秒延迟结束。因此，最后一次 join() 调用几乎是立即返回的。因为当这最后一次 join() 发生时，第二条线程已经做完了它的任务。

如果你编译并运行这个例子，还会注意到，在某些情况下消息会彼此交织在一起。换句话说，你可能会看到消息「Joining thread 1」插在消息「Thread 1」中间，或者反过来。这是因为：

  • 这些线程基本上与程序的主进程（也就是 main() 函数）同时执行。
  • 这些线程与程序的主进程共享同一个 stdout，这意味着线程产生的消息和主进程产生的消息被送到完全相同的地方。

这两点前面在 Section 16.1 里都讲过。所以，由于这些消息大致在同一时间产生，并被送到同一个 stdout，它们可能会交织在一起。总之，当你对一条线程调用 join() 时，当前进程会等这条线程做完再继续；线程做完任务时，与这条线程相关的资源会被自动释放，当前进程再继续执行。

16.4.2 分离线程

分离一条线程时，与这条线程相关的资源会自动交还给系统，不需要另一条线程去和这条已经结束的线程汇合。

换句话说，对一条线程调用 detach()，就像你的孩子长大成人，也就是不再依赖你。一条已分离的线程自己释放自己；这条线程做完任务时，也不会把结果回报给你。因此，当你不需要使用线程的返回值，或者不在乎线程究竟在哪一刻做完工作，也就是线程自己把事情都解决掉的时候，通常会把线程标记为已分离。

看看下面的代码示例。我们创建一条新线程，把它分离，然后就在程序结束之前打印一条收尾消息。这里用的 print_id() 函数，和前面几个例子里用的是同一个。

const std = @import("std");
const Thread = std.Thread;
fn print_id(id: *const u8) !void {
    std.debug.print("Thread ID: {d}\n", .{id.*});
}

pub fn main() !void {
    const id1: u8 = 1;
    const thread1 = try Thread.spawn(.{}, print_id, .{&id1});
    thread1.detach();
    std.debug.print("Finish main\n", .{});
}
Finish main

如果你仔细看这个代码示例的输出，会注意到控制台上只打印了 main 里的那条收尾消息。本来应该由 print_id() 打印的那条消息没有出现在控制台上。为什么？因为我们程序的主进程先结束了，线程还没来得及说出任何东西。

这种行为完全没问题，因为线程已经被分离，所以它可以自己把自己释放掉，不必等主进程。如果你让 main 在结束之前再睡眠（或者说「等待」）额外的若干纳秒，你就很可能会看到 print_id() 打印的那条消息，因为你给了线程足够的时间，让它在主进程结束之前做完。

16.5 互斥锁

互斥锁是每个线程库里的经典组件。本质上，互斥锁是一面互斥标志（Mutually Exclusive Flag），这面标志像某种「锁」，或者说像你代码里某一段的看门人。互斥锁和线程同步有关。更具体地说，它们让你避开程序里一些经典的竞态条件，从而也避开那些通常很难追踪、很难看懂的严重 bug 和未定义行为。

互斥锁背后的主要想法，是帮助我们控制某一段代码的执行，并防止两条或更多线程同时执行这一段代码。很多程序员喜欢把互斥锁比作洗手间的门（这种门通常有锁）。一条线程锁上它自己的互斥锁对象时，就像洗手间的门被锁上了。因此，其他想同时使用同一间洗手间的人（在这里就是其他线程）必须耐心一点，干等当前的占用者（或者说线程）把门打开、从洗手间里出来。

另一些程序员也喜欢用「每个人轮流发言」这个比喻来解释互斥锁。这是 Computerphile 项目的视频 Multithreading Code 里用的比喻 1。想象你处在一个谈话圆圈里。圈子里有一位主持人，由这个人决定那一刻谁有权发言。主持人把一张绿卡（或者说某种授权卡）交给将要发言的人，于是其他所有人都必须安静下来，听这个拿着绿卡的人说话。这个人说完之后，把绿卡交还给主持人，主持人再决定下一个谁说，并把绿卡交给那个人。循环就这样继续下去。

互斥锁就像这个谈话圆圈里的主持人。互斥锁授权单独的一条线程去执行某一段特定的代码，同时挡住其他线程，不让它们执行同一段代码。如果这些其他线程想执行同一段代码，它们就被迫先等那条得到授权的线程做完。得到授权的线程执行完这段代码之后，互斥锁再授权下一条线程来执行这段代码，其余线程则继续保持被挡住的状态。因此，互斥锁就像一位主持人，做的是「每条线程轮流执行这一段代码」这种控制。

互斥锁尤其用来防止数据竞争问题发生。当两条或更多线程试图同时对同一个共享对象进行读或写时，就会出现数据竞争问题。所以，当你有一个所有线程都共享的对象，并且想避免两条或更多线程同时访问这同一个对象时，可以用互斥锁把访问这个特定对象的那部分代码锁住。一条线程试图运行被互斥锁锁住的这段代码时，这条线程会停住自己的执行，耐心等待这段代码被解锁之后再继续。

注意，互斥锁通常用来锁住那些访问或修改所有线程共享的数据的代码区域，也就是存放在全局数据区、或者存放在程序堆空间里的对象。所以，访问或修改线程局部对象的代码区域，通常不会用互斥锁。

16.5.1 临界区

临界区是一个常与互斥锁和线程同步联系在一起的概念。本质上，临界区就是程序里线程访问或修改共享资源的那一段（共享资源可以是一个对象、一个文件描述符，总之是所有线程都能访问的东西）。换句话说，临界区是程序里可能发生竞态条件的那一段，因此也是可能把未定义行为引进程序的地方。

在程序里使用互斥锁时，临界区划定了我们想要加锁的那片代码。所以我们通常在临界区的开头锁定互斥锁对象，在临界区的结尾解锁。下面两条要点出自 GeeksforGeeks 的文章《Critical Section》，很好地概括了临界区在线程同步问题里所起的作用 (Geeks for Geeks 2024)。

  1. 临界区必须作为一个原子操作来执行。这意味着一旦某个线程或进程进入了临界区，其他所有线程或进程都必须等待，直到正在执行的线程或进程退出临界区。同步机制的目的就是确保同一时刻只有一个线程或进程能够执行临界区。
  2. 临界区的概念是计算机系统中同步问题的核心，因为必须确保多个线程或进程能够并发执行而互不干扰。信号量、互斥锁、监视器、条件变量等各种同步机制都被用来实现临界区，确保共享资源以互斥的方式被访问。

16.5.2 原子操作

阅读线程、竞态条件和互斥锁的材料时，你也会经常看到「原子操作」这个词。简单说，一项操作如果在执行到一半时不可能发生上下文切换，就被归类为「原子」的。换句话说，这项操作总是从头做到尾，执行阶段中间不会被另一个进程或另一项操作打断。

如今没有多少操作是原子的。可为什么原子操作在这里要紧？因为数据竞争（这是一种竞态条件）不可能发生在原子的操作上。所以如果你代码里的某一行执行的是原子操作，这一行就永远不会碰上数据竞争问题。因此，程序员有时会用原子操作来保护自己，免得代码里出现数据竞争问题。

一项操作如果编译下来只有一条汇编指令，这项操作可能是原子的，因为它只是一条汇编指令。但这并没有保证。对老的 CPU 架构（比如 x86）这通常成立。可如今，现代 CPU 架构里的大多数汇编指令都会被拆成多个微任务，这本身就让这项操作变成非原子的，哪怕它只由一条汇编指令组成。

Zig 标准库在 std.atomic 模块里提供了一些原子功能。在这个模块里，你会找到一个公开的泛型函数，叫 Value()。用这个函数可以创建一个「原子对象」，也就是一个带有若干原生原子操作的值，其中最值得注意的是 load() 和 fetchAdd()。如果你有 C++ 多线程的经验，大概已经认出了这个模式。是的，Zig 里这个泛型的「原子对象」本质上和 C++ 标准库的模板结构体 std::atomic 一样。需要强调的是，这些原子操作在 Zig 里只支持基本数据类型（也就是 Section 1.5 里介绍的那些类型）。

（译注：Zig 0.17.1 里 std.atomic.Value 的测试也覆盖了 bool 和整数枚举。后文互斥锁的 State 是 enum(u32)，可以放进 std.atomic.Value。原文说「只有基本数据类型」，比实际能用的范围窄一点。）

16.5.3 数据竞争与竞态条件

要理解为什么要用互斥锁，需要更清楚地理解它们想解决的问题。这个问题可以概括成数据竞争。数据竞争问题是一种竞态条件：一条线程正在访问某个内存位置（也就是某个共享对象）的同时，另一条线程正试图把新数据写进、存进同一个内存位置（也就是同一个共享对象）。

我们可以简单地把竞态条件定义成：程序里任何一种建立在「谁先到那儿」之上的 bug。数据竞争问题是一种竞态条件，因为它发生在两方或更多方试图同时对同一个内存位置做读和写的时候，因此这项操作的最终结果完全取决于谁先到达这个内存位置。结果就是，一个有数据竞争问题的程序，每次执行都很可能得出不同的结果。

因此，竞态条件会制造未定义行为和不可预测性，因为每次换了一个人先到达目标位置，程序就会给出一个不同的答案。而且我们没有简便的办法预测或控制谁会先到这个目标位置。换句话说，程序每跑一次，你都可能得到一个不同的答案，因为每次是不同的人、函数或代码的某一部分先于其他人做完自己的任务。

作为一个例子，看看下面的代码片段。在这个例子里，我们创建一个全局的 counter 变量，还创建一个 increment() 函数，它的工作只是在一个 for 循环里给这个全局 counter 变量加一。

既然这个 for 循环迭代十万次，而这个代码示例里又创建了两条单独的线程，你预期打印到 stdout 的最后那条消息里会看到什么数字？答案应该是二十万。对吧？嗯，理论上这个程序结束时应该打印出二十万，可实际上，我每次执行这个程序都得到一个不同的答案。

在下面的例子里可以看到，这一次的最终结果是 117254，而不是预期的 200000。我第二次执行这个程序时，得到的结果是 108592。所以这个程序的最终结果在变，但从来到不了我们想要的那个 200000。

const std = @import("std");
const Thread = std.Thread;
var counter: usize = 0;
// Function to increment the counter
fn increment() void {
    for (0..100000) |_| {
        counter += 1;
    }
}

pub fn main() !void {
    const thr1 = try Thread.spawn(.{}, increment, .{});
    const thr2 = try Thread.spawn(.{}, increment, .{});
    thr1.join();
    thr2.join();
    std.debug.print("Couter value: {d}\n", .{counter});
}
Couter value: 117254

（译注：英文原文的代码和输出里把 Counter 拼成了 Couter，这里照原文保留，下一个示例同。）

为什么会这样？答案是：这个程序存在数据竞争问题。只有当第一条线程在第二条线程开始执行之前就做完它的任务时，这个程序才会打印出正确的数字 200000。但这种情况不太可能发生。因为创建线程的过程太快了，所以两条线程几乎是同时开始执行的。如果你改这段代码，在第一次和第二次调用 spawn() 之间加上几纳秒的睡眠，就会提高程序得出「正确结果」的概率。

所以，数据竞争问题的发生，是因为两条线程几乎在同一时间读写同一个内存位置。在这个例子里，每条线程在 for 循环的每次迭代中，本质上都在做三个基本操作，它们是：

  1. 读取 count 的当前值。
  2. 把这个值加 1。
  3. 把结果写回 count。

（译注：这里原文写的是 count，代码里的变量名是 counter。）

理想情况下，线程 B 应该在另一条线程 A 已经把加上去的值写回 count 对象之后，才去读 count 的值。因此，在理想情形里，也就是 Table 16.1 所演示的那样，这些线程应该彼此同步地工作。可现实是这些线程并不同步，因此它们碰上了数据竞争问题，Table 16.2 演示的就是这种情况。

注意，在数据竞争的情形里（Table 16.2），线程 B 做的那次读取发生在线程 A 的写操作之前，这最终导致程序结束时得到错误的结果。因为当线程 B 读取 count 变量的值时，线程 A 还在处理 count 的初始值，还没有把新的、已经加上去的值写回 count。结果就是，线程 B 读到的还是 count 的同一个初始值（或者说「旧」值），而不是线程 A 本来会写进去的那个更新过的、已经加上去的值。

如果你想一想这些画成表格的图，会注意到它们又回到了我们在 Section 16.5.2 里关于原子操作的讨论。记住，原子操作是 CPU 从头执行到尾、中间不会被其他线程或进程打断的操作。所以，Table 16.1 里的情形没有数据竞争，因为线程 A 所做的操作没有在中途被线程 B 的操作打断。

如果我们再想一想 Section 16.5.1 里关于临界区的讨论，就能找出代表这个程序临界区的那一段，也就是容易发生数据竞争条件的那一段。在这个例子里，程序的临界区就是我们给 counter 变量加一的那一行（counter += 1）。所以，理想情况下，我们想用一把互斥锁，在这一行之前锁定，紧接着在这一行之后解锁。

16.5.4 在 Zig 里使用互斥锁

现在我们知道了互斥锁想解决的问题，就可以学习怎样在 Zig 里使用它们。Zig 里的互斥锁通过 Zig 标准库的 std.Io.Mutex 结构体提供。如果我们拿上一个例子的同一段代码，用互斥锁改进它，以解决数据竞争问题，就得到下面的代码示例。

注意，这一次我们必须改 increment() 函数，让它接收一个指向 Mutex 对象的指针作为输入。要让这个程序免于数据竞争问题，我们需要做的就是在临界区的开头调用 lock() 方法，然后在临界区的结尾调用 unlock()。注意，这个程序的输出现在是正确的数字 200000。

const std = @import("std");
const Thread = std.Thread;
const Mutex = std.Io.Mutex;
const State = Mutex.State;
var counter: usize = 0;

fn increment(io: std.Io, mutex: *Mutex) !void {
    for (0..100000) |_| {
        try mutex.lock(io);
        counter += 1;
        mutex.unlock(io);
    }
}

pub fn main(init: std.process.Init) !void {
    var mutex: Mutex = .{
        .state=std.atomic.Value(State).init(.unlocked)
    };

    const thr1 = try Thread.spawn(.{}, increment, .{init.io, &mutex});
    const thr2 = try Thread.spawn(.{}, increment, .{init.io, &mutex});
    thr1.join();
    thr2.join();
    std.debug.print("Couter value: {d}\n", .{counter});
}
Couter value: 200000

16.6 读写锁

互斥锁通常用在这样一种场合：两条或更多线程同时跑同一段代码并不总是安全的。与此相对，读写锁通常用在你手里混着几种情形的时候。也就是说，代码库里有些片段并行着跑是安全的，另一些片段则不安全。

举个例子。假设你有多条线程，用文件系统里同一个共享文件来存放一些配置或者统计数据。如果两条或更多线程试图同时从这个同一份文件里读数据，不会有什么坏事发生。所以这部分代码完全可以安全地并行执行，多条线程同时读同一个文件也没问题。

可是，如果两条或更多线程试图同时往这个同一份文件里写数据，那就会造成一些竞态条件问题。所以这部分代码并行着执行是不安全的。更具体地说，一条线程可能会把数据写到另一条线程所写数据的中间。两条或更多线程对同一个位置做写，这个过程可能导致数据损坏。这种特定的情况通常叫作撕裂写入（torn write）。

因此，从这个例子里可以提取出的是：某些类型的操作会造成竞态条件，但也有另一些类型的操作不会造成竞态条件问题。你也可以说，有些类型的操作容易碰上竞态条件问题，另一些类型的操作则不会。

读写锁是一种承认存在这种特定情形的锁。你可以用这种锁来控制代码库的哪些部分并行着跑是安全的，哪些部分不安全。

16.6.1 独占锁与共享锁

因此，读写锁和互斥锁有一点不一样。因为互斥锁永远是一把独占锁，意思是任何时候都只允许一条线程执行。有了独占锁，其他线程永远是被「排除在外」的，也就是永远被挡住、不能执行。但在读写锁里，其他线程有可能被授权同时运行，这取决于它们拿到的是哪一种锁。

读写锁里有两种锁：独占锁和共享锁。独占锁的工作方式和互斥锁完全一样，共享锁则是一种不会挡住其他线程、让它们不能同时运行的锁。在 pthreads 这个 C 库里，读写锁通过 pthread_rwlock_t 这个 C 结构体提供。用这个 C 结构体，你可以创建：

  • 一把「写锁」，它对应独占锁。
  • 一把「读锁」，它对应共享锁。

这套术语和 Zig 比起来可能有点不一样。但意思仍然相同。所以只要记住这个对应关系：写锁是独占锁，读锁是共享锁。

一条线程试图获取读锁（也就是共享锁）时，当且仅当没有另一条线程当前正持有写锁（也就是独占锁），并且也没有其他线程已经在队列里等着轮到自己去获取写锁时，这条线程才会得到共享锁。换句话说，队列里的那条线程更早的时候就试图拿到写锁，但这条线程被挡住了，因为当时已经有另一条线程在跑，而且已经持有写锁。结果就是，这条线程排在获取写锁的队列里，当前正在等那条持有写锁的线程执行结束。

一条线程试图获取读锁，但没能拿到，要么是因为已经有一条持有写锁的线程在跑，要么是因为有一条线程在队列里等着获取写锁，这时这条线程的执行会立刻被挡住，也就是暂停。这条线程会一直不停地尝试拿到读锁，只有在它成功拿到读锁之后，执行才会被解除阻挡（或者说解除暂停）。

如果你深入想一想读锁和写锁之间的这种关系，可能会注意到读锁基本上是一种安全机制。更具体地说，它是一种办法，让我们只在安全的时候，才允许某一条线程和其他线程一起跑。换句话说，如果当前有一条持有写锁的线程在跑，那么这条正试图获取读锁的线程现在去跑，很可能并不安全。结果就是，读锁保护这条线程，不让它现在就跑进去，并耐心等待那条「写锁」线程做完任务，然后才继续。

另一方面，如果当前在跑的只有「读锁」（也就是「共享锁」）线程（也就是当前一条「写锁」线程都不存在），那么这条正在获取读锁的线程和其他线程并行着跑就是完全安全的。结果就是，读锁直接允许这条线程和其他线程一起跑。

因此，把读锁（共享锁）和写锁（独占锁）一起用，我们就能控制多线程代码的哪些区域或片段拥有并行是安全的，哪些片段拥有并行是不安全的。

16.6.2 在 Zig 里使用读写锁

Zig 标准库通过 std.Thread.RwLock 模块支持读写锁。（译注：正文写的是 std.Thread.RwLock。在 Zig 0.17.1 里，Thread 上没有 RwLock，读写锁是 std.Io.RwLock，下面的代码用的就是这个类型。）如果你想让某一条线程获取共享锁（也就是读锁），应该调用 RwLock 对象的 lockShared() 方法。如果你想让这条线程改为获取独占锁（也就是写锁），那就应该调用 RwLock 对象的 lock() 方法。

和互斥锁一样，通过读写锁对象拿到共享锁或独占锁之后，一旦到了「临界区」的末尾，我们也必须把锁解开。如果你拿到的是独占锁，那就调用读写锁对象的 unlock() 方法来解开这把独占锁。与此相对，如果你拿到的是共享锁，那就调用 unlockShared() 来解开这把共享锁。

作为一个简单的例子，下面的片段创建三条单独的线程，负责读取一个 counter 对象里的当前值，另外再创建一条线程，负责把新数据写进这个 counter 对象（更具体地说，就是给它加一）。

（译注：上面说的是会阻塞的 lockShared() 和 lock()。下面示例实际调用的是 tryLockShared() 和 tryLock()。这两个方法不会等待：拿到锁返回 true，没拿到返回 false，循环再试下一次。0.17.1 里阻塞版本 lockShared()、lock() 以及对应的 unlockShared()、unlock() 也都在。）

const std = @import("std");
const Thread = std.Thread;
const RwLock = std.Io.RwLock;
const duration = std.Io.Duration.fromSeconds(2);
const clock: std.Io.Clock = .awake;
var counter: u32 = 0;

fn reader(io: std.Io, id: u32, lock: *RwLock) !void {
    while (true) {
        if (lock.tryLockShared(io)) {
            std.debug.print("Thread {d}: {d}\n", .{id, counter});
            _ = lock.unlockShared(io);
            try std.Io.sleep(io, duration, clock);
        }
    }
}

fn writer(io: std.Io, lock: *RwLock) !void {
    while (true) {
        if (lock.tryLock(io)) {
            counter += 1;
            _ = lock.unlock(io);
            try std.Io.sleep(io, duration, clock);
        }
    }
}

pub fn main(init: std.process.Init) !void {
    var lock: RwLock = .init;
    const thr1 = try Thread.spawn(.{}, reader, .{init.io, 1, &lock});
    const thr2 = try Thread.spawn(.{}, reader, .{init.io, 2, &lock});
    const thr3 = try Thread.spawn(.{}, reader, .{init.io, 3, &lock});
    const wthread = try Thread.spawn(.{}, writer, .{init.io, &lock});

    thr1.join();
    thr2.join();
    thr3.join();
    wthread.join();
}

16.7 让出线程

Thread 结构体通过 yield() 方法支持让出。让出一条线程，意味着这条线程的执行被暂时停住，并被移到操作系统调度器所管理的优先级队列的末尾。

也就是说，让出一条线程时，你本质上是在对操作系统说：「嘿！能不能请你现在先别执行这条线程，过一会儿再回来继续它？」你也可以把这个让出操作理解成：「能不能请你把这条线程的优先级调低，先去专心做别的事？」所以这个让出操作也是一种办法，让你停住某一条线程，以便转去做其他线程、把其他线程的优先级抬高。

需要说明的是，让出线程在如今是一种「不太常见」的线程操作。换句话说，生产环境里用让出的程序员不多，原因很简单：这个操作不好用，也很难让它正确地起作用，而且还有更好的替代办法。大多数程序员更愿意改用 join()。事实上，大多数时候，你在某个代码示例里看到有人用这个「yield」操作，他们通常是拿它来帮助调试应用里的竞态条件。也就是说，这个「yield」操作如今大多被当作调试工具来用。

总之，如果你想让出一条线程，只要对它调用 yield() 方法，像这样：

thread.yield();

（译注：英文原文写作 thread.yield();。在 Zig 0.17.1 里，yield() 是 std.Thread 上不接收实例的函数，返回类型是 YieldError!void，要写成 try Thread.yield(); 才能通过编译。）

16.8 线程里的常见问题

16.8.1 死锁

当两条或更多线程永远被挡住，彼此等着对方释放一项资源时，就发生了死锁。这通常发生在牵涉到多把锁、而获取它们的顺序又没有安排好的时候。

下面的代码示例演示了一种死锁情形。这个例子里有两条不同的线程，执行两个不同的函数（do_some_work1() 和 do_some_work2()）。我们还有两把单独的互斥锁。如果你编译并运行这个代码示例，会注意到程序就这么一直跑下去，停不下来。

看第一条线程，它执行的是 do_some_work1() 函数。可以注意到这个函数先获取 mut1 这把锁。因为这是这条线程内部执行的第一个操作，而这条线程又是程序里创建的第一条线程。在那之后，函数睡眠 1 秒，用来模拟某种工作，然后函数试图获取 mut2 这把锁。

另一方面，看第二条线程，它执行的是 do_some_work2() 函数。可以看到这个函数先获取 mut2 这把锁。因为当这条线程被创建出来、试图获取这把 mut2 锁的时候，第一条线程还睡在那行「睡眠 1 秒」上。拿到 mut2 之后，do_some_work2() 函数也睡眠 1 秒，用来模拟某种工作，然后函数试图获取 mut1 这把锁。

这就造成了死锁。因为两条线程里那行「睡眠 1 秒」之后，线程 1 正试图获取 mut2 这把锁，可这把锁当前正被线程 2 使用。然而就在这个时刻，线程 2 也正试图获取 mut1 这把锁，而这把锁当前正被线程 1 使用。因此两条线程最终永远等下去，等着对方释放自己想获取的那把锁。

const std = @import("std");
const Thread = std.Thread;
const clock: std.Io.Clock = .awake;
const duration = std.Io.Duration.fromSeconds(1);
const State = std.Io.Mutex.State;
var mut1: std.Io.Mutex = .{.state=std.atomic.Value(State).init(.unlocked)};
var mut2: std.Io.Mutex = .{.state=std.atomic.Value(State).init(.unlocked)};

fn do_some_work1(io: std.Io) !void {
    try mut1.lock(io);
    try std.Io.sleep(io, duration, clock);
    try mut2.lock(io);
    std.debug.print("Doing some work 1\n", .{});
    mut2.unlock(io);
    mut1.unlock(io);
}

fn do_some_work2(io: std.Io) !void {
    try mut2.lock(io);
    try std.Io.sleep(io, duration, clock);
    try mut1.lock(io);
    std.debug.print("Doing some work 2\n", .{});
    mut1.unlock(io);
    mut2.unlock(io);
}

pub fn main(init: std.process.Init) !void {
    const thr1 = try Thread.spawn(.{}, do_some_work1, .{init.io});
    const thr2 = try Thread.spawn(.{}, do_some_work2, .{init.io});
    thr1.join();
    thr2.join();
}

16.8.2 不调用 join() 或 detach()

如果你对一条线程既不调用 join() 也不调用 detach()，这条线程就变成一条「僵尸线程」，因为它没有一个明确的「返回点」。你也可以把这理解成：「没有人真正负责管理这条线程」。当我们没有确定一条线程究竟是可汇合的还是已分离的，就没有人负责处理这条线程的返回值，也没有人负责清理（或者说释放）与这条线程相关的资源。

你不会想落到这种境地，所以记住，对你创建的线程总是要使用 join() 或 detach()。不用这两个方法当中的一个时，我们就失去了对这条线程的控制，它的资源也永远不会被释放（也就是说，你在系统里泄漏了资源）。

16.8.3 取消或杀死某一条线程

想到 pthreads 这个 C 库时，有一种异步杀死或取消线程的可能办法，就是通过 pthread_kill() 函数向线程发送 SIGTERM 信号。但像这样取消一条线程是糟糕的。糟糕到危险的地步。因此，Zig 的线程实现没有一个类似的函数，也没有一种类似的办法来异步取消或杀死一条线程。

（译注：POSIX 里用来取消线程的接口是 pthread_cancel()，不是 pthread_kill()。pthread_kill() 是向指定线程发信号。把 SIGTERM 发给某一条线程，通常会影响整个进程，并不是安全地「只杀掉这一条线程」。原文的结论仍然成立：Zig 没有提供异步取消或杀死线程的办法。）

因此，如果你想在 Zig 里让一条线程在执行到一半时取消，可以采用的一个不错的策略是把控制流和 join() 结合起来用。更具体地说，你可以把线程设计成围绕一个 while 循环，这个循环不断检查线程是否应该继续运行。如果到了该取消线程的时候，我们可以让 while 循环跳出，并通过调用 join() 让这条线程与主线程汇合。

下面的代码示例在一定程度上演示了这个策略。这里我们用控制流跳出 while 循环，让线程比我们最初计划的更早退出。这个例子也演示了怎样在 Zig 里使用原子对象，用的就是我们在 Section 16.5.2 里提到的那个泛型函数 Value()。

const std = @import("std");
const Thread = std.Thread;
const clock: std.Io.Clock = .awake;
const duration = std.Io.Duration.fromSeconds(2);
var running = std.atomic.Value(bool).init(true);
var counter: u64 = 0;

fn do_more_work(io: std.Io) !void {
    try std.Io.sleep(io, duration, clock);
}

fn work(io: std.Io) !void {
    while (running.load(.monotonic)) {
        for (0..10000) |_| {
            counter += 1;
        }
        if (counter > 15000) {
            std.debug.print("Time to cancel the thread.\n", .{});
            running.store(false, .monotonic);
        } else {
            std.debug.print("Time to do more work.\n", .{});
            try do_more_work(io);
        }
    }
}

pub fn main(init: std.process.Init) !void {
    const thread = try Thread.spawn(.{}, work, .{init.io});
    thread.join();
}
