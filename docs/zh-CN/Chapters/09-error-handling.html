10  错误处理与联合体（Unions）

在本章中，我想讨论 Zig 中的错误处理是怎么做的。我们已经简单了解过 Zig 中处理错误的一种策略，也就是 Section 1.2.3 中介绍的 try 关键字，但还没有学习其他方法，比如 catch 关键字。我还想在本章中讨论如何在 Zig 中创建联合体类型。

10.1 核心认知：错误是一等公民的值（Errors as Values）

在搞懂具体语法前，首先必须建立起对 Zig 错误哲学的认知：在 Zig 里，错误本质上是一个实在的具体数值（Value）！ (Zig Software Foundation 2024a) 它既不是隐秘抛出、不知在何处被接住的运行时异常（Exception），也不是深不见底的黑盒。 错误值可以像普通整数一样在函数间传递、可以存入变量、可以进行集合转换。

写惯了 Python 或 C++ 的同学可能习惯了抛异常（throw）。但在那些语言里，调用方很容易因遗漏 try-catch 而导致未捕获异常一路击穿整个调用栈。 而在 Zig 里，所有可能发生的错误都必须显式处理，编译器绝不允许你视而不见！ 你甚至不能像对待普通变量那样，用下划线 _ 随手把一个错误联合结果丢弃掉：

const cwd = std.Io.Dir.cwd();
// 试图对可能报错的操作用下划线蒙混过关
_ = cwd.openFile(
    init.io, "doesnt_exist.txt", .{ .mode = .write_only }
);

编译器一眼识破并当场报错：

t.zig:8:17: error: error set is discarded
t.zig:8:17: note: consider using 'try', 'catch', or 'if'

编译器会提醒你：这里返回的是可能包含错误的错误联合类型，需要用 try、catch 或 if 处理。

10.1.1 从函数中返回错误：感叹号 ! 与错误联合

如果一个函数在执行过程中可能会报错，那它的返回值类型签名里就必须带上感叹号 !（表示错误联合 Error Union）：

fn print_name(stdout: *std.Io.Writer) !void {
    try stdout.print("My name is Pedro!", .{});
    try stdout.flush();
}

在上面的 !void 中，感叹号左侧没有显式指定错误类型，这叫推导错误集（inferred error set），由编译器分析函数体，推导出函数可能返回的错误集合。

如果你愿意，也可以在感叹号左边显式指定函数可能返回的错误集。这样一来，编译器就能检查函数中是否产生了返回类型里没有声明的错误：

<error-value>!<valid-value>

（即：<错误值>!<正常返回值>。）

例如 Zig 标准库 HTTP 客户端模块里的 fill() 函数：

pub fn fill(conn: *Connection) ReadError!void {
    // 函数体...
}

这清楚地告诉所有调用者：该函数要么成功返回 void，要么只会返回属于 ReadError 范围内的具体错误！

10.1.2 错误集（Error Sets）

当一个函数可能返回多种不同类型的错误时，我们可以用 error{ ... } 定义一个错误集（Error Set）。错误集本质上是一种特殊的联合体类型（Union，我们将在 Section 10.3 中深入探讨联合体）：

pub fn resolvePath(
    ally: mem.Allocator,
    p: []const u8,
) error{
    OutOfMemory,
    CurrentWorkingDirectoryUnlinked,
    Unexpected,
}![]u8 {
    // 函数体...
}

在真实工程里，通常会给这组错误起一个清晰的大写类型名复用：

pub const ReadError = error{
    TlsFailure,
    TlsAlert,
    ConnectionTimedOut,
    ConnectionResetByPeer,
    UnexpectedReadFailure,
    EndOfStream,
};

pub fn readvDirect(
        conn: *Connection,
        buffers: []std.posix.iovec
    ) ReadError!usize {
    // ...
}

10.1.3 错误值的类型转换（从子集到超集）

如果错误集 A 包含了错误集 B 里的所有成员（即 \(A \supset B\)），那么在 Zig 中，B 集合里的错误值可以隐式自动转换为 A 集合类型：

const std = @import("std");
const A = error{
    ConnectionTimeoutError,
    DatabaseNotFound,
    OutOfMemory,
    InvalidToken,
};
const B = error {
    OutOfMemory,
};

fn cast(err: B) A {
    return err; // 隐式转换为超集类型
}

test "coerce error value" {
    const error_value = cast(B.OutOfMemory);
    try std.testing.expect(
        error_value == A.OutOfMemory
    );
}
1/1 file6de04e52901.test.coerce error value...OK
All 1 tests passed.

10.2 优雅处理错误的四大姿势

在 Zig 中，处理错误主要有以下四种常用策略：

  • try 关键字；
  • catch 关键字；
  • if 语句；
  • errdefer 关键字。

10.2.1 try 的真正含义：向上传播错误

正如我们在 Section 1.2.3 中初次见到的，当一个表达式的返回类型为 !T 时，使用 try expr 的语义是： 请执行该表达式；如果它返回了合法的正常值，则解包并返回该值继续往下走；但如果它返回了错误值，则立即将该错误从当前函数中 return 返回出去，并终止当前函数的继续执行。

换言之，当你认为遇到错误时最合理的策略就是立即中止当前流程并将错误向上传播时，就使用 try。

10.2.2 catch 关键字：就地捕获与兜底

需要特别注意的是：在 Zig 中，你可以使用 try 或 catch 来处理错误，但绝不能将 try 和 catch 连在一起同时使用！在 Zig 里，try 和 catch 是两套完全独立的错误处理策略。

catch 放在可能报错的表达式后面，负责拦截错误并就地解决：

10.2.2.1 1. 提供默认值

如果报错，就自动回落到默认值，极具表现力：

// 解析失败时自动兜底为数字 13
const number = parseU64(str, 10) catch 13;

10.2.2.2 2. 接错误处理逻辑块

通过 catch |err| { ... } 捕获具体错误对象并写日志或做后置处理：

pub fn main(init: std.process.Init) !void {
    const cwd = std.Io.Dir.cwd();
    const file = cwd.openFile(
        init.io, "doesnt_exist.txt", .{}
    ) catch |err| {
        logger.record_context();
        logger.log_error(err);
        return err; // 记录完日志后再次抛出
    };
}

10.2.3 使用 if 语句处理错误

你也可以使用 if 语句来处理 Zig 中的错误：如果表达式返回正常值，则将其解包到 |number| 中执行 if 分支；如果返回错误，则在 else |err| 分支中捕获并处理该错误：

if (parseU64(str, 10)) |number| {
    // 成功分支，拿到纯净的 number
} else |err| {
    // 失败分支，拿到具体的 err
}

如果表达式可能返回多种不同类型的错误，且你希望针对每种具体错误采取不同的处理逻辑，Zig 官方文档建议将 if 语句与 switch 语句结合使用 (Zig Software Foundation 2024b)：

if (add_tasks_to_queue(&queue, tasks)) |_| {
    distribute_tasks(&queue);
} else |err| switch (err) {
    error.InvalidTaskName => {
        // 处理无效任务名
    },
    error.TimeoutTooBig => {
        // 处理超时超限
    },
    error.QueueNotFound => {
        // 处理队列未找到
    },
}

10.2.4 errdefer 关键字：错误回滚清理

回顾我们在 Section 2.1.3 和 Section 2.1.4 中介绍过的 defer 与 errdefer：无条件的 defer 总是在当前作用域结束时执行，而 errdefer 登记的动作，只有在退出当前作用域且伴随着错误发生时才会执行！

思考一个典型场景：函数使用我们在 Section 3.3 中介绍的分配器在堆上创建了一个新的 User 对象，将其注册到数据库中，最后把该 user 对象作为返回值交出去：

fn create_user(db: Database, allocator: Allocator) !User {
    const user = try allocator.create(User);
    errdefer allocator.destroy(user); // 挂上防漏油阀门！

    // 如果向数据库插入时报错提前退出了：
    _ = try db.register_user(user);
    
    // 如果一切顺利，user 成功交出，errdefer 不会触发，调用方负责接管其生命周期
    return user;
}

如果在入库那一行（db.register_user）报错了，函数中断退出，普通的 defer 此时帮不上忙（因为正常返回时不能销毁它）；而 errdefer 则精准介入，在函数带着错误返回之前，释放刚刚申请的 user，保证这块内存在出错时也会被释放。

10.3 联合体（Unions）与带标签联合体（Tagged Unions）

联合体（Union）定义了一个变量在某一瞬间只能是多种可能类型中的某一种。 它与 C 语言中的 union 作用相同，效果上也类似于在 Python 中使用 typing.Union1。

举个跨多云存储的实际例子：数据既可能传往 AWS S3、也可能发给 Azure Blob 或 Google Cloud：

const LakeTarget = union {
    azure: AzureBlob,
    amazon: AmazonS3,
    google: GoogleGCP,
};

fn send_event(
    event: Event,
    lake_target: LakeTarget
) bool {
    // 函数体...
}

下面的例子演示了这一逻辑。注意，我们先用 azure 数据成员实例化这个联合体对象，所以这个 target 对象中只包含 azure 数据成员，只有这个数据成员处于激活状态。这就是为什么这个代码示例的最后一行是无效的：我们试图实例化当前对这个 target 对象来说处于非激活状态的数据成员 google，结果程序进入 panic 模式，用一条醒目的错误信息警告我们犯了这个错误。

var target = LakeTarget {
    .azure = AzureBlob.init()
};
// Only the `azure` data member exist inside
// the `target` object, and, as a result, this
// line below is invalid:
target.google = GoogleGCP.init();
thread 2177312 panic: access of union field 'google' while
    field 'azure' is active:
    target.google = GoogleGCP.init();
          ^

所以，在实例化一个联合体对象时，必须从联合体类型列出的数据类型（即数据成员）中选择一个。在上面的例子中，我选择使用 azure 数据成员，结果其他所有数据成员都自动处于非激活状态，实例化对象之后就不能再使用它们了。

你可以通过完全重新定义整个联合体对象来激活另一个数据成员。在下面的例子中，我一开始使用 azure 数据成员，然后把 target 对象重新定义为一个使用 google 数据成员的新 LakeTarget 对象。

var target = LakeTarget {
    .azure = AzureBlob.init()
};
target = LakeTarget {
    .google = GoogleGCP.init()
};

10.3.1 带标签联合体（Tagged Unions）

普通 union 的一个局限是无法直接作为我们在 Section 2.1.2 中介绍的 switch 语句的输入。 如果需要在 switch 语句中对联合体对象进行分支匹配，只需在 union 声明后加上 (enum)，将其定义为带标签联合体（Tagged Union）！

看 Zig 仓库中的 grammar.zig2 里的写法：

pub const Registry = union(enum) {
    core: CoreRegistry,
    extension: ExtensionRegistry,
};
